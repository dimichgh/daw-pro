### F8 😖 — a repeating groove costs its full note array, every time, through the agent's own context

**Hit at:** cycle 1, writing a twelve-bar shuffle for five instruments.

**What happened.** A twelve-bar blues is, musically, *one bar of rhythm applied to a
twelve-bar chord map*. To express that through `clip_add_midi` I had to materialise
**every note**: drums 149 notes / 9.2 KB, guitar 144 / 8.9 KB, bass 96 / 6.1 KB, organ 48,
lead 54. **~30 KB of JSON for one twelve-bar chorus of one song** — and it crosses the
agent's context TWICE, once to generate it and once to send it.

**Mechanism.** There is clip-level repetition (`clip_duplicate`) but **no bar-level or
pattern-level primitive anywhere on the surface**: no "repeat these notes every N beats",
no "apply this rhythm to this chord sequence". So the repetition that is obvious in the
music has no representation in the API, and the agent pays for it in full.

**Why this matters more than it looks.** It is not merely verbose — it is the difference
between an agent that can write a 3-minute arrangement and one that runs out of output
budget partway. Session 1 already measured `project_snapshot` at ~290 KB for a modest song
and called that past an agent's limit; this is the same wall approached from the WRITE
side, and it arrives sooner because writing is what composing mostly is.

**⚠️ Not yet a proposal.** Two plausible shapes (a pattern/repeat argument on
`clip_add_midi`; or a `clip_repeat_notes` verb taking a source span and a count) and I have
not established which fits the undo model — paste already needed its own grow block to
avoid folding into an adjacent edit, so a repeat verb has the same hazard. Filed as
mechanism, not as a design.

**Workaround being tested next, and it is a real one:** write a Standard MIDI File and use
`clip_import_midi`. That is what a user with existing material would do anyway, so it
doubles as coverage of the import path.

### F9 🐛 — `clip_duplicate` echoes the whole note array back; it is the THIRD site of the m30-b defect

**Hit at:** cycle 1, repeating the twelve-bar rhythm section across Verse/Solo/Verse.

**What happened.** `clip_duplicate` on a 149-note drum clip returned **24,702 characters /
1,054 lines** — the complete note array, every note with a fresh id. For an operation whose
entire meaning is *"copy that clip to beat 64"*. The caller already has those notes; they
are the source clip's, which the caller just made.

**Why it is the same defect, not a new one.** m30-b gave `clip_add_midi` a `returnNotes:
false` opt-out for exactly this. m30-g is already filed for "the SOURCE-side note echo +
the `clip_set_notes` sibling". **`clip_duplicate` is a third site nobody enumerated**, and
it is arguably the worst of the three, because duplication is inherently the BULK
operation — you reach for it precisely when there are many notes, and you call it many
times. Twelve duplications is an ordinary arrangement task; at this rate that is ~200 KB of
pure echo.

⭐ **The meta-finding: m30-b was fixed AT ONE CALL SITE rather than as a class.** Nobody
asked "what else returns a note array the caller did not ask for?" That question, asked
once, would have found this.

**Mitigation that already exists and worked.** The MCP result-elision machinery caught it,
spilled the full reply to a temp file, and handed back head + strided samples with exact
line ranges and an explicit "do NOT re-run this mutating call" warning. **That is good
design under pressure and it saved this session** — real context cost was ~2 KB, not 24 KB.
So this is friction, not a wall. But the fields a caller actually needs from a duplicate —
`trimmed` and `removed`, which say what the overlap policy just edited — end up buried
under a thousand lines of data nobody wanted.

**⚠️ WIDENED MID-SESSION — it is a CLASS, and I found the fourth site while writing the
workaround for the third.** `clip_remove_many` documents its return as `{clips}`, *the
removed clips* — notes included. **MEASURED, not estimated: removing ten clips returned 199,858 characters / 7,332 lines
— 200 KB to report a DELETION.** The caller is destroying those notes; it cannot possibly
need them enumerated. That single call is two-thirds the size of the `project_snapshot`
figure session 1 called past an agent's limit. Known sites now: `clip_add_midi` (fixed, m30-b), `clip_set_notes` +
source-side echo (filed, m30-g), **`clip_duplicate`** (this finding), **`clip_remove_many`**.
Nobody has enumerated the surface; each was found by tripping over it. **The roadmap item
should be "audit every tool that returns a note array and justify each one", not a fifth
one-site patch.**

**Fix shape (precedented, low risk):** `returnNotes: false` on `clip_duplicate`, the m30-b
contract verbatim. Additive, so no wire rename. Should be done as a CLASS sweep with
m30-g, not as another one-site patch.

### F10 🔍🧱 — the MCP server process is **6h10m older than the code it serves**, and nothing on the surface can tell you

**Hit at:** cycle 1, reaching for `edit_paste_clips`' `atBeat` — which m25-f-4 added, which
I had *written about in this very session*, and which the live tool schema does not have.

**Measured:**

| | |
|---|---|
| MCP server process `mcp-server/dist/index.js` started | **Sun Aug 23 16:41:06** |
| `mcp-server/dist/server.js` built | **Sun Aug 23 22:51:31** |
| gap | **6 h 10 min** |

The BUILD is current — `grep` finds `edit.pasteClips", { trackId, atBeat })` in
`dist/server.js`, and the source at `src/server.ts:48,61-62` declares and forwards it. **The
artifact is right and the process is stale.** Every tool schema this session has seen came
from a node process launched before half the day's work existed.

⭐⭐⭐ **THE LAW THIS BUYS, AND IT SHARPENS AN EXISTING ONE: VERIFYING THE ARTIFACT IS NOT
VERIFYING WHAT IS RUNNING.** The `/dogfood` skill's own "finish the loop" step says
regenerate the bundle and *verify the bundle carries the change by grepping it, with a
positive control*. **That procedure passes here and is still wrong.** The grep finds the
string; the running process has never read the file. A check that inspects the artifact
gives a confident all-clear about a process it never touched — the same shape as this
tree's standing warnings that a setter's return is not proof it took, and that two
instruments disagreeing is the signal.

**Why an agent cannot self-diagnose this.** There is no build identity anywhere on the
surface. `app_connection_info` reports the APP's port and where it came from — nothing
reports the SERVER's version, build time, or source hash. `tools/list` returns whatever the
process compiled at launch, with no provenance. So the failure is silent and looks exactly
like "that feature was never built", which is precisely the wrong conclusion: **I would
have filed `atBeat` as missing had I not gone and read the source.**

**⚠️ This retro-qualifies a claim I made earlier in this same session** — that `atBeat` was
added to `edit_paste_clips`. True of the source; **not exercisable through the live
bridge**, and I had no way to know that from inside.

**Fixes, in the order I would do them:**
1. **`app_connection_info` (or a new `mcp_server_info`) should report the SERVER's own
   build identity** — build timestamp and/or a hash of `server.js` read AT STARTUP, plus
   the mtime of the file on disk NOW. Those two disagreeing is the whole diagnosis, and it
   is three lines of code. **Route: `mcp-integration-engineer`.**
2. **Amend the `/dogfood` skill's step 3**: regenerating and grepping the artifact is
   necessary and NOT sufficient — the serving process must be restarted, and the restart
   must be verified from the CLIENT side (a schema field that did not exist before), never
   from the file.
3. Note the secondary point: `edit_paste_clips` cannot be driven by an agent at all —
   there is no wire route to PUT anything on the app's clipboard, so it only ever fires
   what a human last copied. Its `atBeat` is a UI mirror, not an agent capability.

### F11 📄 — `render_bounce`'s documented remedy for "too quiet" does not work as written

**Hit at:** cycle 1, trying to land a −20.7 LUFS blues mix at the −14 LUFS streaming target.

**What the description promises.** `render_bounce`'s own text says: *"If you need to close
that gap, add the built-in limiter effect to the master bus (or the track/bus feeding it)
and call render_bounce again: the limiter does real dynamics control, letting a subsequent
gain push closer to the ceiling safely."*

**What actually happens.** I added exactly that limiter — `truePeak: 1`, `ceilingDb: -1` —
and re-bounced. Result: `appliedGainDb: 3.90`, `integratedLufs: -18.34`,
`limitedByCeiling: true`. **Still 4.3 dB short, and adding the limiter had not moved the
outcome toward the target at all.**

**Mechanism.** `render_bounce`'s normalizing gain is applied **after** the master insert
chain, and its clamp is computed from the post-chain true peak. So a limiter on the master
cannot protect that gain — it has already finished processing by the time the gain is
applied. A limiter downstream of the gain is what the sentence describes; a limiter
upstream of it is what you get.

**What actually works** (and it is the fix the wire reference already gives for the +6 dB
master-fader cap, just not cross-referenced here): insert your **own `gain` stage at index
0 of the master chain, ahead of the limiter**. With `gainLinear: 2.5` (≈ +8 dB) then the
limiter, the same bounce landed at **−14.83 LUFS / −1.0000 dBTP** — on spec.

**So the honest shape of the workflow is:** *you* supply the makeup gain, the limiter
catches the peaks, and `render_bounce`'s `lufsTarget` ends up doing nothing
(`appliedGainDb: -0.0000032`) because the signal already sits at the ceiling. Note that
`limitedByCeiling: true` is reported in BOTH the failure and the success case, so it does
not discriminate between them — the field to read is `output.integratedLufs` against your
target, which the description does say.

**Fix:** rewrite that sentence to name the ordering — *"add a `gain` insert at index 0 of
the master chain and a `limiter` after it; `lufsTarget` cannot exploit a master limiter
because the normalizing gain is applied after the chain."* Cheap, and it turns a
three-render fumble into one. **Route: `docs-scribe` for the text; `mcp-integration-engineer`
if the gain should instead be applied pre-chain, which is the deeper fix.**

### M3 🔍 — I nearly blamed the limiter for my own mix moves

Between the −20.74 LUFS baseline and the −22.24 LUFS pre-gain reading I had ALSO cut the
organ to 0.6 and the rhythm guitar to 0.75. For a moment the 1.5 dB drop looked like a
limiter attenuating a signal that never reached its ceiling — which would have been a real
engine bug, and I was one sentence from writing it up. **The confound was mine, introduced
between the two measurements.** Recorded because the near-miss is the lesson: when two
readings of "the same thing" disagree, enumerate what YOU changed between them before
reaching for a defect in the product.

### F12 📄 — the genre roster's track KINDS are invisible until you trip over them, and "Samples" is the trap

**Hit at:** cycle 2, trying to put the Sampler on the track named **"Samples"**.

```
track kind 'audio' cannot host an instrument — only instrument tracks carry an
instrument (add one with track.add kind=instrument)
```

**Measured roster for `lo-fi`:** Drums `instrument`, Bass `instrument`, Keys `instrument`,
**Samples `audio`**, **Vinyl FX `audio`**. Two of five cannot take a MIDI clip.

**Why this is worse than the known vocal case.** The wire reference already warns that
"almost every genre scaffolds a vocal AUDIO track" — but it frames that as a *vocal*
problem, and **lo-fi has no vocal track at all**, so the warning does not fire in the
reader's head. Meanwhile `macro_song_skeleton`'s description lists every genre's roster by
NAME and never once says which entries are `instrument` and which are `audio`. The kinds
are only discoverable by calling `project_overview` after the fact, or by failing.

**And the specific naming collision is unlucky:** the track called **"Samples"** is exactly
the one an agent reaches for when it wants the **Sampler** — the instrument whose whole job
is playing samples. That is the single most predictable wrong guess on this genre, and it
is the one the roster punishes.

⭐ **The error message is genuinely good** — it names the kind, the rule, and the fix in one
line. That is why this cost thirty seconds rather than ten minutes, and it is worth saying
so: most of this session's findings are about places where the product told me nothing.

**Fix (cheap, doc-only):** annotate the kinds in `macro_song_skeleton`'s genre listing —
`Drums (instrument), … Samples (audio), Vinyl FX (audio)`. The information already exists;
it is simply not written down where the decision is made. **Route: `docs-scribe`**, then
regenerate the plugin bundle. Consider also renaming lo-fi's "Samples" to "Sample Bed" or
marking it "(audio — for imported files; use the Sampler on an instrument track)".

### ✅ VERIFIED WORKING — the sidechain recipe, end to end, and it is MEASURED not asserted

The wire reference's documented all-MIDI recipe worked first try, exactly as written:
`track_add {kind:"bus"}` → `track_set_output` keys+sampler into it → `fx_add` compressor on
the bus → `fx_set_sidechain` keyed from the **instrument** drum track.
`sidechainSkewSamples: 0`.

⭐ **And I did not stop at the API's echo.** `sidechainSourceTrackId` coming back in the
response only proves the field was stored. To prove the KEY changes the AUDIO, I cleared it
to self-keyed and re-measured the same render:

| | keyed from drums | self-keyed |
|---|---|---|
| loudnessRangeLu | **4.88** | **7.18** |
| maxMomentaryLufs | −9.31 | −11.18 |
| integratedLufs | −14.66 | −14.82 |

A 2.3 LU difference in loudness range. **The ducking is real.** This is the kind of claim
that is usually filed as "wired up, sounds right" — it costs two extra calls to make it a
measurement instead.

### M4 🔍 — a near-miss I chased for three calls: the harness, not the product

I passed `sourceTrackId` as a bare `null` to clear the key, then noticed the schema accepts
`string | null` and thought I had passed the **string** `"null"` — which should have been
rejected as a non-UUID. It cleared the key instead, which looked exactly like M30's
`"undefined"` string-sentinel coercion bug reappearing.

**It is not a bug.** A bogus string (`definitely-not-a-real-track-id`) errors correctly with
`'sourceTrackId' is not a valid UUID`, and `grep` finds **no** `"null"`/`"undefined"`
literal anywhere in `server.ts` or `bridge.ts` — positive-controlled on the same file. The
tool-call encoding serialises a bare `null` token as JSON null. **I sent null; the product
did the right thing.**

⭐ **Worth keeping because of the shape:** the evidence that killed this was the ABSENCE of
a coercion in the source, and I only trusted that absence because I positive-controlled the
grep on the same file first. An unverified empty grep here would have "confirmed" the
opposite conclusion just as comfortably.

## What the three cycles say together

**Everything musical worked.** Three arrangements in three genuinely different forms —
a repeating harmonic cycle, a loop-based form with no sections in the pop sense, and a
32-bar AABA with named solo choruses — all scaffolded, written, mixed, rendered and
measured without hitting a single wall. All three landed within **0.9 dB of the −14 LUFS
target at exactly −1.00 dBTP**, and cycle 1's file was independently confirmed by
`ffmpeg ebur128`.

**Nothing that broke was in the audio.** Every finding is on the AGENT SURFACE: response
sizes, a stale process, a doc sentence that describes the wrong signal order, a roster whose
types are invisible. That is a meaningful result in itself — the engine is not what is
holding an agent back.

⭐⭐ **The through-line across F9, F10 and F12: three of the five findings are cases where
the product KNEW something and did not say it.** The server knew its build time. The roster
knew its track kinds. The duplicate knew the caller already had those notes. None of that
reached the caller. Session 1's meta-finding was that this tree's characteristic failure is
returning something that LOOKS like a valid answer; round 2's is narrower and more
actionable — **the information exists, it is just not on the wire.**

⭐ **Credit where the design held up under pressure.** The result-elision machinery turned a
200 KB reply into 2 KB with exact line ranges and an explicit "do NOT re-run this mutating
call" warning — it is the single reason F9 is friction rather than a session-ending wall.
The `track kind 'audio' cannot host an instrument` error names the rule AND the fix in one
line. The `clip_import_midi` report gives per-part note counts, `notesPastClipEnd`, and a
`dryRun` that lets you look before committing. These are the places where somebody thought
about the caller.
