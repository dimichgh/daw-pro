# Dogfood session 1 — 2026-08-23

**Build:** `06dca3d`, `dist/` rebuilt at HEAD for this session.
**Method:** make an actual piece of music end to end, driving the app the way an agent
user would. Record friction AS IT HAPPENS, before it is rationalised away. Then fix it.

> **Why this exists.** All four defects the sax team reported were found by making music,
> and the suite was green through every one of them. 6645 tests did not notice that a
> bounce silently dropped an instrument's first entry. A test suite answers questions we
> already knew to ask; this is for the ones we didn't.

## Rules for this log

1. **Write the friction down BEFORE fixing it.** A problem you fixed in ninety seconds
   still cost a real user ninety seconds, and the record is the deliverable.
2. **Distinguish** 🐛 defect · 🧱 missing capability · 😖 works-but-hostile · 📄 doc/discoverability.
   The last two are the ones a test suite structurally cannot find.
3. **No silent recoveries.** If I worked around something, the workaround IS the finding.
4. Numbers where numbers exist. "Felt slow" is a finding; "took 24 s" is a better one.

## Log

### F1 📄 — the shared wire reference says we cannot do the thing we shipped today

**Found:** before making a single note, reading `daw-wire-reference` as instructed.

`claude-plugin/skills/daw-wire-reference/SKILL.md` states, under *"Overlap masks a
retrigger; it does not create legato"*:

> **No instrument in this app has a legato mode.** Every note-on starts a new voice with
> a fresh attack — the built-in sampler and the hosted AUSampler both.

That is false as of `06dca3d`, committed today: `SamplerVoiceMode.mono` exists
(`Sources/DAWCore/Model.swift:1800`) with LAST-NOTE priority, built precisely so a sax
line slurs. `m27-o`'s `legatoOverlapBeats` also ships.

**Why this is worse than ordinary doc rot.** Every agent in the plugin is pointed at this
file, and this passage does not merely omit the feature — it tells the reader the
capability *does not exist* and that any claim otherwise *"is wrong"*. An agent asked for
a slurred line would follow it straight past `voiceMode: "mono"` to the masking
workaround. The doc is confidently, actively wrong, which is this project's own
signature failure mode wearing a documentation hat.

**Cost if unfixed:** every future music agent silently declines a shipped feature.

### F3 📄 — `clip_add_midi`'s tool description told agents MIDI clips are silent

`mcp-server/src/server.ts:3506` shipped this on every `clip_add_midi` call:

> NOTE: MIDI clips are silent until an instrument is wired up (M3) — the data model and

**M3 is 8/8 complete with zero open items.** A new instrument track resolves to the

Fixed to say what is true and point at `track_set_instrument`.

⚠️ **This one needs `npm run bundle:plugin`** — the generated `claude-plugin/server/index.mjs`

**Trap I hit finding it, worth recording:** grepping the full sentence returned NOTHING in

*positive control* — a phrase I knew was in the same description — ALSO returned nothing,
which is the only reason I didn't conclude the text lived somewhere else. A single-line
pattern cannot match a multi-line concatenation. **On this codebase's tool descriptions,
grep short fragments, never sentences.**

### M1 🔍 META — three doc defects before I played a single note

F1, F2 and F3 were all found by *reading the instructions*, not by using the app. The
common cause is not carelessness — every one of these files is unusually well written.
It is that **nothing links a shipped capability to the prose that describes it.** The
sampler gained `voiceMode` in `06dca3d` and three separate documents kept saying it could

The suite cannot catch this class: a stale sentence compiles, ships, and passes 6656 tests.
**Candidate fix worth costing: a gate that fails when a doc asserts a capability the code
contradicts** — even a narrow one (a list of "we cannot do X" claims, each pinned to a
symbol whose existence would falsify it) would have caught F1 the moment mono landed.

## The spectrogram experiment (the user's proposal, tested)

Made a real 16-bar ballad first — 4 GM tracks, 160 notes, D minor, 76 BPM. It renders and
it sounds: **−24.4 LUFS integrated, −9.4 dBTP, LRA 7.0 LU, 52.5 s** (= 64 beats at 76 BPM
+ 2 s tail, so the window is right).

Then rendered a spectrogram of it with `ffmpeg -lavfi showspectrumpic` and READ it.

### What the picture genuinely gave me — real, and not available from numbers

- **Arrangement structure at a glance.** The intro (0–12.6 s) is visibly sparser; sax and
  brushes enter exactly at 12.6 s = beat 16 = bar 5, which is what I wrote. Verifying
  "does the arrangement match the plan" took one look instead of a query per track.
- **Bar lines** show as vertical striations every ~3.16 s — 4 beats at 76 BPM. Tempo is
  legible off the image.
- **The sax's harmonic ladder** is unmistakable, ~880 Hz to ~5.8 kHz, only after 12.6 s.
- ⭐ **A dropped clip — the sax team's defect ③ — would be a BLANK RECTANGLE.** That is the
  strongest argument for this tool: the defect that survived 6645 green tests is trivially
  visible here.

### ⛔ And then it lied to me, on the very first read

The band below ~60 Hz renders bright yellow across the whole piece. I concluded the mix
was bass-heavy. **It is not.** Measured:

| | |
|---|---|
| full-band RMS (control) | −27.6 dB |
| below 60 Hz | **−39.6 dB — 12 dB UNDER full band** |
| below 20 Hz (negative control) | −57.3 dB — negligible |
| DC offset | 0.000039 — zero |

**Cause: it is a rendering artifact, not signal.** `fscale=log` gives 20–130 Hz about a
third of the image height, and my own `gain=3` brightened it further. The eye reads AREA;
the ear and the meter read ENERGY.

⭐⭐⭐ **THIS IS THE FINDING.** A spectrogram is *persuasive*, and my first use of it
produced a confident, specific, WRONG conclusion — this project's signature failure mode
in a new costume. I caught it only because I measured instead of trusting the picture.

### Recommended design, earned rather than assumed

1. **Numbers stay the gate. The image is never an assertion.** Nothing may pass or fail on
   a spectrogram.
2. **Emit it as an ARTIFACT ATTACHED TO A FAILURE** — when a numeric gate trips, the image
   says *what kind* of wrong, which is where it pays.
3. **Pin the render parameters and print them ON the image.** A spectrogram without its
   `fscale`/`gain` is uninterpretable, and two runs at different settings are not
   comparable. This is the trap above, made structural.
4. **Prefer a DIFFERENCE image for A/B work** (e.g. the −3.07 dB warm-vs-warm null): a
   difference has no log-scale area bias, because both sides carry it equally.
5. Use it freely for exploration and dogfooding, where a hypothesis that turns out wrong
   costs one measurement.

**Verdict: worth building, and worth building carefully.** The value is real (defect ③ is
a blank rectangle) and so is the hazard. It belongs in the diagnostic lane, never the gate
lane.

## Today's shipped work, verified END TO END in the running app

`06dca3d`'s `voiceMode` / `bendRangeSemitones` had never been exercised outside the test
suite. Built a sampler from a rendered GM sax A4 (source verified at **440.00 Hz**, with
220 Hz four orders of magnitude down as a negative control), then measured a real render:

| test | measured | expected | error |
|---|---|---|---|
| unbent A4 (baseline) | 440.00 Hz | 440.00 | **+0.0 ¢** |
| D5 after MONO takeover | 587.25 Hz | 587.33 | **−0.2 ¢** |
| A4, full bend at range **6** | 622.25 Hz | 622.25 | **+0.0 ¢** |

**The control that matters:** during the D5, the superseded A4 measures `0.000021` against
the new note's `0.013533` — **645× down**. The old voice is GONE, not masked. That is
precisely the distinction F1's stale documentation got wrong, now measured.

At the old hard-wired ±2 the last row would read ~493.9 Hz. The setting is real.

### F5 🧱 — the sampler cannot be smoke-tested without external sample content

A fresh project ships no sample audio, so `voiceMode`/`bendRangeSemitones` — the features
built FOR the sax team — cannot be exercised at all until someone supplies a file. I had
to render a GM note to a wav and mount that as a zone just to hear the thing we shipped.

That is a five-step detour for what should be a smoke test, and it means the most likely
first experience of a new sampler feature is silence. **A single bundled one-shot with a
known root pitch would make the sampler self-testable** — and would have let the sax team
reproduce our results without shipping us their 46-zone library.

### F6 😖 — `clip_add_midi` echoes every note back, ids and all

The Rhodes clip (64 notes) returned ~6 KB; the brushes clip (46 notes) similar. Writing a
song is dozens of these calls and the echo is pure cost — the ids are only useful if you
intend to edit individual notes, which composition rarely does immediately.

`project_snapshot`'s overflow risk is documented in `daw-wire-reference`; **this one is
not, and it is on the hot path of every composing session.** A `4096`-note clip (the
documented maximum) would return an enormous payload on a call whose useful result is one
clip id. Worth an opt-out (`returnNotes: false`) or summarising past a threshold.

## ⛔⛔ F7 🐛 — A REAL REGRESSION IN `06dca3d`, SHIPPED THIS MORNING, FOUND BY RUNNING THE PRODUCT

The single most valuable result of this session, and it was found by finishing the loop —
regenerating the plugin bundle and running the MCP suite — not by making music.

**MCP suite: 466 pass, 1 fail.**
`instrument_set_sampler_param rejects a non-number/non-boolean value at the schema layer`

**Mechanism.** The bend-range leg had to widen that tool's `value` from
`z.union([z.number(), z.boolean()])` to `z.union([z.number(), z.boolean(), z.string()])`,
because `voiceMode` takes `"poly"`/`"mono"`. Necessary — and it silently re-admitted a
string for EVERY OTHER param. `{param: "gain", value: "loud"}` began passing MCP schema
validation and reaching the app, where it had previously been refused at the boundary with
a clean error. **The test asserts both `isError` AND `calls.length === 0`; the second is
the one that matters — nonsense now reaches the bridge.**

⭐ **This is precisely the silent-success class we spent all of 2026-08-23 eliminating,
re-introduced by the fix for a different defect, in the same commit.**

**Why it shipped.** I ran the full Swift suite after the bend-range leg (6656/623, green)
and did NOT re-run the MCP suite. Agent 1's `467/467` predated the bend-range changes by
hours. **Two verification surfaces, and I re-ran only one after the last change.** The
Swift suite cannot see this: the defect lives entirely in a TypeScript zod schema.

**Fix** (`mcp-server/src/server.ts`): re-narrow in the handler, BEFORE `bridge.send`, since
the `inputSchema` here is shape-based and cannot express a cross-field rule. Deliberately
minimal — restores exactly the lost guarantee and tightens nothing else (a boolean for a
numeric param was accepted before and still is), because the wire contract is
additive-only. **467 pass / 0 fail.** The gate ran its plant/revert cycle in the natural
direction: red with the defect present, green after the fix.

### ⭐⭐⭐ M2 🔍 META — THE LAW THIS BUYS

**A change that widens a schema to admit a NEW valid case silently widens it for every
EXISTING case too.** A union is not a per-variant contract. When a param becomes
polymorphic, the narrowing that used to be free must be re-established by hand.

**And the process law, which is the more important one:**
⚠️ **THIS TREE HAS TWO INDEPENDENT TEST SURFACES — Swift (`./scripts/test.sh`) AND MCP
(`cd mcp-server && npm test`). RE-RUN BOTH AFTER THE LAST CHANGE THAT TOUCHES EITHER.**
A green Swift run says nothing about a zod schema, and an agent's earlier MCP figure is
stale the moment a later leg edits `server.ts`. I quoted `467/467` in a commit message for
a tree where it was no longer true.
