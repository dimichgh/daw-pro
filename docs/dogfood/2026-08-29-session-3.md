### F1 📄 `clip_analyze_audio`: the doc's tonality test does not match the response

**Trying to:** follow §1's instruction *"Check `key.tonal` first: when it is
`false` the tonic/mode fields are absent"*, so I can decide what key to write in.

**Expected:** a percussive break reads `tonal: false` with no `tonic`/`mode`.

**Got** (`clip.analyzeAudio {"clipId":"1A814419-…"}`):

```json
"key": { "tonal": false, "mode": "major", "confidence": 0.1939…, "tonic": "D",
         "alternatives": [ {"tonic":"F#","mode":"minor","score":0.471…}, … ] }
```

`tonal` is `false` **and `tonic`/`mode` are both present anyway.** The shape
block above it hedges (`tonic?`, `mode?`) but the prose asserts absence outright.

**Why it matters:** the doc trains you to test tonality by *reading the field*.
An agent that tested `if "tonic" in key` — the natural reading of "the fields are
absent" — gets `"D" / major` on a drum break at 0.19 confidence and transposes a
whole arrangement into a key that was never measured. This is the tree's
documented characteristic failure mode: a value that looks like a valid answer.

**What I did next:** trusted the `tonal: false` boolean, ignored tonic/mode,
treated the break as atonal. Correct per the doc's *intent*, not its wording.

**Suggested fix:** change the prose to "when it is `false`, `tonic`/`mode` may
still be populated from the best-scoring (weak) candidate — they are NOT a
tonality test. Branch on `tonal` itself."

### F2 🐛 `minSliceSeconds` merging keeps the FIRST onset, not the STRONGEST — and it silently ate the loudest snare in the break

**Trying to:** get ~16 one-hit-per-pad chops out of a 43-onset break, using the
knob §3a names for exactly this: *"`minSliceSeconds` … ⭐ **This — not
`sensitivity`** — is the pad-count knob. Onsets closer together than this are
merged, so raising it is how you get fewer, longer pads out of busy material."*

**Expected:** merging a cluster of onsets keeps a musically sensible
representative — the loud one — so every pad starts on a hit.

**What happened:** the merge is evidently greedy from the last kept onset, and
**strength is not consulted at all.** Three of 15 pads start on ghost notes, and
one of the two loudest hits in the entire break lost its boundary:

| onset `sourceSeconds` | `strength` | became a pad? |
|---|---|---|
| 0.6661 | **0.998** | ✅ pad 1 |
| 2.0000 | 0.832 | ✅ pad 5 |
| 3.2333 | 0.089 (ghost) | ✅ pad 9 |
| **3.3335** | **0.992** | ❌ **merged away** |
| 4.6672 | **1.000** | ✅ pad 13 |
| 1.2604 | 0.016 (ghost) | ✅ pad 3 |
| 2.9271 | 0.017 (ghost) | ✅ pad 8 |

Pad 9 spans frames 142588–161664 (3.2333–3.6659 s). The 0.992-strength backbeat
snare at 3.3335 s sits **100 ms inside it**. Hit that pad and you get a tick of
hat, then the snare. Nothing in the response says so: `warnings: []`,
`sliceCount: 15`, every field looks healthy. Classic looks-like-a-valid-answer.

**How I caught it:** only because I diffed `slices[].sourceSeconds` against the
`clip.detectTransients` list I'd taken first. §2 recommends running the detector
first for the `count`; **it is worth far more than that** — it is the only way to
see which onsets the chop threw away.

**What I did next:** `edit.undo` and re-chopped in `mode: "grid"` (below), which
sidesteps the merge entirely.

**Suggested fixes (either would do):**
1. Make the merge keep the highest-`strength` onset in each merged cluster, not
   the first. That is what a human doing this by hand does.
2. Failing that, **document it** in §3a's `minSliceSeconds` row — one sentence,
   "the earliest onset in a merged cluster wins regardless of strength; check
   `slices[].sourceSeconds` against the detector list if a loud hit matters" —
   and ideally return the discarded onsets in the response so the check is
   possible without a second call.

### W4 ✅ WENT WELL — `audio_profile_file`'s missing-field-means-silence rule caught a silent pad

§"What is NOT here" buries a gotcha that turned out to be the most useful
sentence in the run: *"`audio_profile_file` omits `rmsDb`/`peakDb` entirely for
a digitally silent window … Treat a missing field as silence, never a zero."*

```
audio.profileFile {"path":"…/break-90bpm.wav","windowSeconds":0.3333333}
```
18 windows. Windows 0–15 carry `rmsDb`/`peakDb`. **Windows 16 and 17 carry
neither** — i.e. the last 0.35 s of the file is digital silence.

That matters because my grid chop (below) made **pad 52 out of exactly that
silence**, and reported it as a perfectly healthy pad:
`{"index":16,"pitch":52,"sourceSeconds":5.3333,"residualAmplitude":0}`,
`warnings: []`. `residualAmplitude: 0` on a silent span is indistinguishable
from a flawless zero-crossing cut — the *best* possible reading is produced by
the *worst* possible pad. I only knew because I'd profiled the file first.

**F3b 🐛 (same observation, product side):** `clip_slice_to_sampler` will mint a
pad over pure digital silence without a warning. A `residualAmplitude` of 0 plus
a zero peak inside the span is trivially detectable. Suggest a warning
("slice 16 contains no signal") or a per-slice `peakDb`. I dropped pad 52 from
the arrangement by hand.

### W5 ✅ + 🔍 meta — `mode: "grid"` was the right escape hatch, and TWO INSTRUMENTS DISAGREEING was the signal

After `edit.undo` (`{"undone":"Chop to Sampler"}` — one step, exactly as §3b
promises for the timeline chop and as §3a implies for this one):

```
clip.sliceToSampler {"clipId":"1A814419-…","mode":"grid","gridBeats":0.5,"includeHead":true}
-> sliceCount 17, notes 36–52, createdTrackId 5985FFF8-…, midiClipId 2F445439-…,
   sampleRate 44100, frameCount 250634, warnings []
```

Every pad boundary landed within ~0.6 ms of its onset, and the merge problem in
F2 simply cannot occur because no detector runs. §3's "Which one?" table doesn't
cover this case — it offers `divisions: N` for *"a drone or an ambient bed that
has no transients"* — but the real use for a grid chop is the opposite: material
that is **already exactly on the grid**, where the detector's *clustering* is the
liability, not its accuracy. Worth adding a row.

🔍 **The meta-finding:** `slices[].strength` and actual level DISAGREE, hard, and
believing either one alone would have produced a wrong arrangement.

| pad | `strength` (detector) | `rmsDb` (profiled) | `peakDb` | my read |
|---|---|---|---|---|
| 36 | 0.132 | **−14.09** | −1.84 | kick — *strength says it's nothing* |
| 38 | **0.998** | −23.13 | −2.79 | snare |
| 37 | 0.347 | −35.21 | −11.84 | hat |

Onset strength is a spectral-flux number: it rewards the broadband snare and
almost ignores a low kick. **Anyone using `strength` as a loudness or importance
proxy will build a beat around the wrong hits.** §3a explains why the
reconstruction uses velocity 127 rather than strength (good), but never says
*strength is not level*. It should.

**Final pad map** (RMS clusters at three values — this is a programmed break, so
the classification is tight, not a guess):
- **KICK** (rms ≈ −14.1): 36, 39, 41, 44, 45, 49
- **SNARE** (rms ≈ −23.1 / −20.9): 38, 42, 46, 50
- **HAT** (rms ≈ −35 … −36, and 51 at −30.2): 37, 40, 43, 47, 48, 51
- **SILENT**: 52 → dropped

### F5 🧱 §8 tells you to rewrite the reconstruction clip. Following it exactly produces a beat that is 87 % silent, with no warning anywhere.

**Trying to:** do literally what recipe step 8 says — *"Rewrite the MIDI clip
(`clip_get_notes` → reorder/drop/repeat → `clip_set_notes`) into a pattern the
record never played."* My new pattern is 16 bars: 152 notes spanning beats 0–63.6.

The reconstruction clip `clip_slice_to_sampler` created is **8.524966 beats long**
— the source clip's length. Writing 63.6 beats of notes into it:

```
clip.setNotes {"clipId":"2F445439-…","notes":[152 notes]}
-> {"lengthBeats": 8.524965986394557, "name":"break-90bpm chops", … }   ← unchanged
```

**All 152 notes were accepted. No warning. No error. The clip did not grow.**

Measured, with a positive control so the negative means something:

| window | result |
|---|---|
| `render.measureLoudness {fromBeat:16, durationSeconds:5}` | `"measurement": {}` — **nothing** |
| `render.measureLoudness {fromBeat:0,  durationSeconds:5}` | `integratedLufs −18.243`, `truePeakDbtp −1.925` |

So beats 0–8.5 sound and beats 8.5–63.6 are silent: **131 of my 152 notes were
inaudible while every call reported success.** Had I bounced at this point I'd
have shipped 40 seconds of near-silence and the loudness gate would have passed,
because the first two bars are fine.

**The fix, which the sample-flip skill never mentions:** `clip.fitToContent`.
```
clip.fitToContent {"clipId":"2F445439-…"}
-> "missing or invalid required param 'trackId'"
clip.fitToContent {"trackId":"5985FFF8-…","clipId":"2F445439-…"}
-> {"changed": true, "lengthBeats": 63.6, …}
```
Re-measured beats 16–24: `integratedLufs −18.074`. Fixed.

I only knew the tool existed because `daw-wire-reference` names it — **in a
completely unrelated paragraph about `clip_import_midi`**, whose problem is the
opposite one (wholesale replacement). Nothing connects it to §8.

**Why this is a wall and not friction:** step 8 is the creative heart of the
skill — it is *the* instruction that turns a chop into a flip — and following it
as written silently discards most of your music. Every other trap in this
document is called out with a ⚠️. This one has nothing.

**Suggested fix — one line in §8, and one in §3a:**
> ⚠️ The reconstruction clip is exactly as long as the source clip. `clip_set_notes`
> accepts notes past the clip end and they are SILENT — grow the clip with
> `clip_fit_to_content {trackId, clipId}` after any rewrite that extends it, and
> re-measure a late window to confirm.

### F8 🐛 `clip_add_audio` SILENTLY DELETES any clip it overlaps — proven with a positive control

Noticed while doing §8's resample loop: after importing a second bounce onto the
Resample track at `atBeat: 0`, the first bounce's clip was gone.
Rather than guess, I ran a controlled probe on a throwaway track:

```
track.add {"name":"ZZ Overlap Probe","kind":"audio"}
clip.addAudio {trackId, path: break-90bpm.wav, atBeat: 0}   -> rc 0, id 6B0AC5B4…
clip.addAudio {trackId, path: break-90bpm.wav, atBeat: 0}   -> rc 0, id A47A65A6…
project.overview -> clips on that track: 1   [A47A65A6, start 0]
                    6B0AC5B4 present? False
POSITIVE CONTROL:
clip.addAudio {trackId, path: break-90bpm.wav, atBeat: 40}  -> rc 0
project.overview -> clips on that track: 2   [A47A65A6@0, 81E09FCF@40]
track.remove {trackId}   (probe cleaned up)
```

So the track happily holds two clips; **overlap is what destroys.** Both
destructive adds returned `rc 0` and a complete, healthy-looking clip object.
**No warning, no `replaced` field, nothing.**

**Why this specifically hurts the sample-flip workflow:** §8 is *the resample
loop* — bounce, import, chop, bounce again, import again. The natural thing to
do is import each pass onto the same "Resample" track at `atBeat: 0`, and each
import eats the previous print with no indication. It also contradicts the
wire reference's etiquette rule #2, *"Prefer additive edits. Add, don't
replace"*, which reads as a description of what these tools do.

**Suggested fix:** refuse the overlap (`"a clip already occupies beats 0–9.09 on
this track; move it, remove it, or pass a different atBeat"`), or at minimum
return the displaced clip's id in a `warnings` entry. Either would be caught by
the same error-message quality that F2/F4/W2 show this surface is capable of.

### F10 🐛/😖 the `eq` low-pass cannot go below 1000 Hz — which is most of what a low-pass is for

The source break is bottom-heavy and my GM sub was smearing low-mid, so I went to
low-pass the sub around 220 Hz — the single most common move in a modern mix.

```
fx.add {"trackId":"BD253A3D-…","kind":"eq","params":{"lowPassEnabled":1,"lowPassFreq":220,…}}
-> warnings: ["lowPassFreq was clamped to its minimum 1000 — you asked for 220,
              and this control accepts 1000 to 20000."]
```

**✅ The warning itself is exemplary** and is exactly what the wire reference's
"A clamped value now says so" section promises: what I asked for, what was
stored, the range. I knew instantly. That part is a win.

**The range is the problem.** `lowPassFreq` bottoms out at 1 kHz and
`highPassFreq` tops out around 2 kHz (`lowShelfFreq` 20–2000). You cannot build
a sub-only bass, a telephone band-pass, a DJ filter sweep, or a lo-fi tape
low-pass — all bread-and-butter, and the last one is squarely in this skill's
own genre. I worked around it with two peak cuts (−8 dB at 350 Hz Q 0.8, −8 dB
at 800 Hz Q 0.8) plus the 1 kHz low-pass, which got the job done but is three
controls doing one control's work.

### F11 🔍 the tempo analyzer returns `confidence: 1` for a tempo the project is not at

`clip.analyzeAudio` on my own 96 BPM bounce:

```json
"tempo": { "bpm": 127.974, "confidence": 1, "steady": false,
           "alternates": [ {"bpm": 48.010, "score": 0.646},
                           {"bpm": 63.987, "score": 0.434},
                           {"bpm": 96.020, "score": 0.646} ] }
```

The project is at exactly 96 BPM and the material is machine-quantised MIDI.
**96.02 is in `alternates` at score 0.646, while 127.97 is the headline answer at
confidence 1.0.**

In fairness to the analyzer, 128 = 96 × 4/3 and my groove is full of dotted-eighth
(0.75-beat) kick placements, so it found a real pulse — I am not calling the
number wrong. What I am calling wrong is **`confidence: 1` on it**, and
`steady: false` on material that is sample-exact. §1 tells you to reconcile
`tempo.bpm` against the project tempo and gives careful advice about the field
being *absent*; it gives none about it being *confidently present and 4/3 off*.
An agent that resampled its own bounce and obeyed `tempo.bpm` would retempo the
project to 128 on a maximum-confidence reading.

**Suggested doc fix for §1:** add a sibling to the existing ⭐ bullet — "a
present `tempo.bpm` with high confidence can still be a metrically related
multiple (×2, ×½, ×4⁄3). Check `alternates` for the project's own tempo before
retempoing anything."

### F12 📄 `returnNotes: false` is documented as a `clip_add_midi` parameter but does not exist on the wire

```
clip.addMIDI {…,"returnNotes":false}
-> "clip.addMIDI: unknown parameter 'returnNotes' — valid keys are
    'atBeat', 'lengthBeats', 'name', 'notes', 'trackId'"
```

The wire reference devotes a whole section to it ("**Pass `returnNotes: false`**
unless you are about to edit individual notes right now"). It is an MCP-layer
parameter only. The reference does flag MCP-vs-wire differences for whole *tools*
(`instrument_set_sampler_zones`), and sample-flip §7 does too — but neither says
any *parameter* can be MCP-only. Low severity (plugin agents go through MCP), but
sample-flip §7 explicitly addresses raw-wire drivers, so it is in scope.

## The music that came out

**"Round 2" — 16 bars, 96 BPM** (the record is 90; the chops are one-shots so
they keep their recorded pitch and speed while fighting a grid 6 BPM faster —
§3's "let the pads land where they land" option, chosen deliberately).

**Chop:** `mode: "grid"`, `gridBeats: 0.5`, `includeHead: true` — 17 pads on
MIDI 36–52, one per eighth note of the 2-bar break, plus a tail pad I dropped
because it is digitally silent (W4). Pad roles classified by profiled RMS, not
by ear and not by detector strength (see the meta-finding in W5).

**What makes it not the original loop:**
- New order. Pad 44 is the main kick, 38/46/50 rotate as snares, 43/47/51 as
  hats. Nothing plays in its recorded sequence; six of the seventeen pads are
  never used at all.
- **Section dynamics, measured on the finished file** (2 s RMS windows):
  intro/verse sit at −13 to −14 dB, the bar-9–10 breakdown (kick dropped
  entirely) reads **−17.2 and −19.4 dB**, and the bar-15 16th-note snare roll
  climbs on velocity 70→119 into the loudest passage at −11.8 dB.
- **Repitch, not time-stretch** (§4). A second sampler track holds two
  hand-authored zones built from frame numbers the chop returned: a hat pad with
  `rootPitch 60` played at 65/67/70 (+5/+7/+10 semitones — reads faster and
  brighter), and a snare pad with `reverse: true`, `rootPitch 84`, played at 72
  so it reads at half rate: a 0.334 s snare becomes a **0.667 s backwards
  riser**, placed 1.07 beats before bars 3, 9, 11 and 15.
- **Choke** (§5): the six hat zones share `chokeGroup: 1` so hats cut each other
  while kicks and snares stay polyphonic. Two snares detuned (`tuneCents` +150
  and −100) so the four snare pads are four different snares.
- **Crush** (§6): `bitCrusher` at stock SP-1200 defaults on the chop bus.
- **A sub that is not a pitched-down kick** — see below.
- Master: `gain` (×1.7) → `limiter` (−1 dB ceiling, `truePeak` on).

### The "deep and dull" note from round 1 — measured, failed, then fixed

The instruction was: if you build a sub line, keep something bright on top. I
deliberately pitched **nothing** down (an octave-down kick reads at half rate and
takes its attack with it), and used a GM Synth Bass for weight instead.

**Then I measured it, and I had done it anyway:**

| `spectral` | source break | flip, pass 1 | flip, pass 2 (shipped) |
|---|---|---|---|
| **centroidHz** | 1083.9 | **534.9** ❌ | **1169.1** ✅ |
| rmsDb | −18.24 | −14.22 | −14.68 |
| sub / bass | −27.2 / −39.4 | −22.2 / −34.9 | −22.8 / −35.7 |
| lowMid / mid | −64.3 / −69.7 | −48.0 / −57.6 | −56.2 / −60.8 |
| highMid / **air** | −65.0 / **−63.4** | −58.6 / −60.2 | −58.0 / **−57.9** |

Pass 1's centroid was **half the source's** — the GM bass's harmonics had piled
12 dB of low-mid into the mix and the bright layer, 10 dB down, was doing
nothing. Fix: EQ the sub down to near-fundamental, high-pass the bright layer at
400 Hz, +6 dB shelf at 6 kHz, and raise it 5 dB. Pass 2 is **brighter than the
source it was cut from (1169 vs 1084 Hz) while carrying ~1 dB more relative
sub** — weight and air, which was the brief.

🔍 **The meta-finding this run turns on:** I made the correct *decision* (no
octave-down kick), executed it faithfully, and still produced the exact defect
the user had complained about — through a completely different mechanism I had
not thought of. **The reasoning was not the safeguard. The measurement was.**
Nothing in the skill would have caught this: §"What is NOT here" lists
`spectral.centroidHz` under "your ears", but no step in the recipe tells you to
measure the flip's centroid against the source's. Recipe step 11 checks loudness
and hit count only, and pass 1 passed both.

**Suggested addition to recipe step 11:** *"Import the final bounce and
`clip_analyze_audio` it, then compare `spectral.centroidHz` and the band summary
against the SOURCE's from step 1. A flip that is much darker than its source has
usually gained mud, not weight — and you cannot hear it."*

## Verdict: was the skill sufficient on its own?

**Nearly. It got me from a raw WAV to a finished, measured, arranged flip
without ever reading product source — which is the bar. Two places it did not.**

**Where it was decisive** (I would have failed or wasted loops without it):
`headSeconds`' warning threshold (W3) — the single most valuable paragraph, it
predicted my exact number; the `audio_profile_file` missing-field-means-silence
rule (W4), which caught a silent pad; the `maxSlices` refusal being a teaching
error (W2); §7's raw-wire `zonePatches` route (W8); §6's bitCrusher defaults
(W9); §1's absent-`tempo.bpm` bullet (W1); §9's units table throughout.

**Where I needed something it did not give:**
1. **F5 — the clip-length wall.** §8's core instruction, followed exactly,
   silently produced a beat that was 87 % inaudible. `clip_fit_to_content` is
   the fix and this document never names it.
2. **F2 / W5 — chop-quality verification.** Nothing tells you the merge keeps
   the earliest onset rather than the loudest, or that `strength` is not level.
   I found both only by diffing the chop against a detector run I happened to
   have taken.
3. **The brightness gate above.** The skill's own numeric "ears" include
   `centroidHz`, but no step tells you to use it on the result, and the run's
   worst musical failure passed every gate the skill does prescribe.
4. **The zone schema.** §7 shows `{id, reverse, chokeGroup, tuneCents}` in one
   example; building a sampler track from scratch needs `path`, `rootPitch`,
   `minPitch`, `maxPitch`, `startFrame`, `endFrame`, `gain`, `attack`,
   `release`. I got it by reading `instrument_describe_sampler`'s output shape
   (W6). That worked, but it was luck that I had a populated track to read.
5. **The mute-before-you-bounce step.** Recipe step 4 mutes the fake record in
   the self-contained recipe, but the numbered sections (§1–§9), which the doc
   says are "the actual recipe", never say it. Bouncing with the source still
   audible would produce "the original loop replayed" and pass every gate.

**Standing structural observation:** every one of F2, F3b, F5, F6, F8, F11 is
the same shape — *a call that returns something that looks like a valid answer.*
A merge that ate the loudest snare, a pad made of silence with a perfect
residual, 131 inaudible notes, `measurement: {}`, a deleted clip reported as a
successful add, `confidence: 1` on a 4/3-off tempo. **On this surface, the
refusals are outstanding and the successes are what you have to distrust.**
