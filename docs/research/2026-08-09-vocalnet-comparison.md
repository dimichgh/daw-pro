# VocalNet feature comparison — m23-di-3

Date: 2026-08-09 (research performed 2026-08-09/10)
Author: research-analyst (agent)
Scope: compare DAW Pro's shipped voice-conversion capability against `sessionloops.com/vocalnet` and its sibling free product `sessionloops.com/vocalnet-community`, to establish whether third-party model **import** (m23-di-2) is the only real gap. Explicitly **not** an inference-backend evaluation — `Acelogic/Retrieval-based-Voice-Conversion-MLX` (what `scripts/rvc/` already runs) is out of scope; no code was touched, no sidecar was started, no port was bound.

## Headline

**No — import is not the only gap.** Real-time/live voice conversion and multi-voice blending are both plainly documented, currently-shipping VocalNet capabilities with nothing equivalent in DAW Pro, and both represent a larger engineering lift than import. Import (m23-di-2) is real and confirmed — but it is the *cheapest* of the three, not the only one. Full ranking is in §3; concrete roadmap proposals are in §6.

## 0. What could and could not be verified, and how

VocalNet is a commercial plugin distributed as a paid download behind a 14-day trial/signup. **No hands-on testing was performed** — nothing here reflects running the plugin. Every claim below is sourced from one of three tiers, marked per row in §2:

- **Vendor** — sessionloops.com's own product pages (`/vocalnet`, `/vocalnet-community`), fetched directly.
- **Third-party coverage** — KVR Audio's product/news pages, Bedroom Producers Blog, rekkerd.org — plugin-news sites that generally reprint or lightly rephrase vendor press releases; treated as corroborating a vendor claim, not as independent testing.
- **One user report** — a single identified forum post (Gearspace) from someone who apparently installed and tried the plugin. This is **n=1**, stated as such everywhere it's used, never generalized to "users complain."

Two `WebSearch` calls returned AI-generated summary prose asserting "VocalNet is built on RVC" and "quality degrades on polyphonic input / heavily processed source." Per the honesty constraint on this item, **these are excluded from the matrix** — they were not traceable to a specific page I fetched, and a search engine's synthesized summary is not a primary source. (The RVC claim was later independently confirmed from a fetched vendor page for the *Community* tier specifically — see §1 — but that confirmation covers only that one product, not the flagship.)

## 3. Gap list, ranked by user value, with reasoning

1. **Real-time/live streaming conversion (monitoring + live performance)** — highest value, **structural**. This is the single feature the vendor rebuilt the product around in its Oct-2025 relaunch (their own "Reimagined" framing) and it's the literal request in the user's original ask ("build a plugin similar to VocalNet"). It requires a new low-latency contract end to end: sidecar streaming support, a client-side path that isn't the current blocking-call shape (`VoiceConvertSheet.swift`'s own comment already documents the batch design: "Conversion is BLOCKING seconds-class... not job-polling machinery"), and RT-safety-aware engineering to keep inference off the actual render thread while still hitting a monitoring-usable latency. Size this as its own architecture spike before scoping a build.
2. **Voice blending/morphing across multiple voices** — medium-high value (real creative differentiator for VocalNet, per its own marketing and third-party coverage), moderately structural. Cheaper than #1 in principle (offline-first blending, e.g. interpolate then run one conversion, would sidestep the real-time requirement entirely) but **feasibility against `rvc_mlx`'s actual model surface is unverified** — needs a spike, not a size estimate, before ranking it against #1 with confidence.
3. **Third-party/community RVC model import** — confirmed real gap, matched specifically by VocalNet's free Community tier (not the flagship's headline features). **Cheapest of the three**: the backend already scans for and surfaces exactly this case (`server.py`'s directory scan + the shipped "NEEDS PREP" chip), and the vendored fork ships the `.pth`→`.npz` converter tool already. This is m23-di-2's existing scope, now confirmed against real competitor evidence rather than an internal assumption — proceed with it as filed.
4. **Retrieval-strength / character control exposure** — low value, cheap to build, but **blocked in practice**: touching `scripts/rvc/server.py` needs the user's explicit go-ahead, since that whole directory is on the standing do-not-touch list for this and sibling items. Flag as "needs a decision," not "just do it."
5. **Quick few-shot (5-10 s) cloning as a fast-preview mode** — low value. The one verified user report on exactly this feature describes it as full of artifacts with almost no character transfer. Recommend explicitly **not** copying this path; if a "preview" mode is ever wanted, build it once m10-p-6's full training ships, framed as a fast/low-fidelity preview of the same target voice being trained properly — not a replacement workflow.
6. **ARA integration** — not actionable as a gap in the competitive sense. The user-facing outcome (edit vocals inline, in-timeline, without a manual bounce/reimport step) is already shipped via the clip context-menu convert action. The ARA *protocol* is separately tracked (m23-dh) and deliberately deep-backlogged for reasons unrelated to this comparison (m23-av). Do not re-open it from here.
7. **Artist Mode marketplace** — not actionable. Out of scope by the user's own local-personal-use ruling, not by capability gap.

## 4. What I could not verify, stated plainly

- Whether the **flagship** ($99) VocalNet, as opposed to the free Community tier, supports loading external/third-party models at all — its own product pages describe only the in-plugin 5-10 s sample-cloning workflow. I could not find a page confirming or ruling this out for the flagship specifically.
- The exact underlying model architecture/training method behind the flagship's "voice cloning" black box (few-shot embedding-based cloning vs. some other few-shot approach) — vendor material describes behavior, not implementation.
- Real-world latency, CPU load, or conversion quality of either VocalNet product — no hands-on testing was performed (trial requires signup/download, which was not done for this item).
- Broader user sentiment beyond the single Gearspace report — that thread had mostly speculative/non-substantive replies; I did not find a second independent hands-on account to corroborate or contradict it.
- Two claims that appeared only in AI-generated `WebSearch` summary prose (source not traceable to a specific fetched page) were excluded per the honesty constraint: "quality degrades on polyphonic/heavily processed input" and vague "reliability/company transparency" concerns. Do not treat their absence from this report as evidence either way.

## 6. Actionable takeaways

Concrete, filable proposals for the caller — this item does not itself change the roadmap.

- **m23-di-2 (third-party model import): proceed as already filed, scope unchanged.** This report converts its premise from an internal inference ("the seam is already on screen") to competitor-confirmed evidence (VocalNet Community explicitly ships exactly this, naming the RVC WebUI as its model source). No rescoping needed.
- **File two new roadmap items, both gated on a spike before sizing — do not size them from this report alone:**
  - *Real-time/streaming voice conversion.* Route: `daw-architect` first, for an architecture spike (new sidecar streaming contract + a latency-budgeted path that respects the render-thread RT-safety rules — this is not a parameter added to the existing `POST /v1/voice/convert`). Weight L/XL pending the spike. This is the single largest gap found and the one closest to the user's original literal request.
  - *Multi-voice blending/morphing.* Route: `audio-dsp-engineer` or `daw-architect` for a feasibility spike against `rvc_mlx`'s embedding/decoder surface before any sizing — whether interpolating between two loaded voice models is even representable in the current engine is unverified.
- **m23-di umbrella:** this document discharges di-3 (③, the VocalNet comparison). The umbrella can close once di-2 lands; di-3 itself is done with this report.
- **Explicitly do not file, and why:**
  - Artist Mode marketplace — out of scope by the 2026-08-04 local-personal-use ruling, not a capability gap.
  - ARA support — already tracked as m23-dh, deliberately deep-backlogged pending m23-av; this report's finding (native clip-menu convert already delivers the practical outcome) is a data point for that item, not a reason to reopen it separately.
  - Fast few-shot (5-10 s) voice cloning — recommend against building this path at all, on the strength of the one verified user complaint about exactly this feature's output quality.
- **`docs/ARCHITECTURE.md`:** worth a one-line addition noting that the RVC facade's `POST /v1/voice/convert` contract is whole-file/blocking by design (not a placeholder omission) — it is now the documented reason the real-time gap is structural rather than incremental, and a future cycle reading the architecture doc cold should see that constraint stated rather than rediscover it from `server.py`.
