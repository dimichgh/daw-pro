## 0. The single highest-value question: mid-stream transpose in signalsmith-stretch

**Question:** does `signalsmith-stretch` support changing the transpose factor mid-stream cleanly (interpolated/smoothed), or does changing it between `process()` calls zipper/click? A "no" forces a segment-and-splice architecture instead of one continuous stream with a time-varying pitch curve.

### What I verified directly from the vendored source

File: `Sources/CSignalsmithStretch/vendor/signalsmith-stretch/signalsmith-stretch.h` (all line numbers from this file as vendored in this repo).

- `setTransposeFactor`/`setTransposeSemitones` (`:107-118`) do nothing but assign three plain member variables (`freqMultiplier`, `freqTonalityLimit`, `customFreqMap = nullptr`). There is no lock, no ramp state, no "pending change" queue — the call is synchronous and takes effect for whatever processing happens next. **This means the C API and our shim (`css_set_transpose_semitones`, `Sources/CSignalsmithStretch/include/csignalsmith_stretch.h:40-41`) can legally be called between `css_process` calls; nothing in the type prevents it.**
- The transpose value is consumed once per **internal analysis block/hop**, not once per output sample. In `process()` (`:209-423`), a new hop begins when `blockProcess.samplesSinceLast >= stft.defaultInterval()` (`:281`); at that hop boundary `blockProcess.mappedFrequencies = customFreqMap || freqMultiplier != 1` is evaluated fresh (`:300`), and if frequencies are mapped, `findPeaks()`/`updateOutputMap()` (`:667-670`, `:882-917`) recompute the input-bin-to-output-bin mapping using `mapFreq()` (`:850-856`), which reads the current `freqMultiplier` directly. So: **a value changed via `setTransposeSemitones` takes effect at the next hop boundary**, not instantly and not mid-hop.
- Hop size (`stft.defaultInterval()`) is set by whichever preset/`configure()` call is used. **Confirmed by direct read of `Sources/CSignalsmithStretch/shim.cpp:25-30`: `css_create` calls `s->stretch.presetDefault(channels, sampleRate)`** — the library's *default* preset, not `presetCheaper`. `presetDefault` (`signalsmith-stretch.h:63-65`) configures `blockSamples = sampleRate*0.12` (~120 ms) and `intervalSamples = sampleRate*0.03` (~30 ms). **So in this app specifically, a changed transpose value takes effect at the next ~30 ms hop boundary** (at 44.1/48 kHz), not sample-accurately. This is fine for note-level correction (notes last hundreds of ms) but too coarse for reproducing fast vibrato faster than ~30 ms granularity without accepting the vocoder's own smoothing of it.
- Critically, this per-hop recomputation of the frequency mapping is **not a special code path added for "changing" the parameter** — it is the *normal, continuous, steady-state* operation of the algorithm. Every hop, even with a constant `freqMultiplier`, the code re-finds spectral peaks (`findPeaks()`) and re-derives the output map, because the input spectrum itself is different every hop. The phase-continuity mechanism that keeps output sounding smooth across hops (`outputBin.output = _impl::mul(outputBin.output, freqTwist)` propagating phase via rotation factors tied to the bin-to-bin frequency difference, `:642-660` and the prediction/rotation machinery `:696-803`) runs identically whether `freqMultiplier` changed since the last hop or not. **This is evidence — not proof — that changing the transpose value between hops is architecturally the same class of event as the ordinary hop-to-hop peak movement the algorithm already handles every single hop during normal playback**, rather than a special discontinuity case the library was never designed for.

### What I could NOT verify from source alone

- I did **not** find, anywhere in the vendored header, an explicit smoothing/ramp/crossfade specifically gated on *parameter changes* (e.g., no `previousFreqMultiplier` interpolated toward a `targetFreqMultiplier` across several hops). The smoothing that exists (`smoothEnergy()`, `:815-848`; the Hermite interpolation in `updateOutputMap()`, `:893-912`) smooths the **spectral energy envelope and the bin mapping across frequency**, not the **transpose value across time**. So if you jump `freqMultiplier` from 1.0 to 1.5 (up a fifth) between two adjacent hops, there is nothing in the source that ramps that jump — the next hop simply uses the new value.
- Whether that produces an audible click/zipper in practice for a **large, sudden** jump (e.g., a full-tone note-to-note correction landing exactly at a hop boundary) is a **DSP-behavioral question I cannot answer by reading the header alone** — it depends on how much the resulting output-bin phase/energy discontinuity is perceptually masked by the existing overlap-add reconstruction and phase-locking. I could not find a GitHub issue, the library's own design blog post, or its README explicitly addressing this (see below) — I did not run the code to listen, which this survey-only task does not permit anyway.

### What the upstream README and design writeup say

- **README (`https://github.com/Signalsmith-Audio/signalsmith-stretch/blob/main/README.md`, fetched 2026-07-29):** the library explicitly documents automation as a supported, intended use case, with this exact guidance: *"To follow pitch/time automation accurately, you should give it automation values from the current processing time (`.outputLatency()` samples ahead of the output)"* and *"You should be supplying input samples slightly ahead of the processing time (which is where changes to pitch-shift or stretch rate will be centred), and you'll receive output samples slightly behind that processing time."* This is direct, primary-source confirmation that **time-varying pitch-shift parameters are a designed-for use case, not merely something the API happens to permit** — the author gives explicit timing-alignment guidance (offset automation values by `outputLatency()`) that would be pointless to document if automation weren't expected to work. It does **not**, however, state that arbitrary jump sizes are artifact-free — see the honesty caveats folded into section 2 below.
- **Design blog post ("The Design of Signalsmith Stretch", `https://signalsmith-audio.co.uk/writing/2023/stretch-design/`, fetched 2026-07-29):** describes the peak-finding/non-linear-frequency-map/phase-prediction architecture in general terms but does **not** explicitly discuss dynamic/time-varying parameter changes, artifact risk from parameter jumps, or how often the map is recomputed (I got that from source, not this doc).
- **GitHub issues (`https://github.com/Signalsmith-Audio/signalsmith-stretch/issues`, checked 2026-07-29):** of the 4 open issues at check time (#28 Termux segfault, #26 TypeScript/web construction, #22 `addBuffers()` RangeError/gaps at 100ms chunks, #3 multi-channel handling), **none discusses clicks, zippering, or artifacts from changing transpose mid-stream.** Absence of a filed issue is weak evidence at best (could mean nobody tried it, or it works fine, or both) — flagging as inconclusive, not confirmation of quality.

### My assessment (evidence, not a verdict — that is the architect's call)

- **The API permits mid-stream transpose changes with no structural barrier**, and the author's own README treats parameter automation as a first-class, documented use case with specific timing guidance.
- **The mechanism that would make a changing transpose "clean" (phase continuity across hops) is the library's normal steady-state machinery, not a special case bolted on for automation** — this is a real, source-verified argument in favor of "reachable, not blocked," matching the coordinator's framing.
- **The one thing I cannot confirm either way is perceptual/artifact quality of a large, sudden jump landing at a hop boundary** — no source-level ramp exists for the parameter itself, and I found no upstream documentation, blog discussion, or issue thread that settles whether this is audible. This would need to be **empirically tested** (render a step change, e.g. a whole-tone correction, at a hop boundary and listen/measure), which is implementation work, not survey work.
- **Practical implication for the architect:** a "no" was NOT confirmed. The evidence leans toward "this is reachable without a segment-and-splice architecture," conditioned on (a) accepting the ~30 ms hop-granularity timing resolution this app's `presetDefault` configuration gives, consistent with note-level (not sample-level) correction, and (b) validating empirically that hop-boundary jumps for realistic correction magnitudes (semitones, not octaves) don't audibly click — I could not run that test as a research-only survey.

## 2. Resynthesis substrate — signalsmith-stretch, formant handling verbatim + the case against

**Verbatim from upstream README (`https://raw.githubusercontent.com/Signalsmith-Audio/signalsmith-stretch/main/README.md`, fetched 2026-07-29), independently re-confirmed (not just trusted from the 07-05 doc's paraphrase):**

> "The formant correction is not a[s] sharp as monophonic algorithms (such as PSOLA)."

> "It also needs you to give it a rough estimate of fundamental frequency (relative to Nyquist)." (re: `setFormantBase`)

> "time-stretching sounds best for more modest changes (between 0.75x and 1.5x)."

This is the library's own author stating plainly that its formant handling is a **polyphonic-capable, general-purpose compromise**, explicitly weaker than a dedicated monophonic technique like PSOLA/TD-PSOLA. This matters directly for the design gate: **signalsmith-stretch trades some formant sharpness for the ability to handle full mixes, not just solo vocals** — the case against using it (or against using it *alone*) for note-level vocal correction is that a purpose-built monophonic method could sound better on the exact material (solo sung vocal) this feature targets, at the cost of being useless for anything polyphonic. This is a genuine trade-off for the architect to weigh, not a defect to paper over.

**The internal f0 estimate is explicitly NOT usable as this feature's pitch detector.** Confirmed from source: `estimateFrequency()` (`signalsmith-stretch.h:929-966`) is invoked only from `updateFormants()` (`:972-1036`) when `setFormantBase(0)` requests auto-detection (as our shim does — `Sources/CSignalsmithStretch/shim.cpp:47-51`, `css_set_formant_preserve`). The library's own comment calls it *"VERY rough pitch estimation"* (`:950`) and it is a **single scalar per hop** (a running-average dominant frequency across 3 spectral peaks, smoothed with a fixed 0.25 IIR coefficient, `:962-965`) — not a per-note track, has no confidence value, no octave-error correction beyond a crude harmonic-folding heuristic (`:952-958`), and is private to the C++ class (never exposed through `css_*` or `OfflineStretcher`). **It exists to steer formant preservation, not to give a user an editable pitch curve.** This closes the question the coordinator flagged: signalsmith-stretch cannot supply the note-level f0 detector this feature needs; that detector is the real, separate gap covered in section A.

**What signalsmith-stretch DOES plainly give the architect, restated for clarity:**
- A resynthesis engine already vendored, already wired into `OfflineStretcher`, MIT-licensed (see section E), that can independently control pitch transposition and formant position (`setTransposeSemitones`/`setFormantFactor`/`setFormantBase`), with `compensatePitch` on the formant call explicitly designed to hold formants static while pitch moves — i.e., **the exact "shift this note's pitch without making it sound like a chipmunk/giant" behavior Auto-Tune/Melodyne-class tools need is a named, first-class feature of this library**, not something to bolt on.
- Per section 0, a plausible (evidence-based, not proven) path to feeding it a **time-varying** pitch curve rather than one constant value per whole clip, at ~30 ms granularity in this app's current configuration.
- An honest, author-stated ceiling on formant sharpness relative to PSOLA-class monophonic methods, and a recommended 0.75x-1.5x "sounds best" range for the *time-stretch* axis (not the pitch-shift axis, which is separately configured and not bounded by this figure). **This range is picked up again in section B below**, where it turns out to bound something concrete: how far a single note's *timing* can be edited, not just a whole clip's.

## A. Monophonic pitch detection (the real gap)

**Confirmed: no pitch/f0 tracker exists anywhere in this repo.** Direct listing of `Sources/DAWEngine/Analysis/` (11 files, not the 6 the coordinator named — noting the extra ones for completeness): `MasterMixAnalyzer.swift`, `KeyEstimator.swift`, `LiveLoudnessAnalyzer.swift`, `ReferenceAnalyzer.swift`, `TempoEstimator.swift`, `AudioAnalysisCache.swift`, `TransientCache.swift`, `InsertSpectrumTap.swift`, `SpectrumBandFold.swift`, `AudioContentAnalyzer.swift`, `TransientAnalyzer.swift`. None of these tracks fundamental frequency — `KeyEstimator` estimates musical *key* (a global/statistical pitch-class-histogram operation, not a per-frame f0 curve), and the rest are tempo/transient/loudness/spectrum-shape tools. **This is the real, confirmed gap the coordinator flagged**, and everything below is survey material for filling it, not a claim that it's already filled.

### What Apple ships that's relevant — and where it does not fit

**I could not find a public Apple API that performs monophonic pitch/f0 detection.** Specifically:
- **SoundAnalysis framework (`SNAudioStreamAnalyzer`/`SNClassifySoundRequest`)** is a sound *classification* API (identifying sound categories like "dog bark" or "applause" via Sound Classifier models), not a pitch tracker — my search did not surface any pitch-estimation request type in this framework, and to my knowledge it does not have one. **I am stating this as "not found," not as an exhaustively verified negative** — the architect should not take my word alone as final if this becomes load-bearing.
- **AVFAudio** has no pitch-detection API I could find; it has `AVAudioUnitTimePitch`/`AVAudioUnitVarispeed` (already surveyed in the 07-05 doc) for *changing* pitch, not measuring it.
- **Accelerate/vDSP** is real and relevant, but as a **toolkit, not a tracker**: it provides FFT and (via `vDSP` correlation functions) autocorrelation primitives that a hand-rolled YIN/autocorrelation-class detector could be built on — and this repo already leans on exactly this path: `signalsmith-linear` (vendored alongside `signalsmith-stretch`) is compiled with `SIGNALSMITH_USE_ACCELERATE` (confirmed, `Sources/CSignalsmithStretch/shim.cpp:5`) so its FFT already routes through vDSP. **This means the lowest-new-dependency option on the table is: hand-write a classical detector (YIN-class or SWIPE-class) in Swift/C using vDSP/FFT primitives that are already linked into this app**, rather than any of it being a "zero-effort, Apple already does this" situation — Apple gives building blocks, not a finished pitch tracker.

### Recommendation shape for the architect (not a decision — three real options, honestly differentiated)

1. **Vendor SwiftF0 (MIT, ONNX→CoreML, on-device, no sidecar)** — cleanest license, smallest footprint, purpose-built output shape (f0 + confidence + voicing per frame), and architecturally consistent with `OfflineStretcher`'s own pattern (pure offline computation in `DAWEngine`, no external process). Main risk: it's an ~11-month-old single-author project as of this survey, self-benchmarked, not yet proven at scale — a real "unproven but well-shaped" bet.
2. **Reuse RMVPE from the already-running RVC sidecar** — the single best accuracy on real singing data in the benchmark I found, and the model is *already vendored and running* in this codebase for a different purpose (port 8002). But: license **unconfirmed** (must be resolved before shipping), it's a Python/PyTorch pipeline (would mean either a new sidecar endpoint or reusing the existing RVC sidecar for a second purpose it wasn't designed for), and its exact confidence-output shape for segmentation purposes is **unconfirmed** by me.
3. **Vendor SWIPE′ (MIT, plain C, tiny) or hand-write YIN/pYIN-class autocorrelation on vDSP** — the lowest-risk, most "boring," license-cleanest classical option, at a real accuracy cost versus the neural options above (per the benchmark table, classical methods trail RMVPE/SwiftF0/CREPE by a meaningful margin on singing-specific data) — worth naming as the fallback if the architect wants zero new-model risk.

## B. Note segmentation

This is where, per the task framing, "Melodyne's actual quality lives": detection gives frames, the feature is notes, and frames→notes is the step that either succeeds or embarrasses itself. Failure modes matter more to the architect than algorithm names, because they are what the editor UI must let a user repair by hand — so this section leads with named published approaches, then defines what an editable note segment actually needs to carry (including timing, not just pitch), then gives each requested failure mode its own concrete treatment with mitigation *and* cost.

### Published approaches (what actually turns a curve into notes)

1. **A second, dedicated HMM/Viterbi decode stage — pYIN's own published note-tracking design.** Confirmed via search of the pYIN project's own materials (`code.soundsoftware.ac.uk/projects/pyin`, `vamp-plugins.org`, checked 2026-07-29): pYIN is not a single-stage algorithm. Stage 1 ("pitch tracking") Viterbi-decodes a smooth f0 path through multiple per-frame pitch candidates — this is the part already covered in section A as pYIN's accuracy/confidence mechanism. **Stage 2 ("note estimation") is a *separate* post-processing step: a second HMM, also Viterbi-decoded, run directly on top of the stage-1 pitch track**, described by the sources I found as decoding note boundaries from the pitch track — I did not verify the exact state definitions of this second HMM (e.g. whether states are literally "note on/off plus pitch class" or something else) beyond confirming the two-stage architecture itself, so I am not asserting the internal state design, only that this second, dedicated decode stage is real and published. This is the most directly citable, concrete "how do you actually do this" answer this survey found, and it is a genuinely different, additional piece of machinery from the pitch detector itself — the architect should not assume a pitch detector alone (even a very accurate one, per section A's table) comes with note segmentation for free; it is a second stage with its own design.
2. **Minimum-duration / hysteresis post-filtering.** A generic, widely-used technique in this literature — attributable specifically to the two-state pitch-wise HMM note-segmentation calibration work (arXiv:1704.08729, "Calibration of a two-state pitch-wise HMM method for note segmentation in Automatic Music Transcription systems," checked 2026-07-29) among the general MIR sources surfaced: after candidate note boundaries are produced, any candidate note shorter than a tunable threshold `k` is suppressed or merged into a neighbor — that source's own phrasing: *"all runs of active pitch of length smaller than k are set to 0"*; the stated purpose is explicitly "to reduce short false-positive notes." **This single technique is directly implicated in two of the five failure modes below (vibrato over-splitting and loss of genuinely short notes) — the same knob mitigates one and causes the other, which is the single most important structural fact in this section.**
3. **Onset/transient-informed splitting.** Using a separate onset/transient detector to force a note boundary even where the pitch curve alone shows no change — necessary specifically to catch a *repeated* note at the same pitch (a re-articulation with no pitch change at all, which pitch-only segmentation cannot see by definition). **This repo already has the building block for this**: `TransientAnalyzer.swift`/`TransientCache.swift` exist in `Sources/DAWEngine/Analysis/` (confirmed by direct listing in section A) — I did not evaluate whether their existing transient-detection logic is directly reusable for vocal onset detection specifically (they were built for other purposes; drum/mix transient detection and vocal-syllable-onset detection are related but not identical problems), but this is a concrete "build on, don't duplicate" opportunity for the architect to evaluate, consistent with the roadmap line's own instruction not to duplicate existing capability.

### What an editable note segment must carry — pitch AND timing

The roadmap line's own phrasing is "edit pitch/**timing** per segment," and timing is easy to lose sight of once the discussion is all about f0 curves. A note segment usable by an actual editor needs, at minimum:

- **Onset and offset time** — the segment's boundaries in the clip, independently movable from pitch.
- **A target pitch**, usually quantized to the nearest semitone — the value a piano-roll-style grid displays and the value that would drive `setTransposeSemitones` for that segment.
- **The raw per-frame f0 deviation curve retained *underneath* that target, not discarded** — this is what lets vibrato and natural pitch drift survive as an editable expression attribute of the note (a curve the user can see and choose how much to flatten) rather than being silently thrown away the moment a target pitch is assigned.

**The direct, previously-unstated connection between section 2 and this section: a per-note *timing* edit is, mechanically, a per-segment call into the same resynthesis engine surveyed in section 0/2, with a time-stretch ratio derived from how far the user drags that note's boundaries.** Which means signalsmith-stretch's own documented comfort zone — *"time-stretching sounds best for more modest changes (between 0.75x and 1.5x)"*, quoted verbatim in section 2 — is not an abstract caveat about the resynthesis library in the abstract; it is a concrete, already-sourced bound on **how far the editor can let a user drag or lengthen a single note's timing before quality is expected to degrade**. An editor UI (e.g. a per-note timing-drag handle) should reflect that bound rather than allow unlimited per-note stretch, and this is a design constraint the architect gets for free from section 2 rather than needing to separately source.

### The five failure modes, each with a concrete mitigation and its cost

**1. Vibrato read as several notes.** A segmenter driven by raw pitch-derivative sign changes treats each up/down half-cycle of vibrato as a candidate boundary; solo vocal vibrato commonly runs near 6 Hz (period ~165 ms) and can span up to roughly three semitones in extreme cases (opera-style singing, per literature found in this search round) — well inside a naive "that looks like a pitch change" threshold. *Mitigation*: raise the minimum-note-duration floor above a vibrato period so intra-note oscillation cannot itself produce sub-165ms fragments, and/or explicitly separate a smoothed "note-center" pitch trend (used for boundary decisions) from the raw oscillation (kept as the editable attribute described above, not a boundary signal) — this second approach is the qualitative difference between cheap tools that chop vibrato and Melodyne-class tools that track it as one note with an embedded vibrato curve. *Cost*: a duration floor tuned to suppress vibrato will also suppress or merge genuinely short real notes — see failure mode 5; these are not two independent knobs.

**2. Legato slides and portamento.** Directly sourced from this search round's summary of pYIN-note-tracking literature: *"The pYIN note approach can fail to split some legato passages into individual notes, misses some notes, and its boundaries are not exactly aligned with voiced/unvoiced transitions."* A smooth glide between two sung pitches, with no silence and no clean onset transient in between, gives a segmenter no clean acoustic signal to split on — this is close to a genuine ambiguity, not just an algorithm weakness. *Mitigation*: onset-informed splitting (approach 3 above) helps only when a real transient exists at the transition (common even in nominally-legato singing, e.g. a faint consonant or breath articulation), which by definition true portamento does not have; the more honest mitigations in the literature are either (a) modeling a glide as a first-class editable object in its own right rather than forcing a hard split, or (b) exposing a user-adjustable segmentation-sensitivity control so a human resolves genuinely ambiguous cases by hand. *Cost*: (a) is real editor data-model and UI scope, not a segmentation-algorithm fix — worth flagging plainly to the architect as a case where "pick a better algorithm" is not the actual answer.

**3. Unvoiced consonants and breath.** Sibilants and plosives carry no f0 at all (voicing probability near zero by construction); breath noise between phrases can register as low-confidence, borderline "voiced-ish" content to an overly permissive detector. *Mitigation*: gate directly on the per-frame voicing/confidence signal (this is exactly why section A weighted confidence output so heavily as a selection criterion — SwiftF0's explicit voicing decision, pYIN's probability output) and allow a short bridging tolerance (tens of ms) so a quick mid-syllable consonant does not fracture what a listener hears as one continuous note. *Cost*: too generous a bridging tolerance re-admits real silences and breath noise as spurious note continuations; too strict a one fragments words at every consonant. This is a threshold that needs empirical tuning against real vocal takes, not a value that can be picked from a paper and trusted.

**4. Octave jumps mid-note.** Directly sourced from this search round: *"Octave errors occur when pitch detection fails to locate the correct fundamental frequency and instead identifies the second harmonic as the fundamental frequency... The start and end of notes are most prone to octave errors."* A single outlier frame (or a short run of them) reporting double or half the true f0 either creates a spurious note boundary (the segmenter sees an "impossible" jump and splits there) or, worse, gets accepted and resynthesized at the wrong octave. *Mitigations found in this search round, several real options — with a provenance caveat*: (a) a simple heuristic comparing a note's first analysis frame to its second, flagging jumps exceeding "a predetermined threshold, typically 6 semitones"; (b) bilateral/median filtering to remove single-frame outliers and fill short gaps; (c) folding an octave-jump cost directly into the same Viterbi decode used for pitch tracking (large frequency deviations penalized in the path cost, so the HMM's preferred "smooth path" naturally avoids implausible jumps unless the evidence is strong); (d) cross-frame harmonic-amplitude fitting to identify which candidate frequency is the spurious harmonic. **Provenance flag, not previously stated: (a), (b), and (d) trace in my search results to USPTO patent filings (e.g. "Reducing octave errors during pitch determination for noisy audio signals," "Real-time pitch detection for creating, practicing and sharing of musical harmonies"), not academic papers — I am not able to and did not attempt to adjudicate patent validity, scope, or whether these specific claims would actually read on an independent implementation; that is a legal question outside this survey's scope, and section E's licensing standard (flag, don't assume clear) applies here too.** Mitigation **(c)** is the one of the four with clean academic provenance in this survey — it is architecturally the same mechanism pYIN's own published pitch-stage HMM already uses (section A/published-approach 1 above), just needing the same discipline applied at the note-segmentation stage too. *Cost (all four)*: tuned aggressively, any of these will also suppress or "correct away" a genuine, intentionally large pitch leap the singer actually performed — the architect should treat "is this jump real or an artifact" as a genuinely hard, not fully solved, problem rather than a box any single technique checks completely.

**5. Very short notes.** The exact same minimum-duration/hysteresis filtering that is the standard published mitigation for failure mode 1 (vibrato-over-splitting) and for generic false-positive suppression will, by construction, also delete or merge real short notes: grace notes, fast melismatic runs, rapid rhythmic vocal phrasing (e.g. rap-adjacent vocal lines), if their true duration falls under whatever floor is chosen. *Mitigation*: there is no clean algorithmic fix — the literature's own framing of the duration floor as a tunable parameter "to reduce short false-positive notes" is explicitly a precision/recall trade against genuine short notes, not a resolution of the tension. The most honest mitigation available is (a) exposing the threshold as adjustable (by the user, or by context — e.g. genre/tempo-aware defaults, a stricter floor for a ballad than for fast rap/melisma) and (b) always retaining the raw per-frame f0+confidence data underneath the segmented notes (not just the final segmentation — this is the same "keep the raw curve" point made above under "what an editable note segment must carry"), so a user can manually re-split an over-aggressively-merged short note in the editor rather than permanently losing it to a default threshold. *Cost*: **this is the same threshold as failure mode 1, in direct tension with it — there is no single minimum-duration value that is simultaneously correct for suppressing vibrato-fragmentation and for preserving genuine fast/short notes. This is a real, structural trade-off, not an oversight in any one algorithm, and the design doc should name it explicitly rather than pick one default number and move on.**
