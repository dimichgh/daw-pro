# Design Language — "Glass Cockpit"

Dark, glassy, information-dense but calm. Every glow means something. Think: night-flight avionics meets high-end studio hardware, rendered with macOS-native polish.

## Foundations

- **Surfaces**: near-black layered glass. Base `#0B0D12`, raised panels `#12151D` with 1px `white @ 6%` hairline borders and subtle inner shadow. Use translucency (`.ultraThinMaterial`-style) sparingly, only for overlays.
- **Text**: SF Pro for labels; **SF Mono for every numeric readout** (time, tempo, dB, Hz). Readouts are "digital": mono font, slight letterspacing, colored glow. Text runs a measured hierarchy — `textPrimary` (primary content) › `textSecondary` (legible secondary labels, ≥ 4.5:1) › `textDim` (muted captions/micro-labels, ≥ 4.5:1) › `textFaint` (placeholder & decorative floor, ≥ 3.0:1); every value is measured against the raised-panel surface. Never dim a real label below 4.5:1 with ad-hoc `.opacity()` — reach for the right token. **That whole hierarchy is measured on DARK surfaces and holds nowhere else**: on the app's **light surfaces** — the piano-roll ivory keyboard gutter and, since m23-ct, Musical Typing's on-screen keyboard, which reuses that exact palette rather than inventing a second one — every one of those tokens inverts (`textDim` measures 2.19:1 there), which is why those surfaces carry their own measured ink, `keyLabelOnWhite`. **A light surface always earns its own ink; it never borrows the dark hierarchy.** ⚠️ **That sentence — not a count — is what m23-b established.** This document said "the app's ONE light surface" until m23-ct, and the rule survived a second one intact because an ivory piano key is the one object in a DAW that is ivory in the world. A third light surface that is *not* a piano key is still a thing to argue about, not to add.
- **Accent system** (semantic, not decorative):
  - Cyan `#3EE6FF` — playback/position/active state
  - Amber `#FFB84D` — record/warning/clipping-adjacent
  - Red `#FF4D5E` — clip/overload/destructive
  - Green `#5DFF9F` — healthy signal, success
  - Violet `#B48CFF` — AI/generated content (everything AI-touched carries violet)
- **Glow recipe**: color at full opacity core + same-color shadow (radius 6–10, opacity 0.5–0.7) + faint wide bloom (radius 20, opacity 0.15). Glow intensity may encode magnitude (meter brightness follows level). Never glow static chrome.

## Components

- **Meters**: segmented LED-style bars (Canvas-drawn), green→amber→red zones, peak-hold tick that decays, glow tracks level. 60fps via `TimelineView`.
- **Transport**: oversized readout cluster — bars.beats + SMPTE time in mono cyan, tempo editable inline, glowing play/record buttons with state halos.
- **Knobs/faders**: flat dark caps, thin neon value arcs/tracks; value readout appears on touch. Double-click resets. Fine-drag with ⌥. **Grouped knob-grid surfaces** (the effect editor) follow the tight-column channel-strip convention (2026-07-19 knob-vs-slider report §5): the label sits ABOVE each knob with a persistent SF Mono readout below — never a left-aligned label column (that row shape stays the idiom for *unstructured* generic lists only). A knob's value arc is **unipolar** (sweeps from the range minimum — freq/Q/time/threshold/ratio/mix) or **bipolar** (fills center-out from the zero detent — ±dB gains, the `PanKnob` shape); the arc glows only while hovered or dragging (glow earned by state, the splitter idiom). **A CHANNEL-STRIP knob is the exception on both counts** (m23-a, `VolumeKnob`): it is one face of a value the strip ALSO shows as a fader, so it copies the fader rather than the knob grid — the arc sweeps **unipolar from the range minimum with a unity detent tick** (the fader's bottom-up fill and its "0 dB" line, because two controls showing one value must not disagree about where zero is, even though volume is nominally a ±dB gain), and its **glow follows level** rather than hover (a strip fader's glow encodes magnitude). It wears **cyan**, not `PanKnob`'s neutral white: pan has no meaning-color but volume does — the fader fill, the dB readout, and the arrange VOLUME automation lane are all `playback`. Its label sits above the cap and it carries **no readout of its own**: the strip's dB number is the glowing readout under the fader, and **one value never gets two copies on one strip**. PAN keeps its readout because it has no other — but on a channel strip that readout rides the **label line** (`PAN L100`), not a third line under the cap: vertical points on a strip are contested (see the RESERVED CLUSTER law), and a whole text line per knob row is the difference between a chain that fits at the default window and one that scrolls. It is still a pinned SF Mono readout — smaller (10 pt) but never scaled, and `fixedSize` on a 4-glyph worst case that clears the strip's content box by ~18 pt. **Readout units**: 0…1 "linear" AMOUNT params (mix, feedback, room size, damping, width) read as **percentages**, and the gain utility's linear multiplier reads as its **dB equivalent** — formatter-side only, the wire always keeps the raw model value.
- **Knob COMMIT CADENCE — a knob whose apply path is EXPENSIVE commits on RELEASE, not per frame** (m26-i). The house default is write-through: `KnobControl`'s `onChange` fires every drag tick, the model applies immediately, the user hears the change as they make it, and the store's per-track coalescing folds the whole drag into one undo step. **That default is only correct because most apply paths are free, and "free" is a property of the path, not of the knob.** Before cloning a knob grid onto a new model, price ONE apply. If it does per-item file I/O, rebuilds an engine node, or re-validates a collection, the same cadence that is invisible on a cheap path is catastrophic on yours — and it will *look* right, because the value moves and the sound changes. Reach for **`DAWApp/Components/DeferredKnob`**: it holds an optimistic LOCAL fraction while the drag is live (so the cap and its readout track the pointer at 60 fps with no model involvement at all) and calls the model **exactly once, on release**. Three parts of that are load-bearing and each has already been got wrong somewhere: **(1) the optimistic `@State` lives in the KNOB leaf, never in the owning card** — a `@State` write invalidates its owner, so parking it on the card re-evaluates the whole card body per drag frame, which is precisely the per-frame recomputation the deferral was bought to avoid (on the sampler card that re-maps every zone row and re-runs the coverage analysis); **(2) the commit is gated on the drag having actually MOVED the value** — the gesture is `DragGesture(minimumDistance: 0)`, so a plain CLICK is a complete drag with zero translation and a double-click reset is two of them, and an ungated `onEnded` makes every stray click on the cap pay a full apply; **(3) the local value is CLEARED on commit, unconditionally** — if the apply is refused the cap visibly springs back to what the model actually holds, beside the card's inline error, because a knob still showing the value it failed to write is the silent-plausible failure this project keeps closing. The worked case is the built-in Sampler: `ProjectStore.setInstrument` re-validates the whole zone list on every sampler apply (a `fileExists` plus a media open **per zone**, on the main actor — 46 file opens for the user's saxophone, 309 for a large library) and any per-zone scalar edit flips `instrumentNodeIdentityChanged`, which can force an instrument-node teardown and engine rebuild; the poly-synth card pays **neither** (`case .testTone, .polySynth: return false`), which is exactly why the precedent being copied is silent about both. ⭐ **This is the m25-k shape — a correct land-time policy invoked at drag cadence — and "a correct policy at the wrong cadence looks exactly like a correct policy."** ⚠️ **Undo coalescing cannot see this and must not be read as absolution**: 60 ticks fold into one undo entry whether the cadence is right or wrong, so a green undo test is compatible with thousands of main-actor file opens per second.
- **Centered modal cards — the height budget, and WHICH region yields** (m26-i). A centered dark-glass card is sized by its content, but the moment it carries a region that can outgrow the window — a list, a chain, a variable inspector — it needs an explicit budget, and the budget has two parts that must be decided TOGETHER. **(1) The ceiling is derived from the window, never a constant.** A fixed ceiling is wrong in both directions at once: it overflows a short window and strands space in a tall one. **(2) Exactly one region yields, and it is a DECISION, not a leftover.** A `VStack` compresses its flexible children first, and a `ScrollView` is maximally flexible — so in a card that wants more height than its ceiling allows, **any scroller present absorbs the ENTIRE shortfall**, whether or not it is the region you meant to shrink. The yielding region hugs its content when it fits and scrolls inside its room when it does not — `ScrollView { … }.frame(maxHeight: room).fixedSize(horizontal: false, vertical: true)`, the RESERVED CLUSTER law's own mechanism, where `fixedSize` is again the load-bearing word. Every other region takes a **fixed, computed** height. ⛔ **The sampler card shipped with these backwards and it is the reference failure**: a constant ceiling (620) below the card's own content, with the ZONE LIST as the only scroller — so opening the per-zone inspector collapsed the list to **~1.7 rows**, identical at 3 zones and at 46, in a window with ~280 pt to spare. Selecting a zone to tune it destroyed the list you select zones from. The fix inverted the roles: the list takes a computed height with a **row FLOOR** (a valve, not a target — the `faderRegionFloor` idiom) and the inspector yields. ⭐⭐ **PUT THE ARITHMETIC IN A HEADLESS TYPE** (`DAWAppKit.SamplerCardLayout`, the `MixerStripLayout` precedent) — a visible row count a test can assert is a row count somebody can be wrong about out loud, and its own pin immediately caught a second defect: a *picked* minimum-height constant let the row floor outrank the ceiling and overflow a small window, which deriving the minimum (`chrome + floor rows`) fixed by construction. ⚠️⚠️ **AND NOTE WHAT FOUND THE FIRST ONE: PIXELS.** The suite was green, the build was clean, the model was correct and the card really did render — the collapse existed only in the one state a first glance does not linger on. **A card with a variable region ships with a render probe (`debug.captureUI` on staging) or it ships unverified**; every headless check in that round would have looked identical had the list drawn nothing at all. ⭐⭐⭐ **AND MEASURE THE BUDGET'S CONSTANTS FROM THE RUNNING APP, NEVER BY ADDING UP PADDINGS.** A headless layout type still needs to know how tall the card's fixed chrome is, and that number is the one part of it a test cannot derive — every pin CONSUMES it, so all of them stay green when it is wrong. `debug.explainFrames` reports the card's DRAWN box, and two measurements settle it: take the same card at two row counts and the known list height subtracts out, leaving the chrome+region lump; then **squeeze the window to `WindowFloor`**, where the yielding region CLAMPS, and the card measures `ceiling + (chrome_real − chromeConstant)` — so its overshoot IS that constant's error, isolated. `scripts/gates/_m26i-card-height-probe.mjs` is the worked example; it parses the constants out of the Swift source rather than restating them, and on its first run it found the sampler card's hand-summed inspector height under-stated the drawn one by 3 pt. ⚠️ **Know which constant can actually hurt you: only the FIXED-CHROME one can overflow the card** (an error in the yielding region's estimate merely mis-splits the space), so assert them separately — a check on their sum can pass while the dangerous half is wrong.
- **Mixer strip — the RESERVED CLUSTER law** (m23-a): a channel/bus strip is split into a cluster that **never yields** — header · VOL|PAN knob row · fader + meter + dB readout · Mute/Solo/Arm — and exactly ONE region that does: the Pro signal-flow block (inserts · sends · output). The yielding region is bounded by `DAWAppKit.MixerStripLayout.signalFlowRoom(available:)` = `available − reserved`, further capped at a **share** of the strip (not a point cap — a point cap either scrolls a modest chain on a tall window or starves the fader on a short one) so the fader's throw stays proportional however long the chain grows. Inside that bound the region **hugs its content when it fits and scrolls internally when it doesn't**, from ONE view: `ScrollView { stack }.frame(maxHeight: room).fixedSize(horizontal: false, vertical: true)`. Read those three as one mechanism — a `ScrollView`'s ideal height is its content's height, `fixedSize` makes the region take that ideal instead of the height the stack offers it, and `maxHeight` clamps the ideal to `room`. The region is therefore **inflexible at `min(content, room)`**, so the greedy fader below absorbs every point the chain doesn't use. **`fixedSize` is the load-bearing word**: a bare `maxHeight` frame stretches to whatever it is proposed, and the first m23-a cut (which also used `ViewThatFits` + `layoutPriority(1)` to win that space) held a ~200 pt void in a two-insert strip with the fader crammed underneath — the guard rail reintroducing the very failure it exists to remove. A single scroller is also why there is no `ViewThatFits` here: two branches means two copies of the subtree and two copies of every `.explainable` anchor inside it. **Strips hug independently, so their dividers do NOT line up across the console — that is deliberate**: a uniform divider makes every strip pay the tallest strip's chain height, and the m17-f F2 alignment promise is the reserved instrument-chip SLOT, not a shared fold line. **⚠️ SUPERSEDED FOR THE INSERTS ROWS ONLY — m23-strip-reserve, 2026-07-28, REVERSED AT THE USER'S REQUEST; see the inserts-reserve law below, and do NOT restore the hug there as a regression fix.** The sentence is kept rather than deleted because it still governs SENDS and OUTPUT, which do still hug — so adding a *send* still moves the rows below it. The other budget rule with teeth: **an ordinary full chain must fit at the DEFAULT window without scrolling** (**was** `MixerStripLayout.maximalChainNaturalHeight` — 8 inserts, a send and the output picker, measured — clearing `signalFlowRoom(available: stripHeightAtDefaultWindow)`; **REPLACED at m23-strip-reserve by `signalFlowNaturalHeight(room:isCollapsed:)`, which carries the STRONGER promise — the block fits at the default window at ANY chain length — because the old constant's premise, that height depends on chain length, stopped being true**). A 9th insert scrolling is correct; a console whose everyday full chain cuts its OUTPUT row mid-button at 1440×900 reads as broken, which is why the knob row spends **two lines, not three** — the pan readout rides its label line (`PAN L100`) rather than claiming a whole text line under the cap. **Why this is a law and not a tweak:** the pre-m23-a strip carried a hard `minHeight: 150` on its fader, which is an intrinsic minimum the strip exports to the console — and the console has no vertical scroll, so as m22-e's insert chips stacked the console demanded more height than the window had, pushing the app header row and the transport bar clean OFF the window (measured at 1440×760 with an 8-insert chain) and letting the strip's own `clipShape` cut the dB readout and the Mute/Solo/Arm row away at 1440×640. **The fader's floor is a valve, not a target**: it sits well under a comfortable fader so the fader compresses a little before anything is ever lost, and a strip that reads its own height through a `GeometryReader` exports NO minimum, so the console can never again shove the window's chrome off-screen. A **collapse disclosure** on the INSERTS header (neutral chevron, Rule 3 — a disclosure is not an earned state) folds the rows away for manual fader work; it is a console-wide, app-sticky PREFERENCE (`panelLayout.mixerInsertsCollapsed`, staged by `debug.panelLayout`), **default EXPANDED** — a persisted "collapsed" default would make existing chains vanish on update — and the section always keeps its label, its SF Mono **count badge** (the chain's true length, so a folded *or merely scrolled* chain never reads as a shorter one) and its "+" menu. The **MASTER strip cannot use this law** and says so: since m22-c/d/g its anatomy needs ~690 pt against the ~430 pt a strip gets at the window floor, so it rides ONE internal vertical scroller (the m17-f F4 compression law) with `minHeight: viewport` on the content (the arrange shared-scroll idiom) so it still STRETCHES to fill at a comfortable window. Its identity block scrolls with the rest — a deliberate deviation from F4's pinned header, because pinning costs 52 pt of viewport, enough to turn a strip that fits at the DEFAULT window into one that scrolls, and unlike the Sketchpad/ClipFix panels that header holds no controls and the strip is unmistakable by its cyan accent border.
- **Mixer strip — the INSERTS RESERVE law** (m23-strip-reserve, 2026-07-28). Every Pro strip reserves a fixed viewport for insert rows — **channel 3, bus 5, master 5** (the last two raised at the user's request, m23-ax, 2026-07-30). The fader, dB readout, Mute/Solo/Arm row, Sends and Output therefore **do not move when an insert is added or removed**; a chain longer than the reserve scrolls inside the viewport. **The invariant is per-strip stability under chain length, and cross-strip agreement WITHIN a class** — the three classes deliberately no longer agree with each other, and buses are drawn after the console's own bus divider, so the step is a class boundary rather than a ragged rack. This **reverses, for the inserts rows only, the m23-a "strips hug independently" rule above** — at the user's explicit request, made after five ordinary inserts were measured moving that strip's pan row, fader and dB readout down **121 pt** while the neighbouring strip's stayed put (fader `0:373 → 1:382 → 3:438 → 4:466 → 12:622`). **The mechanism is that `MixerStripLayout.insertsViewportHeight(room:isCollapsed:)` takes the strip's available room and NOTHING ELSE — there is no chain-length parameter, which is what makes cross-strip agreement structural rather than coincidental. Do not add one.** Measured constants (the `WindowFloor` idiom — measured via `debug.explainFrames`, three independent row-count differences all returning 28 = row 24 + gap 4, cross-checked h(1)=44): ordinary insert row **24 pt**, **keyable (sidechain) row 42 pt** — so two compressors already overflow the reserve and scroll, which changes how many rows SHOW but never the positions below — row gap 4, section header 16, giving 80 pt of rows in a 100 pt section. **Three slots is the largest reserve that never degrades on any window the app can show**: `rows(4) = 108` exceeds the 640 pt floor's allowance of 106, proven by mutation. **That is exactly why the CHANNEL stayed at 3 when m23-ax raised the others**, and why the bus's 5 carries a knowingly weaker guarantee: five rows need 136 pt of allowance, so a bus steps 5 → 4 → 3 as the window shrinks (full five from roughly a 685 pt window up, so the default 1440×900 shows all five). Every bus degrades at the same instant, so buses still agree with buses, and the reserve still depends on **room and class, never on chain length** — the property that keeps a control from moving under the hand. **The MASTER takes no valve at all**: the valve prevents an over-tall reserve from clipping a fader inside a region that cannot scroll, and the master's whole anatomy already rides its own scroller, so it scrolls instead of clipping. Deriving a master "room" honestly would have handed it **two** slots — fewer than a channel. Below the floor the reserve sheds WHOLE rows, never a sliced chip, and never below one — a valve like `faderRegionFloor`, not a target. **Honest cost, recorded not hidden:** at the 640 pt floor the reserved block is 190 pt against 126 pt of room, so a zero-insert strip moved from just-fitting to a **64 pt overhang** and Output sits below the scroll fold there (a 1-insert strip already overhung by 8 pt before this change). Nothing clips. **The MASTER's honest cost (m23-ax), measured at 1440×900 before the change:** its fader region stretched to 179 pt against a 130 pt floor — 49 pt of slack — and the section grew 28 pt per insert, so the master already hit its floor and began scrolling at the **third** insert, its fader travelling 205 pt down across an 8-insert chain. The flat 5-slot reserve spends that 49 pt up front: the master now scrolls from an empty chain and its fader sits at the 130 pt floor always. That is the trade the reserve buys — the fader, LOUDNESS, STEREO IMAGE and the REFERENCE row stop moving, and a chain past five scrolls inside the reserve instead of pushing them off the fold. **Collapsing the disclosure reserves NOTHING** and hands all 84 pt back to the fader: the control promises to "give the volume fader more room," and a fold that kept three empty rows would be the do-nothing toggle this document forbids; it is console-wide, so every strip sheds the same rows at once and cross-strip agreement survives. The **empty state is a dashed well filling the full reserve**, labelled "No inserts / Add with +" — the space is deliberate and must read that way; the same dashed treatment continues under a PARTIAL chain so 1-of-3 reads as "three slots, one filled" rather than as content that failed to load (chosen by the user 2026-07-28 after seeing the bare-void alternative). The **MASTER strip is explicitly exempt** and keeps hugging: it already rides one internal scroller for its whole anatomy and has no cross-strip line to hold.
- **Waveforms**: dual-tone (body + brighter RMS core), violet tint when clip is AI-generated.
- **Panels**: every panel has Simple and Pro density modes; Simple shows the 20% of controls used 80% of the time with plain-language labels ("Punchier" over "Ratio 4:1" — Pro mode shows both). Mode is a themed segmented chip pair (SIMPLE / PRO), the active half cyan-lit; Simple is the default. **Density is a per-panel, app-sticky PREFERENCE, never project data** — each panel owns its own mode (a beginner may want a Pro piano roll but a Simple mixer), it survives close/reopen and app relaunch (persisted as `panelDensity.<panelID>` in UserDefaults), and it is NEVER written into the project file. The chip pair is one shared component — `DAWApp/Components/SimpleProToggle`, bound to a `DAWAppKit.PanelDensityStore` + a stable panel ID — so it is pixel-identical everywhere (SF Mono 9 pt bold uppercase, tracking 0.6, active half `playback` on an 0.18 fill, on a raised chip with a hairline border). The headless model lives in `DAWAppKit.PanelDensity`/`PanelDensityStore` (injected persistence backing, `@Observable`); `debug.panelDensity {panel, mode}` stages a mode for captures/E2E (debug tier — not an MCP tool). The per-panel Simple/Pro plan lives in `docs/research/simple-pro-inventory.md`. Panels that already pass the beginner test adopt the model but render identically in both modes (their modes coincide); the piano roll is the reference implementation. As of sp-d, **density coverage is uniform**: five surfaces carry live chips (piano roll, mixer, arrange, transport, and — m10-n-3 — the **instrument picker**, whose Simple "Instrument Sets" and Pro full browser genuinely differ); every other panel's Simple and Pro modes **COINCIDE by design and must never grow a do-nothing toggle** — a toggle that changes nothing is worse than none (the per-surface roll-up lives in `docs/research/simple-pro-inventory.md` §"Density adoption status"). A new surface earns a chip ONLY when its two modes genuinely differ (the picker does; the inventory records the verdict).
- **Arrange timeline**: zoomable pixels-per-beat (m17-b — 4…200 pt/beat, default 16; ⌘+/⌘−/⌘0 via the View menu with a bare-⌘= alias, pinch on the lanes anchored at the pointer, and a neutral toolbar cluster beside the SNAP chip: a −/+ pair around an SF Mono percent readout plus an S/M/L track-height chip whose active step is cyan-lit, the SimpleProToggle active-half idiom — shown in BOTH densities, zoom is navigation not edit chrome). Keyboard/toolbar zoom holds the PLAYHEAD's screen x when it's in view (else the viewport center) so the view never jumps; at the left edge the origin pins instead of showing space before beat 0. The pinned ruler block and the lanes rescale in the SAME update (one `PanelLayoutStore.arrangePPB` value feeds both instances), grid density adapts instead of forking (per-beat hairlines drop below 8 pt/beat; bar numbers thin to every 2ⁿth bar via `ArrangeZoom.barLabelStride`), and the S/M/L steps write the same `panelLayout.rowHeight` the m10-d splitter drags so the sidebar rows and lanes stay row-aligned by construction. Zoom is an app-side sticky PREFERENCE (`panelLayout.arrangePPB` — never project data, never undoable, never in the wire snapshot); math lives headless in `DAWAppKit.ArrangeZoom`; `debug.arrangeZoom` stages it for captures/E2E (app tier, off `allCommands`/MCP). One lane per track in sidebar order. Clips are rounded tinted blocks — signal-green for audio, playback-cyan for MIDI, **violet whenever AI-touched** — with a name label when width allows, selected clip brighter + glowing. Beat grid is hairlines; bar lines brighter; bar numbers in SF Mono. Playhead is a glowing cyan hairline driven by transport position (offset a view, never a per-frame Canvas redraw). The **loop region** (beta m10-g) is a direct-manipulation band in a distinct strip at the TOP of the ruler (`y ∈ [2, 14]` of the 56 pt ruler — the ruler grew 42 → 56 in m11-c to seat the marker lane below the loop band, still clear of the bar numbers and read-through of the playhead): **cyan glowing when looping is enabled** (cyan = earned active transport state, NEVER violet), a **dim low-opacity outline when a region exists but looping is off**, nothing when there is no region. The whole ruler height is the interaction surface (so the loop is grabbable anywhere in the ruler column): **drag empty ruler to sketch** a new region (snapped to the arrange grid — Bar in Simple, the picked snap in Pro — with a minimum of one snap unit, a sub-threshold drag falling through to a click), **drag either edge to resize** (`resizeLeftRight`, clamped one snap unit before the opposite edge — never inverts), **drag the body to move** it preserving length (grab→grabbing, clamped at beat 0), **click inside to toggle** looping (the TransportBar LOOP chip's twin), and **click empty ruler to seek** the transport to that snapped beat (the ruler is never a dead click surface — the piano-roll scrub idiom, one surface over). All zone-classification / create-resize-move / click math is headless + tested in `DAWAppKit.LoopRulerModel` (`LoopRulerGeometry` + `LoopEdit`, the `ClipEdit`/`PianoRollPlayhead` precedent); loop state flows into the timeline by value so an agent's `transport.setLoop` over the wire updates the band live, and the gestures route through the pre-existing `setLoop`/`seek` store methods — a **non-invokable pure-view surface**, no new wire command / MCP tool (the m10-c/e precedent). The **session-marker lane** (m11-c) is a SECOND direct-manipulation strip in the ruler, `y ∈ [15, 33]` — BELOW the loop band, ABOVE the bar numbers — carrying named song-section flags ("Intro", "Chorus", "Drop"). Markers are **navigation furniture, not an active or AI state, so the flags are deliberately NEUTRAL** — a dark raised-glass chip (`panelRaised` + hairline) with the name in SF Pro (`textSecondary` — a name is prose, not a numeric readout) and a thin `textSecondary` anchor bar at the marker's exact beat: **no cyan (that's earned active transport), no violet (that's AI only)**. The marker strip is the marker gesture surface, layered over the loop ruler but occupying ONLY its band, so it carves that strip out of the loop hit zone WITHOUT touching the loop band or the seek area — the m10-g loop gestures (create/resize/move/toggle/click-seek) keep working, regression-pinned. Interactions: **drag empty marker-strip → context menu "Add Marker Here"** at the snapped beat (the strip also click-seeks, so it's never dead), **drag a flag to move it** (snapped, `grabbing` cursor, the move coalesces into one undo step), **click a flag to jump** the playhead to that section (the seek path), **double-click or the context menu to rename in place** (the same SF-Pro dark-glass field + cyan focus border + trim/empty-cancel/unchanged-no-op commit rule as the track-header rename, reusing `DAWAppKit.TrackRename`), and the context menu also **deletes**. All geometry / hit-test / snapped-move / add-beat math is headless + tested in `DAWAppKit.MarkerLaneModel` (`MarkerLaneGeometry` + `MarkerLaneEdit`, the `LoopRulerModel` precedent). Both densities render markers identically (COINCIDENT-EXEMPT — see `docs/research/simple-pro-inventory.md`); markers flow into the timeline by value so an agent's `marker.*` over the wire updates the lane live, and every mutation routes through the store's marker methods (undo/coalescing free). Unlike the loop ruler this DOES ship a wire surface — five `marker.*` commands + the `transport.seek {marker}` interop (the house rule: the drag-to-move UI is a user-facing capability, so it earns a control command + MCP tool + test). **Track header identity** (beta m10-i): the sidebar row's icon+name is ALWAYS readable, and — critically — its width budget **never inflates the sidebar past its 250 pt floor** (that would slide the whole panel off the window's left edge). The name is a **SOFT, priority-won, truncating label** — `.layoutPriority(1)` on the identity cluster hands it the row's surplus so it reads (≳ 60 pt even at sidebar 250), but it carries **no hard minimum width** (its intrinsic min is just an ellipsis), so it can never push the sidebar minimum up. The `MiniLevelBar` gracefully **compresses to a narrower floor** (22–44 pt, a slimmer 10-segment bar, NEVER hidden), and the **clip-count badge is the least load-bearing chip — it folds into the identity tooltip below a sidebar-width threshold** (`DAWAppKit.TrackHeaderLayout.showsClipBadge`, folded < 300 pt) rather than steal the name's room. Row spacing tightens to 4 pt and the row's square chips (M/S/R toggles, the automation/takes disclosures) sit at 18 pt wide (m17-f F1 — at 5 pt spacing / 20 pt chips an instrument row's fixed chrome left the name only ~23–45 pt at the DEFAULT 260 pt sidebar, truncating "Synth 10"; the ~16 pt recovered keeps the name readable at 260 AND at the 250 pt floor with Small rows). A long name truncates at the **tail** (the app's `lineLimit(1)` convention) with the full name + clip count in a `.help` tooltip (`TrackHeaderLayout.identityTooltip`). - **Follow the playhead** (m23-c2): an **opt-in** auto-scroll that keeps the playhead in frame during playback, on the arrange lanes and on all three piano-roll bands. Its rules are one shared headless policy — `DAWAppKit.FollowPlayhead` — so two surfaces can never disagree about when a page turns.
  - **PAGE, not continuous — and that was MEASURED, not assumed.** Both policies were built and driven through the same 8 bars of real playback on the same session: page issued **4** scrolls at a **15 ms** main-actor p50; continuous issued **262** at **49 ms** p50. On a ~33 ms transport tick, a main actor answering in 49 ms is already behind the cadence it is following. Continuous also has no honest implementation on the macOS 14 floor (`ScrollPosition(x:y:)` is macOS 15+), so every tick would re-lay-out an anchor inside the scroll content. The page turn lands the playhead **12% of a viewport in from the leading edge** (never flush — the eye needs the bar it just played), and turns only when the playhead crosses within **32 pt** of an edge (capped at a quarter viewport so a narrow panel cannot chatter).
  - **The target is always CLAMPED to `contentWidth − viewport`.** This is load-bearing, not tidiness: the lanes pad their content to `viewport + hScrollApplyTarget`, so an unclamped target would grow the timeline and re-lay-out the whole lane stack on every page turn. Measured, the content width changes **zero** times across a follow run on either surface.
  - **A manual scroll during playback SUSPENDS follow on that surface** — until the transport is started again or the chip is clicked. The view never fights the pointer. Suspension is **per surface** (scrolling the roll must not stand the arrange down) while the ON/OFF flag is ONE value, and it is **visible**: the header **FOLLOW** chip has three faces — off (neutral chrome), following (cyan fill + glow), **paused (cyan outline, no fill, no glow)**. A control that claims to be following while the view sits still is the dishonest-readout class this project keeps closing. While paused, a chip click RESUMES rather than switching off.
  - **Follow is only suspendable while it is actually DRIVING that surface.** With the transport outside the edited clip the roll has no playhead line to keep in frame (m23-c1), so follow issues nothing — and must not read a scroll as a fight it was never in.
  - **Drive it from the TRANSPORT observation path, never from a geometry callback.** A `scrollTo` issued inside a layout transaction moves layout but does not durably update the scroller's internal position (m17-b, measured), and `debug.captureUI`'s `cacheDisplay` forces exactly the re-render that then jumps. Every follow tick hangs off `transport.positionBeats`, and the landing is re-issued once on a fresh main-actor turn to make it durable.
  - **Scope the `ScrollViewReader` to the axis you are moving.** A reader resolves `scrollTo` against every scroll view inside its content, and `anchor: .leading` carries a y of 0.5 — so a reader wrapping the roll's nested vertical + horizontal scrollers would re-centre the pitch range on every page turn. The roll's reader lives INSIDE the vertical scroller, which is why its `.defaultScrollAnchor(.center)` opening position is untouchable by follow (gate-proven: the keyboard gutter is byte-identical across a following run).
  - **The CONTROLLER strip follows for LOCKSTEP, not for itself.** It carries no playhead of its own (m23-c1), so it has nothing to keep in frame — it takes the same target and nonce as the grid and the velocity lane so the CC line never slides out from under the notes it belongs to. That also makes it the one band the playhead cannot prove: the gate gives the fixture clip a real CC lane with alternating values, and each point's full-height riser is the probe (measured — at a paged offset of 1135 the risers sit at 261.5/1061.5/1861.5/2661.5, on the note starts to within a pixel and where the reported offset predicts). A band whose follow is wired but never drawn is untestable by construction; give it ink.
  - **Off by default, and app-sticky, never project data**: `panelLayout.followPlayhead`, staged and read through `debug.panelLayout {followPlayhead}` like every other sticky dimension; `debug.followPlayhead` echoes both surfaces' live geometry, suspension and churn counters (debug tier — off `allCommands`/MCP, zero wire surface).

- **Clip editing** (arrange interaction layer): the arrange header carries a **grid-snap picker** (Off / Bar / Beat / 1/2 / 1/4, default Bar; **Bar follows the meter** — 3 beats in 3/4), a themed chip menu styled like the input-device chip, right-aligned under an "ARRANGE" label. Snap governs move, trim, and split (never fades — a fade is a continuous shape). A clip is **direct-manipulation**: drag the body to move, the ~6 pt left/right edge strips to trim, the top-corner grips to fade, double-click at a point to split (a context menu also offers Split at Playhead + curve toggles + Reset Gain). Fades render as **translucent** shading (never opaque — the waveform reads through) dimming the faded corner, its inner edge the fade curve (**linear = straight, equal-power = bowed**); a small triangular grip sits at each fade's inner end, faint at rest and bright on hover/selection; alt/⌥-click a grip flips its curve. A live drag shows an SF Mono beat/length/fade readout by the cursor. Per-clip **gain** is a subtle SF Mono cyan dB chip (dB readouts are cyan) shown only when non-zero or on hover/selection; drag it up/down to adjust. In **Pro**, a SELECTED audio clip additionally reveals a **gain-envelope overlay** (m13-e) — a cyan Canvas polyline of glowing breakpoint dots (the glow recipe) that rides the clip's volume up and down over time, over a faint dashed 0 dB guide; click to add a point, drag to move (live SF Mono dB/beat readout), double-click to delete. The overlay draws **no opaque backing** — just the polyline + dots + guide — and **the waveform stays visible UNDER it as a 0.4-opacity GHOST** (m13-g sub-task 3) so breakpoints read against the audio they shape (cyan overlay is the primary layer, ghosted waveform the backdrop). One `.explainable(.clipGainEnvelope)` card summarizes the whole Canvas/gesture surface (the honest-scope rule). **Simple hides the overlay entirely** — the waveform then draws at full strength. **Time-stretch** is the same right edge under ⌥ (option): a faint "≈" grip cue on the right edge of an audio clip brightens cyan while ⌥ is held, and ⌥-dragging it retargets the clip's timeline length (window-invariant, wired to `stretchClip`) instead of trimming — with an SF Mono "length · ratio" readout (e.g. "6.0 beats · 1.50×"); MIDI right-edge ⌥-drag stays a plain trim (stretch is audio-only). Any non-identity clip carries a persistent SF Mono ratio/pitch **badge** ("1.50×", "+3st") so stretched clips read distinct; a clip stretched **outside the 0.75–1.5× transparent band tints amber** (border + badge glow, a soft warning — never a hard block, the ratio range still spans 0.25–4×) with a tooltip naming the ratio. While the engine's offline stretch render is pending the clip body carries an **animated shimmer** (a slow tint-colored diagonal highlight sweep — the "working" cue, never a spinner); a failed render shows a **red border + glowing red dot**. All stretch geometry/threshold/formatting is headless in `DAWAppKit.ClipStretch` (the `ClipEdit` precedent). Audio clips draw a dual-tone peak **waveform** (body + brighter core, violet when AI) computed off-main and cached by file URL, windowed by `startOffsetSeconds` so a split or leading-trim shows the right slice of the source; the outline redraws only on data change (no TimelineView, no per-frame allocation). **Waveform HEIGHT is a view setting, not a property of the file** (m25-e): by default the outline is **auto-fitted** — scaled up so the source's own loudest peak reaches the block's full height — because raw amplitude drew quiet-but-perfectly-normal material as a thin ribbon in a mostly-empty clip. **The boost is CAPPED at 4×** so genuinely near-silent material still reads near-silent instead of blooming into full-height noise; the cost of that cap is stated rather than hidden — above a quarter of full scale every clip fills the block, so fit mode *does* erase the at-a-glance "which clip is hotter" comparison, **and that is exactly why normalisation is a MODE and never a silent global change**. A **TRUE LEVEL** (raw) mode restores real amplitude pixel-for-pixel, and is one click away and persisted. On top of either mode sits a **vertical zoom** (1–8×, a clean ladder 1 / 1.5 / 2 / 3 / 4 / 6 / 8 so a permanent readout never shows `1.9×`); zoomed past full height the drawing is **trimmed at the clip edge**, never squashed back to fit — the standard DAW behaviour, and the only honest one, since rescaling would silently undo the zoom just asked for. The peak used for the fit is **FILE-scope, not clip-scope** (the cache is keyed by URL and shared by every clip windowing that source): a split covering a quiet passage of a loud file keeps the loud file's factor and reads quiet, because a per-window peak would make the two halves of one split draw at different scales. Both settings are ONE value read by **every** waveform in the workspace — the clip blocks *and* the dim take-lane material — so a comping surface can never disagree with the clip comped out of it. All of it is headless in `DAWAppKit.WaveformScale` (the `ArrangeZoom` precedent: that type owns the horizontal axis' math, this one the vertical); the Canvas does one multiply by a scalar resolved once per view, never per column and never per frame. The control is the arrange toolbar's **WAVE cluster** (`DAWApp/Components/WaveformZoomControl`, plain value inputs) — a deliberate mirror of the horizontal zoom cluster beside it, `−` · an SF Mono `FIT` / `RAW` / `FIT 2×` readout · `+`, the middle element opening a chip menu with the mode, the preset ladder and a reset; ⌥⌘± / ⌥⌘0 in the View menu are the keyboard twins of ⌘± / ⌘0, deliberately NOT routed through the editor-surface zoom router (⌘± means *time* on whichever editor has focus, and the piano roll has no waveform to scale). **Neutral chrome in every state** — neither mode is an earned active state, so neither takes cyan (Rule 3); the readout instead lifts `textDim`→`textPrimary` once the user is off the default. The cluster renders **only when the project contains audio** (the m22-g reference-row precedent: zero chrome for a project it could do nothing for). Both settings are sticky app PREFERENCES in `PanelLayoutStore` — never project data, never undoable, never in the wire snapshot — staged for captures through `debug.panelLayout {waveformNormalize, waveformVerticalZoom}`, adding **ZERO new wire commands** (the m10-c/sp-b pure-view rule). **Clip content is never blank** (beta m10-f): a MIDI clip draws a **mini note map** — one small rounded tint pill per note, pitch mapped high-at-top across the clip height (higher note nearer the top), the beat→x/pitch→y geometry headless + tested in `DAWAppKit.MIDIMapGeometry` and SHARED by the shared `ClipMIDIMap` view with the dim take-lane note strip so the two never drift (a single-pitch clip has no vertical span, so its notes land at the bottom — the take-lane idiom; violet flows in via the tint when the clip is AI); an audio clip whose peaks are still loading off-main (or whose file is unreadable) shows a **dim flat center line** so it never reads blank while the waveform arrives (minimal on purpose — the shimmer stays reserved for "stretch working"). Both previews render in **Simple and Pro** (content is not edit chrome) and sit in the same overlay slot as the waveform, under the fade/grip decorations. Every edit routes through one of the five store clip methods, so undo/coalescing come free and mid-play gain/fade changes stay seamless. **Density**: the whole arrange surface is ONE Simple/Pro panel (`TimelineLanesView.panelID` = `"arrange"`, the shared `SimpleProToggle` sits top-right in the Arrange toolbar) — **Simple** = see clips, drag the body to MOVE, and play on a **Bar-locked grid** (an edge/corner drag moves the clip too, no dead hit-zone), with the snap picker and all trim/fade/split/gain/stretch chrome + gestures suppressed; **Pro** reveals the full clip-edit interaction layer plus the snap-resolution picker (rendered beside the chip, Pro only). The Bar lock is the pure, tested `DAWAppKit.ClipSnap.effective(density:picked:)` (it never mutates the picked resolution, so flipping back to Pro restores it — the piano-roll `effectiveSnap` idiom). Automation rows and take lanes are density-unaffected (their comps keep the raw picked snap).
- **Rubber band (marquee) selection** (arrange, m23-g3): dragging on EMPTY timeline space sweeps a **translucent cyan band with a thin bright edge and an earned glow** (cyan = active state; the band exists only while the gesture is live, so it never violates "never glow static chrome"), and every clip it TOUCHES — overlap, not containment — becomes selected as the band grows and shrinks. Shift/⌘ unions onto the pre-drag selection; the SAME chord table a click uses (`ArrangeClickIntent`), so a modifier means one thing on this surface. **Selecting is not opening**: a band never adopts a focus clip, so it never opens the piano roll on a clip the user did not click — a band has no anchor clip, and applying live would otherwise flicker the editor from clip to clip mid-sweep. It arms only past a 4 pt slop (`ArrangeMarquee.dragSlop`, the ruler's `loopClickSlop` value and reasoning) so a click still seeks and a double-click still creates; it is declared `.simultaneousGesture` precisely so the surface's two tap counts keep their events. The geometry is one headless home — `DAWAppKit.ArrangeMarquee` — which takes the RESOLVED lane bands as input and cannot express a row pitch: **the arrange ladder is NON-UNIFORM** (an expanded automation row adds 64 pt, `rowHeight` is user-adjustable), so `floor(y / rowHeight)` is right for every default project and wrong for any real one.
- **Empty-lane hint — A LANE MUST NEVER PROMISE NOTHING** (arrange, m23-v). Every instrument lane with **zero clips** carries a dim SF Pro line at its left edge, vertically centred in the clip row: **"Double-click to add a clip"** in `textFaint` (the measured placeholder/decorative floor — a hint is exactly what that token exists for; reach for the token, never an ad-hoc `.opacity()` on a brighter one), **no glow, no accent, never cyan and never violet**, `.allowsHitTesting(false)` — which is load-bearing and not tidiness, because a hit-testable label would swallow the very double-click it advertises. It is drawn as lane CONTENT (the `ClipMIDIMap` note-map slot), so it renders in **Simple and Pro alike** and sits under the ghost line, the playhead and the refusal bubble.
  - **ALWAYS while the lane is empty, never hover-gated.** The complaint this answers is *"a new track leaves no affordance to start writing notes"* — a LOOKING failure, not a hovering one. A hint you must already be pointing at is only marginally more discoverable than the invisible gesture it advertises, and it is invisible to exactly the user who filed it. Corollary: it is **not pointer state** and must never ride the m17-c pointer seam, which reports null in precisely the resting state the hint exists for.
  - **CONTENT-KEYED ONLY.** `Track.clips.isEmpty` — any clip anywhere on the lane, not "no clip in the visible window" (a lane scrolled away from its only clip is a scroll problem, not an empty-state one, and a viewport-relative rule would blink the hint on and off as you scrolled). It reads no transport state: a track added while the transport is rolling or recording still has no clips and still looks inert, so it still gets the hint. That is structural, not promised — `DAWAppKit.ArrangeEmptyLaneHints.hints(for:)` takes `[Track]` and nothing else.
  - **NEVER ON A LANE THAT WOULD REFUSE.** Audio and bus lanes get silence, because that is where the double-click legitimately throws `midiClipsRequireInstrumentTrack` — **advertising an action that will refuse is worse than saying nothing**. Eligibility is `Track.canHoldMIDIClips` (DAWCore), the ONE home the store's two MIDI-clip guards read, so the affordance and the refusal are the same rule rather than two expressions that agree today. It is deliberately NOT merged with `canExportMIDI`, an identical expression for a different question (the m23-m3c reasoning).
  - **Its Explain card is `.arrangePlayhead`, shared — not a new id.** That card is anchored on the pointer surface the hint sits over, and its body already teaches this exact gesture; a second entry would violate the near-identical-copy rule AND could never be hovered, since the hint must not hit-test. **A non-interactive affordance borrows the card of the surface it explains.**
  - **The echo is reported BY THE DRAWING LAYER** (`debug.arrangePointer` → `emptyLaneHints` + `emptyLaneHintSeq`, debug tier, zero wire surface): the hint set is composed once, the `ForEach` draws that array and the reporter announces that array, both attached to the same layer — so removing the layer removes the reporter with it. Mutation-measured (m23-v): a build that keeps the value and the report but draws nothing leaves **every headless test and every echo leg green** and reddens only the `debug.captureUI` pixel legs. That is the m23-m3b class, and it is why a hint like this ships with a pixel leg or it does not ship.
- **Header-click acknowledgement — A CLICK THAT CHANGES WHAT THE NEXT KEYSTROKE DOES MUST NEVER DRAW NOTHING** (arrange sidebar, m23-an). Clicking a track header selects that track's clips, and the selection is rendered *entirely* as clip blocks going selected — so on a track with **no clips** the click paints nothing at all. It is not inert, which is the whole problem: measured live, a ⇧ click on a zero-clip header bumps the arrange key-focus nonce **and** flips `activeEditorSurface` from `pianoRoll` to `arrange`, silently retargeting ⌘+/⌘−/⌘0 and moving where DELETE lands. The row therefore gets a brief word. **Do NOT "fix" this by removing the side effects** — they are the reason feedback is owed, and removing them breaks the zoom routing and the DELETE path.
  - **The predicate is two terms and it is the ONE home `DAWAppKit.ArrangeTrackClickFeedback`**: *acknowledge iff the track has NO clips **and** the selection did not change.* Fitted to six measured rows, not reasoned: ⇧ on a populated header (loud), ⇧ on an empty one (silent — the filed case), a plain click on an empty header that **clears a real selection and closes the piano roll** (the loudest thing on this surface — must stay silent), a plain click on an empty header over an already-empty selection (**equally silent, and its effect is `.replace`, not `.noClips` — the defect spans two branches, not one**), and a repeated plain click on a populated header (nothing changed, but three blocks are visibly selected — which is why "did the selection change?" alone is the wrong rule).
  - **It is NEUTRAL, and that is a decision, not an omission.** Nothing was refused and nothing was destroyed, so it must not borrow the app's refusal register — **amber is what `ArrangeRefusalBubble` and the piano roll's blocked bar-op wear to say "the edit did not happen"**, and using it here would teach the user that an ordinary click was an error. Cyan is playback/active, green is success (nothing succeeded — nothing *happened*), violet is AI-only. None of the five is honest, so it takes none of them: a dark raised-glass chip (`panelRaised` + hairline + a soft cast shadow), SF Pro (prose, never SF Mono), `textSecondary` ink, **no glow** — the marker-flag and empty-lane-hint precedents. Its salience is **motion**, not colour (0.15 s in, 0.3 s out), which is also the honest signal for something about to leave.
  - **Transient, and it must never read as selection state.** Three seconds, model-owned (`AppModel.trackClickAck`, the auto-clearing `ArrangeSplitRefusal` shape) — never row `@State`, because the staging seam drives the same `AppModel.clickTrack` the row tap does and a row-local flag would light for the mouse and stay dark for the seam. It is drawn **beside** the row, never as a fill or border **on** it, and one careless `.background(isSelected …)` on a header row is how a track-valued *selection* would arrive by accident. A click that *does* select something clears any standing word, so it can never outlive its condition. **⚠️ AMENDED AT m25-l-1:** this clause used to rest on `ArrangeTrackSelection`'s prohibition — *"a track as a distinct selectable object ships only on the user's word; do not add it on the way past"* — and **the user has since given that word**, so the row now carries exactly one persistent mark (the active-track rail below). The rule that survives is the narrower and original one: **this chip** must never read as state, and the two marks must stay unconfusable — transient/neutral/prose/trailing versus persistent/cyan/wordless/leading. What is still forbidden is a track that a *verb* acts on as a member.
  - **⚠️ IT IS A CHILD OF THE ROW IT NAMES — `row.overlay(alignment: .trailing)`, never a positioned overlay on the row stack.** This one was built wrong first and the mistake is the rule's whole justification. Build 1 hung the chip 2 pt below the clicked row's bottom edge, borrowing `dropIndicator`'s geometry off the measured `TrackRowLadder`. **That geometry is right for a drop indicator, which is a *line* at a boundary and belongs to neither neighbour, and wrong for a chip, which has a body.** With `VStack(spacing: 6)` and a ~21 pt chip, measured at 2× from a real capture, the body landed at y 298.5…319.5 pt while the *next* row's band was 302.5…336.5 pt: the sentence naming track *i* was painted across track *i+1*'s row, over its icon and the top of its name. **The model named the right track and the pixels blamed an innocent one — the m23-am defect exactly, in the one feature whose entire purpose is saying which row stayed silent — and every headless test, every echo leg and `trackClickAckTrackId` itself stayed green throughout.** Hanging it off `row` is not merely a better offset: the chip is a *child* of the row it describes, so "drawn on the wrong row" stops being expressible — no index lookup, no ladder read, no arithmetic to get wrong (the `ArrangeDropSnap` `fileprivate init` principle: make the inconsistent state unrepresentable rather than test for it). Three things fall out free — it cannot be clipped away on the **last** row (the old geometry drew outside the row stack, and a newly added track lands last with no clips, the likeliest way a user meets this at all), it rides correctly during a reorder drag where the ladder holds un-parted positions, and `alignment: .trailing` centres it on any row height in the 24…64 pt range with no constant to drift.
  - **Trailing edge, because the NAME is the row's identity.** The chip covers the automation button and M/S/R for three seconds; that is a deliberate trade, and it is occlusion *without* interaction loss (`.allowsHitTesting(false)` — the controls under it still take a click). Attribution has to be readable at a glance, and it is the track name that makes it readable.
  - **The copy carries NO call to action**, and that is deliberate: **"No clips to select"**. It read *"This track has no clips to select."* while it hung between two rows, where "this track" was doing real work; drawn **inside** the row the deixis is free — the row's own name is right there — so what remains is only the part that carries information, and the shorter string is what lets it sit at the trailing edge at the 250 pt sidebar floor without reaching that name. **A chip that has to name its owner is a chip in the wrong place.** The obvious addition — "double-click the lane to add one" — is already the empty-lane hint's sentence, and it would be **wrong on an audio or bus track**, where that double-click legitimately refuses. This word appears on every kind of track, so it says only what is true everywhere. It is pinned as a `static let` in `TrackListView` (the `deleteBarBlockedReason` idiom — DAWAppKit returns a *verdict*, the view owns wording, placement and register), and `scripts/gates/m23an-header-feedback.mjs` reads it out of that source and asserts it matches this document verbatim.
  - **It ships with pixel legs that read POSITION, not just presence** — per the empty-lane hint's law, and then one step past it, because presence is what was green while the chip sat on the wrong row. The gate measures a row's band the only honest way (**toggle its mute and see which pixels move** — never computed from `rowHeight`, which is user-adjustable and would agree with the layout only by luck) and asserts the chip's ink falls **in the clicked row's band and not in its neighbour's**. *A gate that proves a hint appeared has not proved it appeared on the right thing.* Alongside: the verdict is echoed on `debug.arrangeSelection` (`trackClickAck` / `trackClickAckTrackId`, debug tier, zero wire growth) **and** the gate proves ink — a resting frame captured after one click has expired, two frames captured while the word stands that differ from it, and a frame after expiry that is byte-identical to rest again (which is also the pixel proof that nothing persistent was left on the row).
- **The ACTIVE TRACK — "you are here", and it must be VISIBLE** (arrange sidebar, m25-l-1). The arrange has a cursor: the track the next implicit action targets. It is worn as a **3 pt cyan bar on the leading edge of the track card**, full card height (takes and automation sections included — it marks the *track*, not the header row), corners cut by the card's own `clipShape`, and `.allowsHitTesting(false)` so it can never eat a click meant for the row. **Cyan because cyan is the accent system's "playback/position/*active state*"** and an accent is earned by state (Rule 3) — this is the arrange's active state, so it is the honest token rather than a borrowed one. **No glow**: "never glow static chrome", and this mark is persistent by design. The drag lift keeps the glowing cyan *rim* as its own earned, momentary treatment, so a picked-up row and an active row never read the same; a **rail** rather than a border or a fill also keeps the card's stroke free, which is already spoken for (dragging → cyan, AI-generated → violet, else hairline).
  - **⚠️ A CURSOR IS NOT A SELECTION, and the whole design rests on the distinction.** A selection is *what a verb acts on*; the active track is *where the next thing goes* — the arrange's insertion point. It is **not** a member of `ArrangeSelection.ids`, **no verb reads it**, and group DELETE still removes exactly `ids`. That is what lets this ship without reopening what `ArrangeTrackSelection`'s banner closed: the still-forbidden thing is a track a destructive verb would act on as a member.
  - **It is a live READOUT of the resolution rule, never a second opinion about it.** The rail draws on `AppModel.activeTrackID`, which is `ArrangeActiveTrack.resolve(...)` — the *same* property the paste target reads. One home, two inputs at documented precedence: an explicitly clicked header wins, else the track owning the focused clip, else nothing. Fit is judged **per note**, so a run of eighths can name `C4` and not `C#4` — the names are different lengths and the rule is honest about it, which is the arrange clip label's shipped behaviour one surface over ("a name label when width allows"), chosen over a uniform worst-case-width rule that buys tidiness with a whole tier of ordinary material. **DUAL INK, PER PILL** — the gutter's law applied to the app's OTHER variable-luminance surface, and a harder case: a key is one of two fixed tones, while a pill sweeps continuously with velocity (fill 0.45…0.95) across two tints. The polarity is picked from what THAT pill composites to over THAT row (a black-key lane is 22 % darker and it moves the answer), and the two inks are **pure black and pure white**, which is a measurement rather than a taste: a mid-luminance object cannot be labelled at 4.5:1 by anything softer — `keyLabelOnWhite` peaks at **3.80:1** on a cyan pill at velocity 32, `background` crosses over at 4.41:1, and black/white break even at **4.58:1**, the most any ink pair can promise. So this surface clears Rule 5 by ~2 %, not comfortably; do not "harmonise" these inks with the text hierarchy. **A FIXED ink is not an option, measured off real renders with a positive control (white-on-black 21.00:1 in the same pass)**: dark ink alone fails every violet note under ~v60 (2.8–4.1:1 — most soft AI-generated material, i.e. exactly the content violet exists to mark), light ink alone fails cyan from ~v20 up, and the two tints do not even flip at the same velocity (cyan ≈ 8, violet ≈ 56), so no velocity constant serves both either. **Ghost pills take no name**: latent data draws as a flat dim core with no bloom (m19-g) and a crisp name would be the brightest thing on a deliberately inert block; a partially-overhanging note still gets exactly one, on its lit body. Snap resolutions read musically: Off / Bar / Beat / 1/8 / 1/8T / 1/16 / 1/16T / 1/32 / 1/64 (default Beat; m21-c added the triplets — 1/8T = 1/3 beat, 1/16T = 1/6 beat — and the 1/32–1/64 fines, matching `QuantizeModel.grids` so snap and quantize never diverge). **Grid density adapts to zoom, never forks** (the arrange rule): bar (`gridEmphasis`) + beat (`hairline`) lines always draw; SUB-beat division hairlines **fade linearly between 4 and 8 pt spacing** (`PianoRollZoom.subBeatLineAlpha`) so a 1/64 grid appears only when zoomed in enough to be useful — never visual soup, never a pop. A note's **resize floor is ONE grid step of the current snap** (snap off → the store's own `MIDINote.minLengthBeats`) — the ADD default (`defaultLength`, one cell / 1 beat off-grid) is a different number on purpose (m21-c untangled the conflation so AI-authored short notes are editable, not just viewable). - **Per-insert spectrum — the PRE-FADER / POST-FADER LABELLING LAW** (m23-r3): a track EQ card's green fill and the master EQ card's green fill are **different measurements wearing identical ink**, and the app says so in words. Because `.task(id:)`'s cancellation is not ordered before the next task's start, the app-side arm slot carries a **generation token**: a release only bites while it still holds the current token, so a cancelled task can never disarm a tap a newer task just took (arm A → B → back to A). - **Instrument frequency guide — SOFTNESS MUST SURVIVE THE TRIP TO PIXELS** (m23-o2). A confident-looking bracket over a waveform is a strong claim, and six of the table's thirteen rows are softly sourced: three **ADMISSION-DOUBTFUL** (`kick`/`snare`/`tom` — a drum's pitch is a TUNING CHOICE from a practice source) and three **FILTER-WEAK** (`piano`/`rideCymbal`/`crashCymbal` — a tier-C or class-level corner). Two rules follow. **(1) Softness is a FIELD, never a prose scrape.** m23-o1 disclosed it only inside the `rationale`/`explanation` strings, which is right for the copilot and unreadable by a drawing layer — and the marker is not even uniform: `SOURCE CAVEAT:` appears in **four** strings for **six** soft facts, so a UI grepping for it would have drawn two soft claims as firm ones. - **Instrument frequency guide — the FOUR states, and never a defaulted range** (m23-o2). `.notApplicable` (master/bus — no instrument identity is possible, so **draw nothing at all**, not an empty state explaining a question nobody asked); `.unknown` (a track that could be identified and is not YET — the honest empty state, carrying a remedy **the user can actually perform in this app**); `.drumKit` (a GM percussion track must NOT pick a representative piece — a kick and a hi-hat are three octaves apart); `.family`. - **A GUIDE THAT CANNOT REACH ITS BEST ROWS IS AN HONEST COST, NOT A BUG TO PAPER OVER** (m23-o2). The bass enhancer is sold — correctly — as *“makes bass audible on small speakers”*, which is a claim about hearing something that is already there. What it does is manufacture 2nd/3rd/4th partials from the sub-crossover content and inject them above the corner, so the listener infers a fundamental the speaker never reproduced. Both sentences are true; only one is flattering. **The card carries both, and the unflattering one leads.** **The criterion is the GAP between the promise and the mechanism — it is not a tax on generating new content**, and getting that line right is what stops this becoming a badge on every effect. `saturator`, `reverb` and `chorus` all create material the source did not contain, and none of them owes a note, because nothing in this app tells a user they are *revealing* anything: DRIVE says it distorts. - **A CONTROL LABEL FROM A CLOSED VOCABULARY IS NOT A SOFT NAME** (m23-s, 2026-07-29 — the classification half of the m22-g law below, which m22-e got wrong). m22-g says a shared control component pins its own width and **a control label never truncates**, while keeping exactly one soft name truncating beside it. Applying it needs a rule for deciding which is which, and the rule is: **a label drawn from a CLOSED VOCABULARY the app authors is a control label and pins its width; a string the USER or a PLUGIN supplies is soft data and truncates, tail.** `MixerFormat.effectDisplayName` returns ten authored strings for the built-in effect kinds and arbitrary vendor text only for `.audioUnit`, so a mixer insert row draws a PINNED name for a built-in and a TRUNCATING one for an AU. m22-e classified all of them as soft ("the soft insert name, which truncates first") and the mixer shipped `Lim…`, `Compr…` and `Bass Enh…` on channel strips at the DEFAULT window — not just under GR bars, and not just at small windows. **The pin is only half the fix, and shipping it alone would have been worse than the bug**: a `fixedSize` label that does not fit does not truncate, it OVERFLOWS, and the strip's `clipShape` then cuts it mid-glyph with no ellipsis — silent, and invisible to any "is there an ellipsis" check. - **Step sequencer — ONE pane, TWO editors, ONE note store** (m23-cq-1). The clip editor pane carries a **NOTES | STEPS** chip pair (the house segmented idiom, active half cyan-lit — the density chip's twin, the arrange S/M/L cluster's cousin), and STEPS swaps the note grid for a **drum-machine grid**: one row per pitch, one column per step, **click an empty box to place a hit and click a lit box to take it away**. All of it — the lane set, the step↔beat mapping, hit-testing, the toggle semantics — is headless in `DAWAppKit.StepSequencerGeometry` / `StepSequencerLanes` / `StepSequencerEdit`; the view holds one Canvas and one gesture.

The app is sitting on an undiagnosed keyboard-routing report (m23-cf: a bare DELETE reported dead on notes and clips), and a second keyboard-driven editor stacked on an unexplained routing failure compounds it. Click-to-toggle needs no key at all, which INVERTS the risk: the sequencer is a working note-DELETION route that does not depend on the broken key. **A shortcut added here re-acquires exactly the risk this scoping removed, and must re-derive the m23-cf question first.** The pointer says the same thing: a cell is the place/paint family (`CursorAffordance.stepCell` → crosshair — you author by position; nothing here can be picked up), and the SAME crosshair covers a lit box, because the vocabulary has one shape for "act at this position".

"Is this a drum kit" is asked of `SMFProjectExporter.isDrumKit` — the app's ONE predicate, made `public` for this call rather than re-expressed in the UI layer — and the resolve is one pure function, `ClipEditorModePolicy.resolve(override:isDrumKit:)`, which never mutates the pick (the `ClipSnap.effective` shape, so flipping back restores it). The mode is **session state on `AppModel`, never persisted and never project data**: every sticky dimension is a leak class that changes a later gate's verdict (m23-be/bf/bg), and it must survive the `.id(clip.id)` rebuild a clip switch causes, because the workflow is several drum clips in a row.

Two modes of one pane over one clip must not flip the vertical axis under the user's hand at the moment they click the chip. The GM percussion map ascends kick → snare → hats → toms → cymbals, so descending pitch also lands the kit in conventional drum-machine order with the kick at the bottom, for free and with no special case. **Drum lane names are read off the GM percussion key map** (`InstrumentFamilyResolver.percussionNotes` — "Bass Drum 1", "Acoustic Snare"), never hardcoded and never invented: a note the v1 table does not cover takes its scientific pitch name (`Fundamental.noteName`, the repo's one note-name home) rather than a plausible label. A melodic clip gets a two-octave window around middle C, where the roll opens. **EVERY pitch present in the clip gets a lane, whatever the base set says** — a note the grid cannot show is a note the grid cannot delete, and the toggle is this surface's only deletion path, so the union makes "every note is reachable" structural rather than promised. The same reasoning extends the COLUMN count past the clip end to cover a stranded onset (the `PianoRollModel.contentWidth` rule).
  - **The grid reuses the app's ONE snap vocabulary** (`SnapResolution`) minus `off`, which names the absence of the thing this surface is made of; **Simple locks it to 1/16 and hides the STEP picker, Pro honours the pick** — that is a genuine density difference, so the panel's SIMPLE/PRO chip stays honest rather than becoming the do-nothing toggle this document forbids. A lit box carries the note's **velocity as fill opacity with the roll's own curve** and earns the glow recipe (a hit is content and state, never static chrome); a box past the clip end takes the **m19-g ghost** — flat dim core, no bloom, velocity no longer modulating it — over the same 0.28 shade and `gridEmphasis` boundary hairline the roll's three bands draw. **Violet whenever the clip is AI-touched**, because it is the roll's own `noteColor`: two surfaces over one note must not disagree about colour. The round trip that IS exact — toggle a cell on, then off, and the clip's notes return to their original content, compared through the store's own canonical order — is pinned by a test, and so is each lossy case. **Undo granularity is the funnel's, and was MEASURED rather than asserted:** `setClipNotes` journals under the per-clip key `clip.notes:<uuid>`, so a burst of fast toggles folds into ONE "Edit Notes" entry (`UndoJournal`'s 800 ms sliding window) — a run of clicks undoes as one gesture, exactly as a run of piano-roll note edits does. ## Panel splitters

The arrange workspace is **adjustable** (beta item m10-d): three dimensions resize by dragging, each persisted so a shaped layout survives relaunch. **Sidebar width** (drag the vertical splitter between the track list and the timeline, clamped 250–420 pt), **bottom-editor height** (drag the horizontal splitter on the editor's top edge, stored as a FRACTION of window height, clamped 0.30–0.55), and the **global track-row height** (drag the bottom edge of any track header, clamped 24–64 pt). Row height is ONE global value, not per-track: the sidebar headers and the timeline lanes read the SAME `PanelLayoutStore.rowHeight` in the same expression, so they stay pixel-aligned at every size (only the base clip lane scales — the automation row and take sub-rows keep their own constants and compose on top). Layout is an app-side sticky **PREFERENCE**, never project data — persisted as `panelLayout.<dimension>` in UserDefaults, never written into the project file (the density precedent). **The clamp ranges are conservative on purpose**: the reachable extremes must not visibly break at the window the app runs at. The sidebar min (250) is the track-header row's measured intrinsic floor (the fixed-width meter + M/S/A chips don't priority-shrink yet); the editor max (0.55) keeps the app header + arrange chrome + transport visible at the height the app opens at — and **stays 0.55 even now that the editor can be maximized**, because maximize is a mode that suspends the clamp at render time rather than a wider clamp (see the maximize paragraphs below).

## Window floor + shared-scroll arrange

**The floor holds under the m25-b-1 maximized editor, and that was checked rather than assumed** — `minHeight` is DERIVED from the 0.55 ceiling, so a mode that suspends the ceiling could have invalidated it. It does not, because the maximized height reserves `fixedChromeHeight` in POINTS before dividing, so the leftover is the reserve at every window height; the swept assertion and a negative control (a constant 0.92 fraction, which DOES break the floor) are in `EditorMaximizeTests`. ⚠️ Found while measuring for it: `WindowFloor.timelineSliverMinHeight`'s comment says "the 42 pt ruler" and **the pinned ruler block measures 80 pt** — the prose predates the loop band / marker lane / tempo lane joining it. The constant is deliberately NOT moved (that would move the shipped window floor); the staleness is recorded in the source so nobody derives a new number from it.

The window itself has a **measured minimum size** (beta item m10-j): the smallest window at which ALL fixed chrome stays visible and usable — the app header row, the arrange toolbar, a usable timeline sliver (the ruler + a row or two), the bottom editor at its max fraction when open, and the transport bar. The numbers are **measured, not guessed** (the m10-d law): each chrome row is rendered via `NSHostingView.fittingSize` at the app's real fonts/paddings and the floor derived from those intrinsics — **width 1208 pt** (bound by the Pro transport bar's measured 1183 pt inside the window's 24 pt outer padding; the transport is the widest fixed chrome and is present in both workspaces) and **height 640 pt** (derived so the editor open at its max 0.55 fraction still leaves the fixed chrome ≈189 pt + a ≳96 pt timeline sliver visible). The floor + clamp math is headless + tested in `DAWAppKit.WindowFloor`; the window enforces it via the SwiftUI root `.frame(minWidth:minHeight:)` AND the NSWindow `contentMinSize` (belt-and-suspenders), opens at a comfortable `.defaultSize` (1440×900), and `debug.windowFrame {width?, height?}` stages/echoes the window content size for captures/E2E (app-level, debug tier — off `allCommands`/MCP, the `debug.panelLayout` precedent; no-param call echoes the current frame, a size request clamps to the floor keeping the top-left fixed).

The arrange **track area scrolls as ONE unit** rather than pushing chrome off-window when content exceeds the viewport: the sidebar track rows and the timeline lanes live inside a **single shared vertical `ScrollView`** owning both columns (one HStack), so there is exactly one scroll position and the two columns can **never desync** — the structurally safer choice over synchronizing two offsets. Rows stay pixel-locked to lanes (both read `PanelLayoutStore.rowHeight`). The timeline's own **horizontal** scroll (ruler + lanes) nests inside. **The ruler block — the bar ruler, loop band, marker lane, tempo lane, and the TRACKS header — PINS ABOVE the shared vertical scroll (m13-g, audit F7)**, staying visible however deep you scroll, while the rows + lanes scroll under it. Pinning it as a **sibling above the one shared `ScrollView`** (never a second scroll) preserves the no-desync invariant — there is still exactly ONE vertical scroll owning both columns. The pinned ruler stays HORIZONTALLY synced with the lanes: the scrolling `.lanes` timeline reports its horizontal offset up through a `PreferenceKey` (`ArrangeHOffsetKey`) and the pinned `.ruler` timeline mirrors it (`offset(x: -h)`), so bar lines stay aligned across the seam. One `TimelineLanesView` renders both — an `ArrangeContent` mode (`.ruler` / `.lanes`) selects the ruler-only vs lanes-only body, so they share geometry (contentWidth / beat scale) by construction. The pinned block is fixed to the ruler height (`.frame(height: rulerHeight)`) — load-bearing: a spacer with no height constraint is vertically greedy, which would split the VStack ~50/50 and float the ruler mid-panel. Row 0 and lane 0 both anchor at the scroll's top (the ruler is pinned separately, so the lanes carry NO ruler inset). `debug.arrangeScroll {trackId?, index?, bottom?, reset?}` jumps the shared scroll to a target row (a nonce, not the id, so a repeat still fires) so a capture can frame a deep session with the block pinned. A `minHeight = viewport` on the shared content keeps the two glass panels full-height when the content is short. The Sketchpad/ClipFix side panels and the bottom piano-roll editor stay OUTSIDE the shared scroll at full height (the m10-e scrub strip is unaffected). On macOS, wheel-driven scrolling doesn't conflict with the click-drag splitters inside the scroll (the row-height grabber already lives inside a scroll). With the floor + shared scroll in place, the m10-d clamp ranges hold at every reachable value — a genuinely small window now scrolls instead of overflowing.

**Maximizing the note editor is a MODE THAT SUSPENDS THE CLAMP, never a wider clamp** (m25-b-1). The 0.55 ceiling exists so that *every value a drag can reach* keeps the app header, arrange chrome and transport visible; widening the range to serve one big-editor case would have degraded the ordinary resize for it, and would have invalidated the window floor that is DERIVED from that ceiling. So the editor gets a persisted `panelLayout.editorMaximized` flag (default OFF — a mode that collapses the arrange must be asked for, the `followPlayhead` rationale), and while it is set the pane is laid out at `EditorMaximize.effectiveFraction` instead. **The maximized height is COMPUTED from the live window height, never a constant fraction**: the fixed chrome is reserved in POINTS (`WindowFloor.fixedChromeHeight` + the arrange sliver) and the fraction falls out of the division, so the chrome fits at 640 pt and at 2160 pt alike — a constant 0.92 would leave 51 pt for 189 pt of chrome at the floor, which is exactly the m10-j overflow, and that negative control is a test. A floor for the mode (never below the ordinary 0.55) means maximizing can never render *smaller* than dragging.

**Restore returns to the user's own height because maximize NEVER WRITES `editorFraction`.** The mode is a render-time override, so the dragged value sits untouched in its own slot and leaving the mode simply drops the override — no "previous fraction" stash, and therefore no question about what to do when a stash and the live value disagree. A test pins that not one write reaches the fraction key while the mode is toggled.

**The arrange stays MOUNTED at its pinned ruler block, never unmounted.** Removing it would silently reset live view state the user did not ask to lose (the arrange horizontal scroll offset, the reported lanes viewport width, follow's runtime, the arrange key-focus scope) and rebuild it on restore; collapsing it to zero would let the block — which is `.frame(height: rulerHeight)`-pinned and does not shrink — draw on top of the editor. So at maximum the arrange degrades to exactly the strip m13-g already promises never scrolls away, and the user keeps a bar ruler for position context. The row is *hard-pinned* to that height rather than left to compress, because SwiftUI does not reliably squeeze a flexible child to exactly the leftover and an overflow is invisible to every headless gate here.

**A mode that fills the window ships with TWO ways out, and a third by reflex** (Rule 6): the header toggle, the **Escape** key, and dragging the splitter (a manual resize is a request for a manual height, so it leaves the mode and resumes the clamped drag from where the splitter visually is). Escape has TWO mounts — the roll's own and the arrange workspace's key scope — both routing to ONE app-side decision (`AppModel.handleEditorEscape`), the m23-cf lesson applied before it had to be paid for twice: focus arbitration in this tree was *measured* to be a coin flip, so no key's meaning may depend on who holds focus. The decision SETS rather than toggles (a double-delivered press is a no-op, never a re-maximize) and is claimed **only while maximized** — outside the mode it consumes nothing, so the rename fields' Escape is untouched. A modal on screen or a live rename field each close the exit; Escape means "cancel the thing in front of you" first. The toggle itself is a 22×22 icon square in the `closeButton` grammar, seated beside CLOSE: neutral `textDim` at rest, `playback` cyan + fill + glow while maximized with the glyph flipping outward→inward, so the state reads at a glance (Rule 3 — maximized is an *earned* active state). Cyan, never violet: nothing here is AI-touched. The maximized tooltip names the Escape exit, so the second way out is discoverable from the first.

**The note editor carries a VIEWPORT MINIMAP, and it is a corner OVERLAY rather than a reserved band** (m25-b-2). A map of the whole part with a rectangle marking the slice on screen: press anywhere to aim the editor there, drag to slide through it — one rule for both gestures (press and drag both centre on the pointer), because a navigator that behaves differently depending on whether the press landed inside the box makes one gesture mean two things. **The placement is forced by the same budget the maximize mode exists to relieve**: the editor pane is clamped at 0.55 of the window precisely so the arrange and transport survive, and a navigator band across the top would spend ~60 pt of that permanently — four semitone rows of the grid it exists to help you read, making the editor worse at its own job to make it easier to move around in. Floating over the bottom-trailing corner costs zero layout. The cost it *does* have is stated rather than hidden: it covers a ~176 × 56 pt patch of grid, which is why it is **dismissible**, and why the collapsed face is a 22 × 22 chip in the SAME corner rather than a tenth control in a header that already carries nine (the clip name truncates first). Visibility is one more `PanelLayoutStore` slot — **persisted, not view `@State`, for a structural reason**: the roll is mounted `.id(clip.id)`, so a view-local flag would resurrect the map on every clip switch.

**A minimap jump is a MANUAL SCROLL — the user wins, and follow stands down on that surface only.** The precedence question ("what happens when follow is driving and the user grabs the map?") was answered by reusing the policy that already shipped rather than inventing one: the jump is delivered through `FollowPlayheadModel.scrollExternally`, so the offset the scroller reports back is one follow never asked for, `reportOffset` suspends, and the follow chip drops to its PAUSED face — **the stand-down is visible instead of a silent tug-of-war**. ⚠️ **`panelLayout.followPlayhead` is deliberately NOT switched off to achieve this.** That is the single persisted ENABLE the arrange lanes read too; writing it to win a piano-roll gesture would stop follow on a surface the user never touched and would outlive the gesture by every future session. Suspension is per-surface runtime state that re-arms on the next play, which is exactly what "the user wins THIS scroll" should mean and all it should mean. While the transport is stopped nothing is suspended, because nothing was contesting the scroll.

**The map's vertical axis is ABSOLUTE (pitch 0…127), and that is what makes a viewport rectangle possible at all.** `MIDIMapGeometry` — the arrange clip block's note thumbnail — maps pitch SPAN-RELATIVE, which is right for a decoration whose only job is "show where the sound sits" and disqualifying for a navigator on two counts: a viewport rectangle drawn in a span-relative space runs off both ends of the box (the visible pitch window is routinely wider than the note span), and the mapping rescales whenever the span changes, so the map would move under the pointer mid-drag. ⚠️ **The two are not interchangeable and the thumbnail must not be extended into a navigator.** What IS shared is the note rectangle itself: pills are `PianoRollModel.noteRect` — the roll's single producer, the same rect a click hit-tests — projected through one scale, never a second spelling of beat→x. Rectangle and pills are both drawn from the scrollers' **reported** offsets, never a pointer-derived or predicted value, so a clamped scroll at the ends of the part cannot draw the box where the editor is not; the cost is a frame of lag behind the pointer, which is the honest trade. Chrome grammar follows the splitter (Rule 3): the rectangle is neutral at rest and cyan + glow only while dragged — where you are *looking* is not playback, and a second permanent cyan object in a box that already shows the playhead would make both unreadable. The moving parts (rectangle, playhead) are **offset views, never Canvas redraws**, so the note Canvas keeps tick-stable inputs and its pill array is allocated on an edit or a zoom — never per frame. Math + the precedence decision are headless in `DAWAppKit.PianoRollMinimap`; the view is `DAWApp/Components/PianoRollMinimapView`. **Wire: none** — the rule below decided it rather than the question being re-opened; visibility is staged and echoed by `debug.panelLayout {pianoRollMinimap}`.

A splitter is a **dark-glass hairline that earns its accent by state** (Rule 3): a quiet `gridEmphasis` line at rest, cyan-lit + glowing ONLY while hovered or dragging — never violet. Its hit target is ≥ 6 pt even though it draws as a 1 px hairline, so it is easy to grab, and it holds its resize cursor for the whole drag (the m10-c gesture-driven cursor idiom) so the cursor persists when the pointer leaves the strip. A **per-row grabber is idle-invisible** (no rest hairline) so N stacked track rows don't grow N rest lines — it is discovered by the resize cursor + hover glow alone; panel-boundary splitters (sidebar, editor) show their rest hairline.

**Cursor convention — labeled decision**: a height adjustment (editor top edge, track-header bottom edge) shows **`resizeUpDown`**, NOT the open-hand grab the beta note loosely called for. Up/down resize is the macOS-correct glyph for "drag to change a height/amount" (the Pointer-affordances value-adjuster rule); grab means "pick up and move an object," which a divider is not. Width adjustment (sidebar splitter) shows `resizeLeftRight`. **Architecture**: values + clamping are headless in `DAWAppKit.PanelLayoutStore` (`@Observable`, injected `PanelLayoutBacking`, the `PanelDensityStore` precedent — clamping lives in the store so a raw drag delta is tamed); the reusable `DAWApp/Components/PanelSplitter` takes plain drag closures (axis + cumulative translation) so any resizable boundary wires to it. `debug.panelLayout {sidebarWidth?, editorFraction?, rowHeight?, editorMaximized?, …, reset?}` stages the layout for captures/E2E (app-level, debug tier — off `allCommands`/MCP, echoes the post-clamp values). Like pointer feel, adjustable layout is a documented **non-invokable** window preference — no wire command / MCP tool. **This rule is what decided m25-b-1's AND m25-b-2's wire questions rather than either being re-opened** (a corner navigator changes no project byte and no sound either, and an agent that wants to know where the notes are reads `project.snapshot` — where a human happens to be *looking* is not a capability): maximizing changes no project byte and no sound, every one of the eleven `PanelLayoutStore` slots obeys the rule already (`auditionEnabled` decisively so — it gates actual SOUND and still stayed debug-tier), and an `allCommands` entry would have broken the wire-count pins to buy an agent a control over how tall a pane is drawn. The echo carries `editorMaximized` **beside** `editorFraction` on purpose: the two are independent, so one round trip proves the restore contract (maximize → the fraction did not move → un-maximize → it is still the user's).

## Wide windows

The window floor bounds the small end; these rules govern the LARGE end (m18-f — the 1728+-wide and 3456 pt ultra-wide stress states the m17-f sweep filed). The m17-f law ("workspace side panels compress, never overflow") handles shrinking; wide windows have the dual failure — **dead glass**: a content-width surface that stops mid-panel and leaves a void the eye reads as broken rendering.

**The piano-roll grid EXTENDS to the editor viewport — never a dead panel right of the grid.** Every horizontal editor band (note grid, velocity lane, controller canvas) draws at `max(content width, viewport width)` — ONE definition, `PianoRollModel.drawnWidth(content:viewport:)`, all three bands past the shared 54 pt gutter — so each band always reaches the panel's right edge. Honesty is preserved by construction: the playable window still ends at the clip end, because the out-of-clip shade (and the controller strip's m18-e boundary hairline + ghost treatment) marks everything past it as latent — the extension adds SHADED latent grid, never lit "playable" grid, so the m18-e statement "the grid is the playable window" survives as "the LIT grid is the playable window." Creating a note in the extension is deliberately legal: it is the SAME legal-but-latent semantics the m18-e ghost rule recorded for CC points (`setClipNotes` never trims to the clip length; the engine's schedule pass emits only `startBeat < clip length`, strict — verified, `MIDISchedule.buildEvents`; an extension re-lights them, a trim re-window drops them), and editing stays boundary-blind — a possibility that already existed by dragging or resizing a note past the end, so the extension invites nothing new. Anchoring or centering the content was rejected: centering detaches the keyboard gutter from the panel's leading edge (the gutter is the row-identity anchor, the sidebar-column idiom), and a max-content-width panel just relocates the same dead glass this rule exists to kill. Pro precedent: Logic's piano-roll grid always fills its editor viewport.

**The transport readout cluster stays LEFT-ANCHORED at every width — recorded intent, not an oversight.** The transport is ONE instrument cluster: the buttons and the Position/Time readouts describing them read together in a single glance (cockpit — a gauge sits beside its control; the m10-j 340 pt anchor already fixed the readouts' home so chrome changes never move them). At ultra-wide, surplus width accrues to the middle Spacer — between the record/readout cluster pinned left and the status/master cluster pinned right — never between a control and its readout, and never by re-centering: centering at 3456 pt would put ~1300 pt between the play button and the position readout it drives, and controls that drift with window width break muscle memory (the stable-reach rule every pinned 1440-class capture depends on). A workspace's CONTENT may claim wide-window surplus (the piano-roll rule above; arrange lanes and the mixer rack already scroll/fill); fixed CHROME never re-flows for it.

## Pointer affordances

Every drag/resize surface **advertises its controllability by changing the mouse cursor on hover** (beta item m10-c) — a beginner should discover what is adjustable just by moving the pointer, without a manual (Rule 6). Cursors follow ONE convention per control family; pick the family, never hand-code a per-control cursor:

- **Vertical value drags → `resizeUpDown`.** Long-throw faders (master + channel), rotary knobs (pan), velocity stems, the clip-gain chip. A value adjuster keeps its resize cursor for the WHOLE drag — a fader never "grabs" (it is not a movable object, it is a value). Convention chosen over open-hand because up/down resize reads as "drag to change the amount," the most literal cue for a beginner.
- **Horizontal value / resize drags → `resizeLeftRight`.** Clip trim edges, note right-edge resize handles, clip fade-corner grips, the send mini-fader, the ⌥ time-stretch handle. Anything dragged left/right to resize or set a horizontal amount.
- **Movable bodies → `grab` (open hand) at rest, `grabbing` (closed hand) while dragging.** Arrange clip bodies, piano-roll notes, automation breakpoints, the arrange playhead (grab strips over each track's clip band). The hand OPENS on hover and CLOSES for the whole drag, even when the pointer leaves the object's bounds (driven by the gesture, not the hover).
- **Place / paint surfaces → `crosshair`.** Empty automation-lane space (click to add a breakpoint), take-lane comp painting. Distinct from `grab` because you are authoring content by position, not picking up an existing object.
- **Place / move the TRANSPORT POSITION → `verticalBar`** (m25-o) — the app's ONE custom-drawn cursor (`NSCursor.playheadPlace`): a 9 pt cap over a 2.5 pt hairline, white with a hairline dark outline, hot spot on the bar's own x. It is **a miniature of the surface's own playhead handle** (`PianoRollScrubRuler.handleWidth` is that same 9), so the pointer is a picture of the thing it is about to place. Shown while ⌘ is held over the piano-roll note grid, where a ⌘-click seeks the transport to the pointer's snapped beat. **Why a new family and not a borrowed cursor**: the transport position had no family and had already accreted two conventions for the same object — the arrange playhead grab strip took `grab`/`grabbing`, the roll's scrub strip took `resizeLeftRight` — so a third *silent* convention was the one thing the rule above forbids outright. Naming it makes those two visible as **migrations to file, not precedent to copy**. The three stock candidates were each rejected for a reason worth keeping: `iBeam` is the right silhouette and the wrong meaning (the I-beam is reserved for text, one bullet down, and spending it here teaches the pointer to lie), `crosshair` belongs to authoring content by position and is not the *vertical sign* the user asked for, and `resizeLeftRight` reads as "widen this", which is the one thing this gesture cannot do. ⚠️ **It is NEUTRAL, never cyan** — cyan is earned active transport state, and this pointer describes a playhead that does not exist yet; the SHAPE carries the meaning, the COLOR would be a claim. ⚠️ **A modifier-gated affordance must react to the MODIFIER, not just the pointer.** The `hoverCursor` tracking area re-resolves on movement only, so ⌘ going down with the mouse still would change nothing; the surface bumps `hoverCursor(resolve:refresh:)`'s opt-in token instead, and the token is opt-in precisely so overlapping tracking areas elsewhere never start fighting over the cursor. The `NSEvent` flags monitor behind it lives only while the pointer is on the surface and is torn down on hover-exit **and** on view teardown (a local monitor that outlives its view is a leak, and a hover-exit is not guaranteed for a view destroyed under the pointer).
- **Hover ghost line**: a 1 pt `textSecondary` line at 0.35 opacity marking the snapped beat under the pointer — deliberately NO glow (glow is earned by transport state; a hover hint must never be confusable with the cyan playhead). Its x comes from **the same producer the click acts on** — a preview computed by different arithmetic than the action is a preview that lies, and on a snapping surface it lies by up to half a grid cell.
- **Refusal bubble**: when a direct-manipulation gesture is refused, a transient amber bubble carries the store's error VERBATIM — the same words an agent gets over the wire; one vocabulary, human and machine.
  - ⭐⭐ **A REFUSAL IS NOT ALWAYS A THROW, AND THE SILENT ONES ARE THE ONES USERS REPORT** (m25-a-2). Auto-extend refuses to grow a MIDI clip when a ceiling blocks it — the note is still written, the store still returns a clip, nothing throws, and from the moment m25-a shipped until m25-a-2 nothing at all was shown. The user reported exactly that: *"It should warn with signal or something and direct user or give a clue."* **A refusal that the store cannot express as an error still owes the user the bubble**, so the store carries a REPORT CHANNEL beside the throw (`ProjectStore.lastAutoExtendRefusal`) and the same amber component renders it. ⚠️ The one-vocabulary clause above is weaker here and the gap is stated rather than hidden: a non-throwing refusal has no wire echo today, because `clip.setNotes` deliberately does not plumb `extendToCover` at all (`ClipAutoExtend`'s wire decision), so an agent cannot provoke this refusal and therefore cannot be told about it. Filed, not built.
  - ⛔⛔ **NAME THE OBSTACLE, AND FIRST PROVE YOU CAN TELL THE OBSTACLES APART.** The remedies differ — move the neighbouring clip, or place the note nearer — so a bubble that names the wrong one sends the user to do something that cannot work. The rule is therefore a NAMED OUTCOME derived in ONE headless home (`ClipAutoExtend.ExtendOutcome`, switched EXHAUSTIVELY with no `default:`), never re-derived at the view from the same inputs. **The trap that makes this the correctness of the feature rather than a detail**: the underlying helper returned a bare `Double?`, and by far its most common `nil` is *"the notes already fit"* — the ORDINARY case, on essentially every note edit inside a clip. `if result == nil { warn }` would have fired amber on every keystroke, which is far worse than the silence it fixed. **A `default:` clause reintroduces exactly that, and no test catches it, because every fixture anyone writes for a refusal helper is a refusal.** The compiler forcing a human to handle the do-nothing case IS the safety mechanism.
  - **The bubble hangs on the thing it is about.** The shared `ArrangeRefusalBubble` now has three anchors — a refused clip edit over its BLOCK, a refused empty-lane create on the LANE, and a refused auto-extend over the piano roll's NOTE GRID (clearing the scrub ruler band). The piano roll's older bar-ops notice keeps its own trailing 240 pt chrome under the header cluster it explains, deliberately unconverted: it is anchored to a BUTTON, and unifying it would be a visual change to a surface the item that noticed it never examined.
- **Text-editable fields stay the system I-beam** — never override it.

⭐ **A MODIFIER THAT TAKES A GESTURE AWAY MUST TAKE ITS AFFORDANCE AWAY TOO — AND THE ONE RESOLVER IS WHERE THAT HAPPENS** (m25-x). The rule above ("react to the MODIFIER, not just the pointer") is only half of it: making the cursor *re-resolve* on a chord change is worthless if the thing it re-asks is modifier-blind. A surface that resolves "what is under the pointer" from geometry alone, while its press router *also* consults the chord, has two decision layers that can disagree — and they will, silently, the day some other item gives the chord a consequence. That is exactly what happened here: the piano roll's group-scale handle drew its glowing bar and offered its edge-drag cursor under ⌘ for as long as ⌘-click on that band did nothing, and the lie only became visible when ⌘-click gained a meaning (place the transport). **So the chord is an INPUT to the one hover resolver, ranked alongside panel density**, which is the same kind of gate — both answer *is this affordance offered here*, neither answers *what is the geometry*. The test that keeps it honest: **a target survives a chord iff the chord's verb belongs to that target.** ⌘ over a note keeps the note (⌘-press toggles it — still note-scoped); ⌘ over the transport line keeps the line (⌘-click still moves the transport); ⌘ over a group-scale band keeps *nothing group-scoped*, so that target retracts and the resolver falls through to what is genuinely there. ⚠️ **Then delete the now-redundant gate at the press site.** Once the resolver refuses to return a target under a chord, a second `if !chord` on the branch that consumes it is a second source of truth for one rule — the very shape that produced the defect. Keep such a gate only where the resolver deliberately does *not* own the rule, and say so in a comment. ⚠️ **Each consumer passes the chord IT knows, and that is correct**: hover can only know an `NSEvent` flags monitor's state, a press must use the chord it was actually delivered with. Do not "unify" them into one source — feeding a real click from the hover monitor is stale on the first press after the pointer enters with a modifier already down, which reproduces once and gets closed as unreproducible.

**Architecture**: the pure vocabulary and per-surface catalog are headless in `DAWAppKit.CursorKind` / `CursorAffordance` (with `forClipZone` / `forNoteZone` mirroring the geometry classifiers), so the mapping is tested once and every view reads the same contract; DAWApp resolves `CursorKind → NSCursor` in one thin switch and applies it via the `.hoverCursor(_:)` / `.hoverCursor(resolve:)` modifier (`Components/HoverCursor.swift`). The modifier is a transparent, hit-test-through `NSTrackingArea` overlay — it COEXISTS with the Explain hover machinery and the view's own gestures, and it restores the arrow on hover-exit and teardown so a cursor never sticks when a hovered view disappears or a panel opens mid-hover. During a drag the cursor is forced by the gesture's `onChanged`/`onEnded` (not hover) so it holds outside the bounds and returns to the correct rest state on release. Pointer feel is a documented **non-invokable** convention — no wire command / MCP tool (the sp-b pure-view precedent).

## Controller strips

Numeric value readouts always carry their parameter label — "Mod (CC 1) 123", never a bare floating "123"; the number is SF Mono, the label SF Pro (m17-f). A controller strip's drawn trace is data, not chrome — it never earns glow.

**Beyond-clip controller points render as a GHOST — never clipped away, never lit as if they play** (m18-e). A CC point at or past the clip end is store-legal on purpose (`setControllerLane` clamps values and floors beats at 0 but never trims to the clip length — the write boundary never silently drops data) yet **latent**: the engine's schedule pass emits only `beat < clip length` (strict — a point exactly AT the end is silent), and a trim/split re-window drops out-of-window points, so the data persists only through ordinary edits and comes alive when the clip is EXTENDED over it. Both wrong answers were rejected for the same honesty reason: clamping the canvas hides real, editable data (the standing idioms — hover ghost line, refusal bubble, panels compress never overflow — never hide truth), and full-brightness rendering claims the points sound (they don't). So the strip splits at the engine's exact boundary: **in-clip = full neon treatment; beyond-clip = the dim accent core only — no bloom, no glow (inert data earns none, the disabled-automation-lane idiom)** — over the existing out-of-clip shade, with a 1 pt neutral `gridEmphasis` hairline at the clip end so the region reads as a deliberate boundary, not a rendering seam. No new accent colors: the ghost is the lane's own accent, dimmed. **Editing is boundary-blind on purpose**: ghost points hit-test, drag, and delete exactly like lit ones; drag a point across the boundary and its treatment flips live in either direction (no clamp at the clip end — dragging out is legal, the store accepts it). The split math is ONE definition, `ControllerStripModel.playableCount` (engine-honest strict `<`), so the drawn boundary can never drift from what plays.

**Beyond-clip NOTE pills get the same ghost — and a tail crossing the clip end tells the TRUNCATION truth** (m19-g, extending m18-e to the note grid). Engine rule for notes, verified in `MIDISchedule.buildEvents`: a note sounds iff its **onset** is strictly inside `[0, clip length)` — strict `<`, an onset exactly AT the end is latent — and its note-off lands at `min(note end, clip length)`, so **a tail past the clip end is TRUNCATED, never sounded in full**. The pills render exactly that: an onset at/past the boundary ghosts the **whole pill and its VEL stem** (flat dim core — fill 0.35, hairline stroke 0.45, the m18-e ghost-handle ratios; **velocity no longer modulates a ghost's opacity** — latent data reads uniformly inert; no bloom even when selected, though the selection's neutral hairline stroke stays so a selected ghost still reads selected — a hairline is chrome, glow is state); a note **crossing** the boundary draws a **lit body to the clip-end hairline and a ghost tail past it** — the truncation drawn honestly — while its **VEL stem stays fully lit, because the onset velocity genuinely fires**. The split is ONE model definition, `PianoRollModel.playableEndBeat(of:clipLengthBeats:)` (the `playableCount` sibling: `nil` = latent, `min(end, length)` otherwise), called from the Canvas draw sites — never re-derived beat math in a draw closure. The 0.28 out-of-clip shade + 1 pt `gridEmphasis` clip-end hairline now draw in **all three editor bands** (note grid, velocity lane, controller canvas) at the same x — exactly one hairline per band, aligning into a single continuous boundary column (where the clip end lands on a bar line the two same-color lines merge, never a doubled line). Editing stays boundary-blind: ghost pills select, move, resize, and velocity-drag exactly like lit ones, and dragging across the boundary flips treatment live in either direction.

## Musical Typing — playing notes with no hardware (m23-ct)

**The user has no MIDI controller.** Everything in `Sources/DAWEngine/MIDIInput/` was a fully-built subsystem with no door they could reach, and the nearest affordance — the piano roll's ivory gutter — is one mouse pointer (so one note), inside one editor. Musical Typing is the door: **an explicit mode that turns the letter keys into a keyboard, plus an on-screen playable piano across the bottom of the window.**

**THE MODE IS EXPLICIT AND VISIBLY INDICATED — never ambient capture.** A `KEYS` chip in the transport bar's right region turns it on; lit it wears `playback` cyan with the glow recipe (an accent earned by state, Rule 3) and it shows in **both densities** — by Rule 6 a beginner needs a way to play a note more than a pro does. While it is on it claims exactly **21 physical keys** and nothing else: 17 notes (A/W/S/E/D… = C/C♯/D/D♯/E…, Logic's and Live's shared layout, so a user arriving from either already knows it) plus Z/X for octave and C/V for velocity. **Space still plays and stops, ⌫ still deletes, every ⌘ shortcut still works** — the three key sets are disjoint by construction, which is what lets you play along with the transport.

**KEY ROUTING IS A HEADLESS PREDICATE BEHIND ONE `NSEvent` MONITOR, NEVER `.onKeyPress`** — the space bar's and ⌫'s shipped pattern (`TransportKeyRouting`, `DeleteKeyMonitorRouting`), for their measured reason: SwiftUI focus arbitration in this app is a coin flip (m23-al) and `.onKeyPress(.delete)` cannot fire for ⌫ at all (m23-fi). Keys are matched by **virtual key CODE, not character** — a code names a physical position, which is what a keyboard layout is, and character matching is the m23-fi defect. ⚠️ The cost, said out loud: on a non-US layout the positions are right and the **printed legends are not**.

⛔⛔ **GATE THE ONS, NEVER GATE THE OFFS.** A note-on is refused by any of: mode off, unmapped key, a ⌘/⌥/⌃/⇧ chord, a focused text field, a secondary window. **A note-OFF is granted on one condition only — that the pitch is sounding.** Hold a key, click into a rename field, let go: that key-up arrives classified as text-editing, possibly in another window, possibly with ⌘ down, and applying any note-on guard to it strands a note ringing forever. It is `auditionPitches`' own law ("Stopping is ALWAYS allowed… a refusal here would strand a voice"), and it is expressed as a SHAPE — the release path takes no responder, window or modifier argument, so a guard cannot be added to it without changing a signature a test pins.

**A held key auto-repeating is a THIRD outcome, swallowed inert.** Space and ⌫ pass repeats through because they are one-shot commands; a note key repeats ~15×/s and both two-outcome answers are wrong — passing it through types letters into whatever is behind, re-performing it machine-guns the note-on.

**ONE HELD LEDGER, TWO SURFACES.** Typing and clicking write the same ordered set, and the on-screen keyboard lights **what is SOUNDING**, never what is pressed — a key whose voice was stolen, or that was pressed while nothing could sound, is not lit. Above the seam the model speaks presses and releases; **across the seam it is SET-shaped** (`LiveNoteSink.setHeldPitches`), because the live-play path re-asserts the held set on a 500 ms heartbeat and an edge-shaped crossing would make every heartbeat look like a fresh note-on — which, now that the path records, would write the note into the take again on every beat of it.

**A MODE LAMP MUST NEVER READ ON OVER SILENTLY DEAD KEYS.** The indicator renders from a resolved target state, not from the mode flag — no instrument track, wrong track kind, note preview switched off — and each state's line names the FIX rather than the fault. ⚠️ **A running take is deliberately NOT in that list.** It was, while typing could not be captured; the m23-ct join made it sound, so it resolves to a STATUS instead (being captured, or heard-and-discarded) — which is what forces the ordering rule below. The keyboard itself reuses the piano-roll gutter's ivory palette verbatim (the second light surface, see "Foundations"); a lit key fills `playback` and its legend takes the measured `NotePillInk` answer for that composite, never a picked ink.

⛔⛔ **A KEY MONITOR IS INSTALLED APP-WIDE, SO A PANIC PATH IN IT MUST BE GATED ON YOUR OWN STATE.** Musical Typing releases everything when ⌘ engages, and that handler runs on **every ⌘ press in the whole application** — ⌘Z, ⌘S, ⌘C, a few hundred times an hour, with the mode OFF. The release pushes an empty set, and an empty set at a **shared** seam (`auditionPitches`) stops whatever is holding it: the piano roll's gutter key, or a note drag in progress. Unguarded, a ⌘Z during a roll drag cut the roll's own note, through a mode nobody had turned on. **The guard is on the feature's own ledger** (`holdsAnything`) and it does not weaken the rule — when anything IS held, ⌘ still releases all of it. ⚠️ The distinction that decides it: **mode-off, resign-active and record-start are EVENTS and keep the blind unconditional push; a modifier key is not an event, it is a key someone presses all day.** Any monitor-installed handler inherits this — you are running inside every other feature's keystrokes.

⛔ **THE STAGING SEAM AND THE MOUSE MUST ENTER THE SAME FUNCTION, NOT MERELY REACH THE SAME MODEL.** The on-screen keyboard takes its press as an injected closure and the app hands the identical one to `debug.musicalTyping {pointerPitch:}`; the shared function owns the target refresh. Two call sites that each *look* right diverge in what they do FIRST — here, a click can be the first event after a track switch — and a gate driving the seam is then green on a path no human takes (the m23-an class).

⚠️ **A "LAST CALL" FIELD ON A SEAM IS STALE WHENEVER THE CALL DID NOT HAPPEN.** A swallowed auto-repeat never reaches the sink, so the sink's "edges captured by the last call" still holds the previous press's number — and a gate asserting `== 0` after a repeat fails against entirely correct behaviour. **Name these fields for what they are and compare them against a value read BEFORE the call**, or report a monotonic counter instead. This is the same family as the decision-inference trap below: a field that cannot distinguish *nothing happened* from *something happened and the answer was zero*.

⚠️⚠️ **A SEAM MUST REPORT THE DECISION, NOT INFER IT FROM THE SIDE EFFECT.** The seam first derived its verdict label from *"did the monitor swallow the event?"* — but a performed note and a swallowed auto-repeat are **both** swallowed, so it reported `performed` for a repeat that sounded nothing. It was found by a live smoke that **printed** the label instead of asserting a guessed one, and fixed by carrying the predicate's real verdict across. A guessed assertion would have passed. **An instrument that returns something which looks like a valid answer is this codebase's characteristic failure; when you do not know what a field says, measure it before you pin it.**

⭐⭐ **WHAT YOU TYPE IS RECORDED — AND THE SEAM IS WHY THAT COST ONE FILE.** The first version pushed at the audition path, which refuses mid-take by design; the shipped one pushes at `ProjectStore.playLiveNotes`, which sounds the notes *and* feeds the rolling take. Swapping the implementation under `LiveNoteSink` changed **nothing above the seam** — not the controller, not the keyboard, not the key monitor. ⚠️ **The old ceiling comment said in bold that recording was "not a deferral, it is exclusion"; that sentence is dead and is retracted in place rather than deleted, because a stale *"this cannot be done"* is the class that froze four items in this repo for eight days.**

⛔⛔ **AN "IT WORKS" LIGHT MUST READ THE ANSWER THAT CAME BACK, NOT THE REQUEST THAT WENT OUT.** Live play returns whether this call's edges actually reached a capture session, and the surface shows **that**, beside the app's own prediction. The two can legitimately differ — the engine narrows the verdict further (is a take really capturing MIDI, is there a session, is CoreMIDI up) and only it can see the rest. Any indicator that says *"saving"*, *"recording"*, *"connected"* or *"applied"* should be built this way: the request is not evidence.

⛔⛔ **AND THE THIRD STATE IS THE ONE WORTH DESIGNING FOR: IT SOUNDS RIGHT AND IT IS BEING THROWN AWAY.** Captured MIDI fans out to **armed** instrument tracks only, so playing an un-armed track during a take sounds completely normal, looks completely normal, and keeps nothing. **It is deliberately NOT a refusal** — the user asked to hear the track and there is no reason they cannot — so it is modelled as a status the indicator has to *say*, in the destructive red rather than the warning amber: a refusal costs you nothing, this costs you a take. The line names the fix (*"arm this track (R) first"*), and arming while the strip is up refreshes the indicator **without** cutting the note you are holding. ⚠️ Generalise it: **when a state is inaudible, invisible and lossy, the indicator is the entire feature.**

⚠️ **REFUSALS OUTRANK STATUSES IN A STATE RESOLVER, PERMANENTLY.** Splitting one blocking `recording` case into two sounding ones inverted an ordering that had been correct: while every case below `ready` meant silence, any order produced an honest message. The moment one of them SOUNDS, checking it first reports *"everything you play is going into the take"* over keys that are dead. **A lamp that reads ON over silence is the failure the whole type exists to prevent** — so the resolver answers every genuine refusal before it answers any status, and a test pins that order by name.

⚠️ **A NOTE PLAYED IN THE FIRST ~70–300 ms AFTER RECORD IS DROPPED, BY DESIGN, AND THE SURFACE DOES NOT YET SAY SO.** A take's `PlaybackAnchor` is scheduled slightly ahead of the take's start and every pre-anchor note-on is discarded — the same rule that makes count-in work. Measured: a chord struck at t≈0 vanished; a note 120 ms later landed at beat 0.103. **Deliberately not solved here:** the honest cue is a count-in, which needs a transport-clock read this strip specifically does not have (its Canvas mounts no `TimelineView` and takes no clock, by contract). Written down rather than left silent.

## The breath pad — a circular morph controller, and what it established (m28-p7)

The pad is a **big circular knob with a dot that moves between gestures placed around the circle** (the user's own words, and the spec). Eight `EffortPattern`s sit at evenly spaced angles, **index 0 at the TOP and the ring running CLOCKWISE**; the dot's ANGLE picks which two blend and its RADIUS picks how strongly. Everything below generalises to any future morph pad, so it is written as rules rather than as a description of one panel.

- **A gesture control STREAMS only while a gesture is open, and COMMITS once on release.** Preview between `begin` and `end`, one apply at the end, and the apply is **gated on the value having actually MOVED** — `DragGesture(minimumDistance: 0)` makes a plain click a complete gesture with zero translation, so an ungated release spends an undo step and pays an engine rebuild for a stray press. This is `DeferredKnob`'s commit-on-release rule at the scale of a whole gesture; the m25-k warning applies unchanged — *a correct policy at the wrong cadence looks exactly like a correct policy*, and undo coalescing cannot see the difference. **The rate cap has ONE home** (`DAWCore.PadPreviewController`, 30 Hz + change filter); a second throttle in the view layer is a second place for the two to disagree. Dismissing the panel mid-gesture ends the stream and commits NOTHING — a dismissal is not an edit — and a refused preview is printed (`PanelRefusalLine`), never swallowed, because a pad that silently does nothing is indistinguishable from a broken one.
- **The gesture API takes no points.** `beginGesture` / `setDot(angle:radius:)` / `endGesture` is the primitive; the pointer path is a thin adapter over a geometry value type. A mapped hardware knob (m28-knob) holds one gesture open across many value changes with no pointer at all, so that extension adds an adapter rather than a second state machine.
- **Glow is earned by the gesture.** The dot is a plain accent disc at rest and takes the full glow recipe (core + tight shadow + wide faint bloom) only while a gesture is open — the knob-arc rule, one surface over. Its **trail is the DRAG trail**: a fixed-capacity ring buffer written in place, drawn oldest-faintest, cleared on release. Nothing on the pad animates between gestures, so the Canvas redraws on interaction only and needs **no `TimelineView`** — reach for one when a dot PATH (`.orbit`/`.drift`) animates it, and not before.
- **Draw shapes in the Canvas, draw text over it.** `GraphicsContext.resolve(Text:)` builds a resolved text at every draw, so eight pattern names inside the Canvas allocate eight per drag frame. The names are ordinary `Text` views `.position`ed over it — laid out once, only their tint changing.
- ⛔ **A label ring is hit-tested GEOMETRICALLY, never with its own tap gesture.** A tappable `Text` inside the pad's `DragGesture(minimumDistance: 0)` receives BOTH gestures: the drag opens and jumps the dot, the tap parks it again, and **one click spends two undo steps**. The names are `allowsHitTesting(false)` and a `patternHit` band outside the rim resolves the press inside the one gesture — one gesture, one commit path. (Pressing the rim itself must stay an ordinary dot placement, or dragging to the edge would keep snapping.)
- ⛔⛔ **A DRAWN switch, never a stock `Toggle` — and the reason is measured, not stylistic.** A `Toggle(.switch)` rendered through `debug.captureUI`'s window `cacheDisplay` path drew its knob in the **OFF** position while the model was ON: the label, the readout and the gauge beside it all said "enforced" and the switch did not. A control whose picture disagrees with its value is this project's characteristic silent failure, and here it would have been lying about the one setting that overrides what the composer wrote. **Any stock AppKit control inside a surface that must be capturable is suspect until a capture proves it.**
- **The consequence surface is part of the control** (design §9.4). The pad's air budget can quieten a phrase, so the panel draws the report: a horizontal strip with one band per phrase whose height IS the air remaining, amber where it fell below the reserve, a **breath mark** at each detected breath (solid = a breath taken, dashed = a gap too short to breathe in — two marks, because they have opposite fixes), and a plain sentence above it. ⛔ **Tense follows `Report.applied`, everywhere.** The report is computed whether or not enforcement is on, so with the switch off every figure in it is a **counterfactual** and the panel says *would*, never *did*. A gauge that read the constrained notes and ignored `applied` would report an edit that never happened. Amber, never red: the budget cannot silence a note, and a destructive colour would overstate it.
- **The centred-card height law (m26-i) gains a second clause: the budget must see EVERY variable-height block, not only the window.** Measured here: a single fixed-chrome constant was 136 pt light once a warning list and a second warning sentence were on screen, and the dial — the region that is supposed to yield — could not see either, so it sat at full size while the card overflowed. A third one nearly got away: the dot's blend SUMMARY is DAWCore prose that runs two rendered lines to four depending on which gesture is nearest, so the card changed height with the dot's ANGLE. **Stop a block varying rather than predicting it** — the view reserves the measured worst case as a `minHeight` (a minimum, not a fixed frame, so a longer sentence one day wraps and pushes instead of being truncated), and a test pins the library against the string the reservation was measured with.
- **The yield is an ordered CASCADE with every floor declared, and its LAST step is a scroller** (`BreathPadLayout`): the dial gives up every point it has down to its floor → the warnings block sheds → **the card scrolls, with the header and the primary button pinned outside the scroller**. A smaller circle is still a circle; a hidden warning is a silence; and deferred content is still reachable. ⛔ **"It overhangs symmetrically, so nothing clips" is FALSE and was shipped as a pinned number.** A centred card does not overhang into empty space — it overhangs into the screen edge, and the rows it loses are the FIRST and the LAST, which on a panel are dismiss and commit. At the app's own window floor the pad's **WRITE THE SHAPE button was clipped off the bottom of the window**, and every test in the round was green. **Exactly one scroller is live at a time**: while the card fits, the inner block scrolls and is bounded; once the card scrolls, the inner block is given its natural height, because nested vertical scrollers make the inner one a trap for the wheel.
- ⭐⭐ **A CARD WITH A HEIGHT BUDGET REPORTS WHAT IT WAS GIVEN AND WHAT IT DREW.** `fixedChrome` was wrong three times: 372 summed from paddings, 380 pixel-scanned from a capture, **433** measured (**510.5** since m28-knob-ui added the precision knobs and the hardware disclosure — re-measured the same way, never adjusted by an estimated delta). The pixel scan was not merely imprecise, it was *unresolvable* — the card's measured height, the dial's measured diameter and the window's height each implied a different `available`, because a centred card's edges move when EITHER the card or the window changes and a capture cannot tell those apart. The panel now publishes `available` and its drawn height through a preference into its model, and the debug echo states both alongside what the budget PREDICTED; the disagreement becomes a subtraction instead of an argument. ⛔ **The layout must never read its own report back** — a budget that consumed its own measurement converges on whatever it drew last and the discrepancy vanishes into the loop.
- **No violet** (a breath gesture is performance, not generated content) and **no Simple/Pro chip** (the circle, the switch and the button are identical in both densities, and a toggle whose modes coincide is a do-nothing control).
- ⛔⛔ **A BUDGET CONSTANT IS ONE NUMBER, SO THE BLOCK IT DESCRIBES MUST BE ONE HEIGHT — RESERVE THE WORST CASE, DO NOT SAMPLE A STATE** (m28-knob-ui). The hardware section was first measured at **260** in the state it happens to open in: nothing mapped, not listening. But its status sentence has three variants and *the one in the measured state was the longest* (two lines where the others take one), and its FORGET ALL MAPPINGS button appeared only once something was bound. So the sampled state was the state the panel leaves the instant the feature is used, and the error was not even reliably one sign. Reserving the worst case (`hardwareFeedReservation`, the `summaryReservation` idiom) and keeping the destructive button **present-but-disabled** made the section a constant **298.5 pt in every state** — and the honest constant **285**, not 260. ⚠️ **A correctly-measured constant for an incorrectly-varying view is still wrong, and it fails in the state nobody measured.** ⚠️⚠️ **AND THE SCROLL CASCADE HIDES THIS CLASS OF ERROR**: where the block always overflows, everything looks right at every window the developer owns, and the overhang appears only where the card *just* fits — i.e. on someone else's display. No capture can find it. **The gate is an EQUALITY ACROSS STATES**, read from the block's own reported height (four states in the m28-knob-ui probe), plus `lineLimit(1)` on every status string for the states no wire verb can reach.
- ⭐⭐ **IF A SURFACE CAN OUTGROW EVERY AVAILABLE DISPLAY, GIVE IT AN INSTRUMENT FOR BEING LOOKED AT** (m28-knob-ui). With the section expanded, this card wants 971.5 pt against 934 pt of room at the tallest window this machine grants — so the new content is **always** below the fold and no window size makes a plain capture truthful. The probe cheerfully logged *"captured: the WHOLE expanded section, unclipped"* over a photograph the section was not in: a green check on an image of an absence. A scroller that a probe can drive (a request **counter** — an `onChange` on a flag already set is silent — plus an anchor on the card's last row, through the existing debug verb) is the difference between "a UI phase is not done until someone has looked at it" being a rule and being a wish. **A capture is only evidence of what is IN it.**
- ⚠️ **`.frame(minHeight:alignment: .top)` CENTRES THE HORIZONTAL AXIS.** A one-axis alignment still resolves both, so reserving vertical space with `.top` silently indents a wrapped second line. Use `.topLeading`. Found by looking at the render; **no test in the suite measures x**, so nothing else could have found it.
- ⚠️⚠️ **A CLAMPED MEASUREMENT LOOKS EXACTLY LIKE A REAL ONE** (m28-knob-ui). Once the cascade's last step engages, the card's drawn height IS its room — so the difference between two drawn cards is the difference between two clamps. Measuring the hardware section's cost that way returned **21.5 pt** for a block that is **285**, a plausible-looking number wrong by a factor of thirteen. **Measure the BLOCK, not the difference of the containers**: the block reports its own height (a `ScrollView`'s content keeps its natural size), and the constant is pinned against that reading rather than against a card height the display may be unable to show unclamped. The same trap has a sibling in the probe: a check that picks its branch from the value it is checking cannot fail — the branch must come from the budget's own claim (`predicted <= room`), not from `drawn`.

## Hardware mapping surfaces — the panel is quiet until the user asks (m28-knob-ui)

A panel that lets the user assign a physical control has one property no other panel has: **the act of listening is itself a side effect on their hardware.** Bringing the CoreMIDI client up connects to every online source on the desk. So the rules here are about restraint, and they generalise to any device-facing surface (MIDI learn, audio-device pickers, control surfaces).

- ⛔⛔ **OPENING A PANEL MUST NEVER OPEN A DEVICE.** The bring-up follows from the user pressing LEARN — never from an `onAppear`, never from a preview, never from a state refresh. ⚠️ **Find EVERY route in, not the obvious one**: here the observer install was the expected route and `availableMIDIInputs()` was the second one, because enumerating devices *is* the lazy client bring-up. A design that closed only the first would have been quiet in the test and loud on the desk.
- ⭐ **Make it structural, not a promise.** The view takes a model of **values and closures** and holds no `ProjectStore`; the model holds no engine. Then "this panel cannot wake the device layer" is a fact about types, and the gate is a source-shape test (`BreathPadHardwareSiteTests`) plus a behavioural one against a call-counting spy — **with a positive control, because a counter that cannot reach one proves nothing by reading zero.** `DAWApp` has no test target, so the structural half is the only thing that can see the view at all.
- **Name what you know; number what you do not.** A device seen during a learn is named; a `sourceID` an agent wrote through the wire and this session never enumerated is shown as **`device 4242`**, because resolving it would mean waking the client. "Any device" (`sourceID == nil`) is a **third state**, not a synonym for either — it is a deliberate wildcard, and collapsing it into "unknown" or "unbound" is wrong in opposite directions.
- ⭐⭐ **Show the LAST THING HEARD.** "I turn the knob and nothing happens" has two causes that are indistinguishable from every other part of a mapping panel — the control sends a CC you are not mapped to, or it sends nothing at all. A non-destructive last-event readout (CC number, value, channel, device) separates them without leaving the panel. It reports **unmapped** controllers too; that is the entire point.
- **State the feed, and state it from reality.** A LISTENING indicator reads the actual subscription (an engine holding the observer), never the intent to be subscribed — the two came apart once and every variable insisted the feed was live while the control was dead. The three cases are genuinely different diagnoses and get different sentences: listening / mapped but no engine / nothing mapped, *so we are deliberately leaving your gear alone*.
- **Say out loud what is not saved.** A mapping that belongs to the desk and not the song must say so on the panel ("not saved into the project… forgotten when DAW Pro quits"). Said out loud it is a limit; discovered after a relaunch it is a bug.
- **An armed learn is MODAL-SCOPED.** Closing the panel disarms it. Otherwise the app sits waiting to capture the next controller change on the desk with nothing on screen saying so, and one stray mod-wheel nudge silently re-points the control.
- **Collapsed by default, but the collapsed row carries the DIAGNOSTIC** — not a teaser. What hides behind a disclosure is the *editor*; "2 knobs mapped · listening" stays visible. The reason is arithmetic and belongs in the budget: an always-expanded editor moved this card's scroll threshold from ~689 pt to ~860, i.e. it would have scrolled at nearly every real window size.
- **An on-screen control for every mapped dimension, sharing ONE value with the hardware.** A knob-mappable parameter gets a real on-screen knob beside its gesture control, rendering the same model value — so a hardware turn visibly moves the cap and there is one position, not three copies of it. ⛔ **Reuse the house knob** (`KnobControl`) rather than adding a release hook to it: open the streaming gesture only on a tick that genuinely changes the value, which makes *"we opened a gesture"* and *"`onCommit` will fire"* the same condition. Otherwise a plain click — a complete zero-translation drag — opens a gesture nothing ever closes, and parks a live preview on the instrument. Compare the **travel fractions**, not the values they map to: the round trip through radians is not bit-exact, and an inexact comparison leaks that gesture at arbitrary positions.
- ⛔ **ONE KNOB RESETS ONE AXIS.** `KnobControl.onReset` restores *the value that knob displays*, and nothing else. Wiring two knobs to a shared "reset both" is a control silently moving a parameter it does not name — here, double-clicking DEPTH swung the ANGLE. ⚠️ **The test asserted the coupling, so a defect shipped with a green gate certifying it**: a test written from the implementation inherits the implementation's bugs as requirements. Write the assertion from the CONTRACT. And a reset restores the value the surface OPENS with, never the value that disables the primary button — a double-click that greys out the commit reads as a broken panel, not as a reset.
- **The on-screen knob is the same SOURCE as the pointer** (`.pointer`), so the existing "the pointer wins" precedence covers hand-vs-hardware with no second rule to keep in step. And **replace the plain readouts you are duplicating** — `KnobControl` already draws its label above and its SF Mono value below, so keeping both prints every number twice and costs a row the card does not have.
- ⚠️ **A derived presentation struct is CONSTRUCTED on every read — build it once per body.** `hardware.state` composes an array of rows plus several strings; reading it three times in a header meant three allocations per body evaluation, on a card that re-evaluates on every drag frame of the dial above it. Hoist it to a `let` at the top of `body` and pass it down. This is the ordinary shape of the no-allocation-per-frame rule on a surface that is not itself a `Canvas`.
- ⚠️ **A plain (non-`@Observable`) controller needs a push, and the push needs an equality guard.** The mapping table lives in a plain class, so nothing invalidates a view when it changes: the app pushes it in on every pump pass **and** on every agent-driven mutation (a wire write is invisible to a pump, which only speaks when a control physically moves — MEASURED, the panel read "No knobs mapped" over a live binding). The pump ticks ~30 Hz including **empty** passes, so an unguarded write to an `@Observable` property invalidates the whole card at that rate forever.

## Generation progress card

The **generation progress card** is the canonical violet surface — violet marks AI identity and nothing else; the card lives in-window (never a popover), the FAILED state is red with the reason verbatim, and it offers no affordance the engine cannot honor (no cancel button exists because the engine has no abort).

## Destructive actions, and the two routes to every one of them

**Every destructive operation must be reachable WITHOUT the keyboard** (m23-cf). A key press is not an affordance: it is invisible, it is undiscoverable in Simple mode, and when its delivery fails the operation does not degrade — it disappears. A user reported exactly that about notes and clips (*"once notes are added, I cannot remove them"*), and they were right: DELETE was the only route, so a dead key meant a dead feature. The standing rule is now **key path + menu path, always** — a context menu on the object, and, where the operation has an app-wide meaning, an Edit-menu item.

**A destructive item NAMES ITS BLAST RADIUS.** "Delete Clip" / "Delete 3 Clips" / "Delete 3 Notes", never a bare "Delete" that could mean one thing or twelve (Rule 6 — the beginner test applies hardest where the action cannot be taken back by looking away). The label and the target come out of **one producer** so they cannot disagree: `DAWAppKit.DeleteMenuPolicy` returns the title and the target together, and the handler is handed the same value the user was shown. A menu reading "Delete Clip" while the action removes three is worse than no menu at all. Where the count genuinely is not knowable at that layer, the label says so honestly ("Delete Selected Notes") rather than interpolating a number from somewhere else.

**`role: .destructive`, and the item exists even when it is inert.** A greyed "Delete" teaches that the operation is there and needs a selection; an item that vanishes teaches nothing, and is indistinguishable from the bug. So a disabled destructive item is SHOWN — and drops its count, because a greyed "Delete 5 Clips" claims a pending action that is not pending.

**Deletion is never Pro-only.** Clip-edit chrome (split, fades, quantize, crossfade) is Pro density per sp-c, but removing an object is the other half of creating it. Gating deletion behind Pro is what left Simple-density clips with **no context menu at all** — the density built for beginners was the one with no escape route.

⚠️ **A DESTRUCTIVE MENU ITEM MUST NOT CARRY A BARE-KEY EQUIVALENT.** Menu key equivalents are checked **before text insertion**, so `.keyboardShortcut(.delete)` on an Edit-menu item steals Backspace from every rename field in the app (the m17-d trap, written up on `ContentView.ArrangeDeleteKey`). ⭐ **The hazard belongs to the SHORTCUT, not to the ITEM** — a menu item with no key equivalent carries none of it, which is exactly why the menu path can be added without touching the `.onKeyPress` handlers that already exist. Add the route; never move the key.

**Menu enabled-state must be built from observable state only.** A `Commands` body re-evaluates on `@Observable` changes, not when the menu opens, so a term read from AppKit (`NSApp.keyWindow.firstResponder`, say) freezes at whatever it was when the body last ran — and a destructive item showing a stale count or a stale grey is the one staleness that costs the user something. If a guard cannot be expressed in observable state, keep it out of the enabled predicate **and** out of the action, so what was offered and what runs can never diverge.

**Where a selection lives on several surfaces, the menu obeys the KEY path's precedence — expressed without focus.** Piano-roll notes, then automation points, then arrange clips (`DeleteMenuPolicy.editMenuItem`, mirroring `AppModel.handleArrangeNudgeKey`'s guard stack). On the key path that ordering is structural — the editors own `.onKeyPress` as focused descendants — but a menu that depended on the same focus would inherit the same failure it exists to work around, so it reads the selection bridges instead. Right-clicking an object that is IN the selection acts on the whole selection; right-clicking one that is not acts on that object alone and leaves the selection untouched.

**Both routes call the same store function.** Undo must behave identically whichever way the user got there, which means the menu never re-implements the operation — it reaches the editor's own handler (via a bridge nonce, for surfaces whose model is `@State private`) or calls the same `ProjectStore` method the key handler calls.

⚠️ **A `.contextMenu` ON A `Canvas` SURFACE NEEDS `.contentShape(Rectangle())` — and its absence is silent.** MEASURED at m23-cf on staging: identical synthetic right-clicks opened the arrange clip's menu and did **nothing** on the piano-roll grid. A `Canvas` draws but contributes no hit-test region, and the two modifiers do not agree about what that means — SwiftUI **gestures** resolve against the view's FRAME (which is why the grid's drag, pinch and double-tap all worked without one), while **`.contextMenu`** resolves against the AppKit hit region and so passes straight through. The failure looks exactly like a missing modifier, in a codebase where every meter, scope, waveform and note grid is a `Canvas`. Rule: **any custom-drawn surface that takes a context menu declares its content shape**; a surface that draws real filled shapes (the arrange clip block) gets its region for free and is not evidence to the contrary. Adding one is not free of risk either — `.contentShape` rewrites the hit region the surface's *other* gestures resolve against, so **re-exercise the left-button paths after adding it**: at m23-cf the grid's note drag (p60 beat 0 → 4) and double-tap add (3 notes → 4) were both re-measured live afterwards, because nothing in the Swift suite can see them.

**A trailing `Divider()` in menu content is collapsed — MEASURED, and measured with a calibrated probe.** A/B on staging (m23-cf, macOS 26), reading the menu's own window off the window list at layer 101: the Simple-density clip menu was `99 × 34` with the separator guarded *and* `99 × 34` with it emitted unconditionally, while a calibration build of `Button + Divider + Button` read `165 × 69`. The 34 → 69 step (item ≈ 23 pt, separator ≈ 12 pt) is what makes the first pair a real negative rather than a blind instrument. Guard the separator anyway — it states the intent where a reader can see it instead of leaning on undocumented AppKit behaviour — but do not claim the guard prevents a visible artefact. ⚠️ **Note what could NOT have decided this: a keyboard-driven menu check.** A separator is unselectable, so Down still lands on the item either way; and the window list is also the only way to answer *"did the menu open at all?"*, because AX cannot see open menus and `screencapture` needs a Screen-Recording grant.

## Rules

1. Dark theme is the product; light theme is out of scope until M9+.
2. No stock gray AppKit controls in the main window — custom or restyled.
3. One accent color per meaning; never reuse cyan for anything but playback/activity. Create/add affordances (the "+" glyphs) are **neutral chrome** — `textPrimary` on the raised chip, no accent and no glow at rest (the standard hover-brighten is fine); an accent is earned by state, not by inviting a click.
4. Animation: 120–200ms ease-out for state; meters/positions animate continuously, chrome never bounces. **A transient notice that dismisses ITSELF fades out slower than it faded in — 0.15 s in, 0.3 s out** (`PianoRollView.flashBarOpsNotice`, the m23-an header-click chip): the 120–200 ms band is for a change the *user* just caused and is waiting on, while an unrequested disappearance should not snap away in the corner of the eye. Arriving is a state change; leaving is not.
5. Text contrast ≥ 4.5:1 for labels; readouts may glow but must pass at core color.
6. Beginner test: every panel understandable by a newcomer in Simple mode without a manual. If a label needs a manual, rewrite it.
