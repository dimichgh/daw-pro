# daw-pro-mcp

A TypeScript [MCP](https://modelcontextprotocol.io) server (stdio transport) that gives AI agents
control of DAW Pro. It does two things:

1. **Bridges to the app.** `src/bridge.ts` connects to the DAW app's control-protocol WebSocket
   (`ws://127.0.0.1:${DAW_CONTROL_PORT}`, default `17600`) and turns MCP tool calls into control
   commands — transport, tracks, and a full project snapshot. See `docs/ARCHITECTURE.md` for the
   protocol.
2. **Calls AI providers directly.** `src/ai.ts` calls Anthropic/OpenAI/Suno over HTTPS for lyrics,
   full-song, and image generation — no DAW app required for these.

The server holds no DAW state of its own; `project_snapshot` always reflects the live app.

## Build & run

```sh
cd mcp-server
npm install
npm run build
npm start          # = node dist/index.js
```

For development, point an MCP client (Claude Code, Claude Desktop, etc.) at
`node mcp-server/dist/index.js` via stdio — see the repo's `.mcp.json`.

Requires Node.js >= 22 (uses the global `fetch` and `WebSocket` — no `node-fetch` or `ws`
dependency).

## Environment variables

Copy `.env.example` (repo root) to `.env` and fill in what you need. Keys are read from the
environment only — never hardcoded, never logged.

| Variable | Default | Used by |
|---|---|---|
| `DAW_CONTROL_PORT` | `17600` | `DawBridge` — port of the app's control WebSocket |
| `ANTHROPIC_API_KEY` | — | `generate_lyrics` (primary provider) |
| `OPENAI_API_KEY` | — | `generate_lyrics` (fallback provider), `generate_image` |
| `OPENAI_TEXT_MODEL` | `gpt-4o` | `generate_lyrics` OpenAI fallback |
| `OPENAI_IMAGE_MODEL` | `gpt-image-2` | `generate_image` |
| `SUNO_API_KEY` | — | `generate_song_suno` |
| `SUNO_API_BASE` | `https://api.suno.com/v1` | `generate_song_suno` |

`generate_lyrics` uses Anthropic if `ANTHROPIC_API_KEY` is set, otherwise falls back to OpenAI if
`OPENAI_API_KEY` is set, otherwise throws telling you to set one of them.

**Note:** the Suno API integration (`generate_song_suno`) is a best-effort, defensively-coded
implementation — Suno's official current endpoint shape has not been verified. See
`docs/AI-INTEGRATIONS.md`, "Research items (M6)". It returns the raw JSON response from Suno as-is
rather than assuming a shape, and surfaces the raw response body on any error.

| `fx_describe` | `fx.describe` | Look up the parameter schema (`{name, min, max, default, unit}`) for one or every available effect `kind`; omit `kind` to list all; available: `gain` (linear gain stage), `eq` (4-band parametric — low shelf, two peaking bands, high shelf), `compressor` (soft-knee, stereo-linked dynamics — and the DE-ESSER: `detectorMode` 0 (default) is OFF and bit-for-bit the compressor this kind has always been, 1 is a BAND-PASS detector around `detectorFreqHz`, 2 a HIGH-PASS one. ⛔ There is NO separate `deEsser` kind — a de-esser IS a compressor whose DETECTOR hears only the sibilant band, so park `detectorFreqHz` on the 'sss' (5000-9000 Hz) and it ignores the rest of the voice. `detectorQ` is the band's WIDTH at mode 1 and the corner's RESONANCE at mode 2 (default 2 = +6 dB there; 0.707 is flat). ⛔ WIDEBAND, not split-band: the WHOLE signal ducks for the length of the 'sss' — fine on a solo voice, wrong on a full mix — which is why it adds ZERO latency. With a sidechain key attached it is the KEY that gets filtered. `detectorMode` is DISCRETE (hold steps, never a ramp; modulation refuses it); the other two zipper under modulation and are WARNED), `limiter` (lookahead brick-wall, adds 5 ms latency — see `project_snapshot`'s `latencySamples`), `reverb` (Freeverb-style room — roomSize/damping/mix/preDelayMs/width; ⚠️ `roomSize` is a DECAY control, not a size — the comb lengths are compile-time constants so this room has exactly one shape forever — and one `damping` setting covers the whole spectrum; use `hallReverb` when you need a real size, a decay in seconds, or separate bass/treble decay times. NOT deprecated: its small, bright, dense room is its own sound), `delay` (stereo echo — timeMs/feedback/mix/pingPong/highCutHz; `feedback` reaches 0.999 = an ECHO FREEZE, the repeats hold instead of fading — it stops short of 1.0 because at exactly 1.0 the loop grows without bound, measured, and at that ceiling `highCutHz` is what bounds the tail), `saturator` (tanh drive colour — `driveDb`/`mix`/`outputDb`/`oversampling`: BENDS the wave instead of cutting it, so quiet parts pass almost untouched and loud parts squash toward a limit they never quite reach. ⛔ **NOT `clipper`**: `tanh` only ASYMPTOTICALLY approaches its bound, so this kind can never promise a peak ceiling — reach for `clipper` when a level must not be exceeded, and this one when you want the sound to thicken. ⭐ **`oversampling` (1/2/4) DEFAULTS TO 1, WHICH IS THE OPPOSITE OF `clipper`'s DEFAULT OF 4, AND IT IS NOT A QUALITY JUDGEMENT.** This kind shipped long before the control existed, so projects already using one must keep sounding exactly as they did; at 1 the machinery is skipped entirely and the effect is bit-for-bit what it always was — pinned, off rendered audio, by `scripts/gates/m39ad-saturator-default-bytes.mjs`. **If you are adding a saturator today and driving it hard, set `oversampling` to 4**: bending a wave creates tones above Nyquist that FOLD BACK as an inharmonic metallic fizz, and 4× moves the fold out of the band — measured at 90.28 dB of alias-floor reduction by `scripts/gates/m39ad-saturator-physics.mjs`. Only 1, 2 and 4 exist; 3 rounds UP to 4. ⚠️⚠️ **THIS KIND'S LATENCY DEPENDS ON THAT KNOB** — 0 samples at 1, 32 at 2 or 4 — which is unlike `clipper`, whose 32 is constant at every setting. Delay compensation removes it either way; read `latencySamples` back from the `fx_add`/`fx_set_param` result rather than assuming. At `oversampling` 1 a `mix` of 0 is an untouched buffer; at 2 or 4 it is the input DELAYED BY 32 SAMPLES, sample for sample. ⚠️ `oversampling` is DISCRETE and is **neither automatable nor modulatable** — creating a lane on it is refused, because moving it from the render thread would leave the delay-compensation plan stale. Every `fx_add`/`fx_set_param` result also echoes `resolvedOversampling` (the SNAPPED value the render thread uses), `latencySamples` and `aliasRejectionDb` inside that insert's `params` (per-instance/constant echoes, NOT part of `fx_describe`'s schema)), `gate` (noise gate — thresholdDb/attackMs/holdMs/releaseMs), `chorus` (2-voice modulated thickener — rateHz/depthMs/mix), `bassEnhancer` (psychoacoustic sub harmonics — synthesizes the 2nd/3rd/4th partials of the sub-crossover content so a speaker that cannot reproduce the fundamental still implies it; NOT the broadband `saturator`), `bitCrusher` (SP-1200 / MPC60 lo-fi sampler character — bit-depth + sample-rate reduction, deliberately no anti-aliasing and no dither, because the aliasing IS the reference sound), `djFilter` (club / DJ-mixer sweep — ONE bipolar knob, `position` 0 is a bit-exact dry centre, negative sweeps a low-pass down, positive sweeps a high-pass up), `ringMod` (ring modulator — the metallic/bell/sci-fi-voice sound; multiplies the signal by a tone at `carrierHz` so every partial `f` becomes the PAIR `|f − carrierHz|` and `f + carrierHz`, i.e. a harmonic sound comes out inharmonic; under ~20 Hz it is a tremolo instead, and the clangorous fold-back at high carrier settings is deliberate character — pull `inputHighCutHz` to ~4000 for a cleaner bell), `flanger` (feedback flanger, the jet-plane whoosh — one swept comb filter; `delayMs` is the sweep FLOOR and the sweep moves only UPWARD from it, so a `depthMs` larger than `delayMs` is safe rather than broken; the first notch sits at 1/(2*delay) and every `fx_add`/`fx_set_param` result echoes it as `firstNotchHzAtSweepFloor` inside that insert's `params` (a per-instance echo, NOT part of `fx_describe`'s schema); `feedback` is BIPOLAR — negative inverts the response into a hollow metallic character — and it changes level, (1-mix) + mix/(1-feedback) on a steady tone), `hallReverb` (8-line FDN hall — the reverb that has an actual SIZE: `sizeMeters` 1–60 scales the delay-line lengths, `decaySeconds` is a real RT60 in seconds, `lowDecayMultiplier`/`highDecayMultiplier` give bass and treble their own decay times around `lowCrossoverHz`/`highCrossoverHz`, `modRateHz`/`modDepthMs` are the anti-metallic tail modulation, `freeze` ≥ 0.5 is infinite hold; `highDecayMultiplier` defaults to 0.5 rather than 1 because real air absorbs highs and a reverb with no HF damping is what "metal tank" means; ⚠️ moving `sizeMeters` while a tail is sounding gives a smooth Doppler glide), `tapeDelay` (tape echo, FREE-MS ONLY — timeMs/feedback/mix/wowDepthMs/wowRateHz/flutterDepthMs/saturationDrive/highCutHz: the echo whose repeats WOBBLE IN PITCH, which `delay` structurally cannot do — it reads its line at whole-sample offsets only, so a sub-sample drift is unrepresentable there. `wowDepthMs` is the slow motor drift and is the identity; every `fx_add`/`fx_set_param` result echoes the pitch deviation each setting causes as `wowCents`/`flutterCents` inside that insert's `params` (per-instance echoes, NOT part of `fx_describe`'s schema), so you can ask for a stated amount of wobble instead of guessing. `saturationDrive` 0 is EXACTLY linear; `highCutHz` sits in the RECORD path, so unlike `delay` even the FIRST repeat is already rolled off. ⛔ NO tempo sync on this kind in v1 — `delay` is the one with `sync`/`division`), `stereoWidth` (mid/side widener and mono-maker — `width`/`spread`/`bassMonoHz`/`bassMonoAmount`: the one effect whose headline is a GUARANTEE rather than a sound, because it touches only the side channel and so its mono fold-down is arithmetically identical to its input's at every setting — unlike a Haas delay or a polarity-flipped duplicate, which widen on speakers and then collapse on a phone. `width` scales the stereo difference you already have and costs nothing, but ⚠️ does NOTHING on a mono source, and ⛔ `width` 0 ALONE IS NOT A MONO-MAKER — `spread` defaults to 0.3 and builds a new side channel *after* `width` has scaled the old one, so folding a track to dead centre needs `width` 0 AND `spread` 0 together; `spread` manufactures a new side channel out of the centre through a four-stage all-pass chain and is the true-pseudo-stereo control, at the cost of a per-channel ripple that every `fx_add`/`fx_set_param` result echoes as `channelPeakDb`/`channelNotchDb` inside that insert's `params` (per-instance echoes, NOT part of `fx_describe`'s schema); `bassMonoHz`/`bassMonoAmount` keep the low end centred at 12 dB/oct and are ON by default. ⛔ NO `mix` on this kind — a dry/wet blend on a mid/side widener is algebraically just another `width`; the neutral BIT-EXACT position is `width` 1, `spread` 0, `bassMonoAmount` 0), `phaser` (swept all-pass phaser — `rateHz`/`centerHz`/`depthOctaves`/`stages`/`feedback`/`mix`/`stereoPhaseDeg`: ⛔ **NOT a flanger**, and that is the only thing anyone gets wrong about it. A flanger sums with a DELAYED copy and puts DOZENS of evenly spaced notches in at 1, 3, 5, 7 × a base frequency — metallic, jet-like. This kind has no delay line: it sums with a PHASE-SHIFTED copy and puts in exactly `stages` ÷ 2 notches — a handful — UNEVENLY spaced and spreading apart as they climb. Few, uneven, spreading is the soft vocal “wow” a phaser is for. `stages` is therefore the notch COUNT control, EVEN numbers only (an odd value snaps to the nearer even one, and the snapped value is what comes back). `centerHz` is where the sweep bottoms out and is NOT itself a notch — the lowest notch sits well below it — and every `fx_add`/`fx_set_param` result echoes `notchCount`/`firstNotchHz` inside that insert's `params` (per-instance echoes, NOT part of `fx_describe`'s schema). `depthOctaves` 0 FREEZES the sweep into a fixed notch filter, which is a real setting; `feedback` is bipolar, sharpens the peaks between notches, and ⚠️ changes the LOUDNESS; `mix` 0 is a BIT-EXACT bypass and 0.5 is where the notches are deepest. ⚠️ `mix` 1 with `feedback` 0 is very nearly INAUDIBLE and that is correct — an all-pass chain alone changes no frequency's level, so with no dry signal to cancel against there is nothing to hear), `transientShaper` (transient designer — `attackDb`/`sustainDb`/`attackMs`/`sustainMs`/`outputDb`/`mix`: changes how HARD a sound starts and how LONG it rings, and nothing in between. ⛔ **NOT a compressor and it has NO threshold**, deliberately — it responds to how fast the signal is rising or falling relative to its OWN running average, so it compares the sound to ITSELF and turning the fader down does not turn the effect down. `attackDb` is PUNCH (the front of each hit), `sustainDb` is BODY (the ring-out), and the two are INDEPENDENT by construction. ⚠️ A POSITIVE `sustainDb` LENGTHENS the tail and a negative one SHORTENS it. ⭐ The dB numbers are MAXIMA, not promises: the full amount lands only on a hit starting at least 12 dB above its own running average, and every `fx_add`/`fx_set_param` result echoes `attackWindowMs`, `fullShapeDifferentialDb` and `detectorFloorDb` inside that insert's `params` (per-instance/constant echoes, NOT part of `fx_describe`'s schema). Nothing at all happens below −70 dBFS so room tone is never shaped, and nothing audible happens on material with no onsets such as a held pad — both deliberate. At its defaults it is BIT-EXACT DRY and it adds ZERO latency), `freqShifter` (frequency shifter — `shiftHz`/`fineHz`/`stereoSpreadHz`/`mix`/`outputDb`: moves every partial by the same number of **Hz**, where a pitch shifter multiplies every partial by the same **ratio**. ⛔ **IT DOES NOT PLAY IN TUNE, and that is the feature** — adding a constant to every partial destroys the harmonic series, so 100/200/300 Hz becomes 200/300/400 Hz and the ear hears a BELL or a sheet of METAL rather than a note. Reach for a pitch shifter if you want in-tune. ⛔ **NOT `ringMod` either**: a ring modulator is DOUBLE-sideband (it emits both `f + fc` and `|f − fc|`, and the input vanishes) while this is SINGLE-sideband — one sideband survives and the other is rejected by ~50 dB, measured off a rendered sine rather than asserted. `shiftHz` is coarse and `fineHz` is fine; they are ADDED and the SUM is clamped to the coarse range, so the advertised range is the real one. ⭐ **THE SIGN IS THE DIRECTION** (positive up, negative down) — there is no mode switch, so it sweeps continuously through zero, which is exactly what a discrete direction param could never do. ⭐ The famous use is NOT a big shift: 1–20 Hz on `fineHz` makes the sound beat slowly against itself for a thickness no chorus can produce, and is the oldest fix in live sound for a microphone on the edge of feedback. `stereoSpreadHz` shifts the two sides by different amounts (1–6 Hz churns the image; it partly cancels in mono). ⚠️ Shifting DOWN by more than a partial's own frequency pushes it below 0 Hz and it REFLECTS back up — 100 Hz shifted −300 Hz returns at 200 Hz — which every analog Bode shifter does too. Every `fx_add`/`fx_set_param` result echoes `effectiveShiftHz`, `sidebandRejectionDb` and `hilbertPhaseErrorDeg` inside that insert's `params` (per-instance/constant echoes, NOT part of `fx_describe`'s schema). `outputDb` trims the SHIFTED copy only, so `mix` 0 stays BIT-EXACT DRY at any trim, and it adds ZERO latency), `clipper` (hard/soft clipper with oversampling — `driveDb`/`ceilingDb`/`mode`/`oversampling`/`mix`/`outputDb`: a HARD CEILING — everything above `ceilingDb` is cut off, which is how loud masters and hard-hitting drums are actually made. ⛔ **NOT `saturator`**, and the difference is exact rather than a matter of degree: `tanh` only ASYMPTOTICALLY approaches its bound, so a saturator can never promise a peak ceiling, while BOTH of this kind’s modes reach the ceiling at a finite input and stay there (`hard` immediately, `soft` at 1.5× the ceiling through a cubic knee). ⛔ **NOT `limiter` either** — a limiter rides a GAIN to avoid clipping and keeps the waveform’s shape; this deforms the waveform on purpose, which is where the loudness and the bite come from. Clipping starts at an INPUT level of `ceilingDb − driveDb`, which neither knob shows on its own and every `fx_add`/`fx_set_param` result echoes as `clipThresholdDbfs`. ⭐ **`oversampling` (1/2/4, default 4) is the quality control and the reason this kind exists**: hard clipping generates harmonics far above Nyquist that FOLD BACK as inharmonic metallic fizz, and running the shaper at 2× or 4× moves the fold out of the audio band — measured, off rendered audio, by `scripts/gates/m39ac-clipper-physics.mjs`. `1` is a SHIPPED setting rather than a degraded one: plenty of records want the grit, and it is the only way to hear what the other settings remove. Only 1, 2 and 4 exist; 3 rounds UP to 4. ⚠️ The ceiling bounds SAMPLES, not TRUE PEAK — the wave drawn between samples can ride about a decibel higher, which is what a broadcast meter reads; follow with a `limiter` at `truePeak` 1 if you need that guarantee, and note a positive `outputDb` raises the real maximum to `ceilingDb + outputDb` (echoed as `wetCeilingDbfs`). ⚠️ `mode` and `oversampling` are DISCRETE — automate them with `hold`, never a ramp. ⛔ **Unlike every other built-in except `limiter`, this kind REPORTS LATENCY**: a CONSTANT 32 samples at every `oversampling` setting including 1, removed automatically by delay compensation — so at `mix` 0 the output is the input DELAYED BY 32 SAMPLES, sample for sample, rather than an untouched buffer. Every `fx_add`/`fx_set_param` result also echoes `resolvedMode`, `resolvedOversampling` (the SNAPPED values the render thread actually uses), `latencySamples` and `aliasRejectionDb` inside that insert’s `params` (per-instance/constant echoes, NOT part of `fx_describe`’s schema)), `dynamicEQ` (four-band dynamic EQ, the LARGEST kind in the app at 32 params, band-major — `band1Mode`/`band1Freq`/`band1Q`/`band1ThresholdDb`/`band1Ratio`/`band1RangeDb`/`band1AttackMs`/`band1ReleaseMs` repeated for bands 2–4 (`slot = (band−1)·8 + p`): a normal EQ band whose gain moves only once the signal crosses a threshold, so it corrects the moment that needs it and leaves the rest alone. BELLS ONLY in v1, no shelves. `bandNMode` 0 (default) is OFF — a TRUE no-op, the band's filter is not even run, so a fresh insert is bit-for-bit transparent; 1 is ABOVE (reacts when the level inside the band rises past `bandNThresholdDb`); 2 is BELOW (reacts when it falls under it). ⭐ `bandNMode` × the SIGN of `bandNRangeDb` gives FOUR musical moves from two knobs: above+negative (the default sign) de-esses or tames a resonance, above+positive exaggerates a transient, below+positive restores air on a quiet passage, below+negative is one-band downward expansion. ⚠️ `bandNMode: 2` sits at FULL RANGE ON SILENCE and that is correct, not a bug — digital silence reads as −180 dBFS, under every threshold. ⚠️ **THIS `Q` IS NOT `eq`'s `Q`**: at 1 kHz, Q 2, this band is about 704 Hz wide where an `eq` peaking band is about 498 Hz, and unlike `eq` this band WIDENS as it works harder — a Q ported from `eq` will not sound the same. No per-band `mix` and no lookahead, so this kind adds ZERO latency at every setting; there is NO gain-reduction meter in v1 — poll `fx_spectrum` during playback to see a band actually moving. Every `fx_add`/`fx_set_param` result (NOT `fx_describe`) echoes `band1ModeLabel`…`band4ModeLabel` (the SNAPPED mode as a string, "off"/"above"/"below"), `latencySamples` (always 0) and `kneeDb` (a fixed 6, not a param). ⚠️ `bandNMode` is DISCRETE — `fx_set_param` clamps a stored value to 0–2 but does NOT round it, the `phaser.stages`/`clipper.mode` precedent, so automate it with `hold`, never a ramp; modulation refuses it outright, and `bandNFreq`/`bandNQ` are WARNED under modulation (filter coefficients, the `eq.peak1Freq` problem). ⚠️⚠️ **BUDGET**: automation lanes and modulated effect params SHARE ONE 64-entry cap per mixer strip, and ONE fully-automated `dynamicEQ` instance is 32 of them — half a strip. `mod_add_route` refuses past the cap and names both contributors, but `automation_add_lane` does NOT check it — past 64 the render schedule silently keeps only the first 64 effect-param tracks and drops the rest, no error, no warning) |

| `clip_add_audio` | `clip.addAudio` | Import an audio file (wav/aiff/mp3/m4a) as a clip on an audio track; length auto-computed from file duration at current tempo |
| `clip_add_midi` | `clip.addMIDI` | Create a MIDI clip on an instrument track and write its notes in one call (pitch, velocity, startBeat relative to the clip, lengthBeats); returns the clip with server-minted note ids, notes normalized/sorted; silent until an instrument lands (M3) |
| `clip_set_notes` | `clip.setNotes` | Replace a MIDI clip's entire note array — the only note-editing primitive; one call = one undo step; errors on audio clips |
| `clip_remove` | `clip.remove` | Permanently remove a clip (audio or MIDI) from its track by id; reversible with `edit_undo`; returns the removed clip |
| `mixer_set_master_volume` | `mixer.setMasterVolume` | Set master output linear gain, 0–2 (1 = unity gain / 0 dB) |
| `render_mixdown` | `render.mixdown` | Bounce the session offline to a stereo 48 kHz WAV file; returns `{path, durationSeconds, sampleRate, channels}` |
| `project_save` | `project.save` | Save the session as a self-contained `.dawproj` bundle (project.json + copied media/); omit `path` to save in place; incremental re-saves; returns `{path, mediaFilesCopied, warnings}`; cannot save while recording |
| `project_open` | `project.open` | Open a `.dawproj` bundle, replacing the current session; unsaved changes auto-saved first unless `discardChanges`; returns `{warnings, snapshot}`; refuses while recording or if the project was saved by a newer app version |
| `project_new` | `project.new` | Start a fresh empty untitled session; unsaved changes auto-saved first unless `discardChanges`; returns the new empty snapshot; refuses while recording |
| `edit_undo` | `edit.undo` | Revert the most recent document edit (track/clip/mixer/tempo/loop/punch/metronome — not playback position); returns `{undone, snapshot}`; errors "nothing to undo"; refuses while recording |
| `edit_redo` | `edit.redo` | Reapply the most recently undone edit; returns `{redone, snapshot}`; errors "nothing to redo"; redo history clears once a new edit is made after an undo |
| `project_snapshot` | `project.snapshot` | Full session state: transport, tempo, master volume, tracks (each with routing: `outputBusId` and `sends` — see `track_set_output`/`track_add_send` — plus a PRE-FADER `effects` insert chain, an ordered array of `{id, kind, bypassed, params, latencySamples}` capped at 16 — see `fx_add`/`fx_remove`/`fx_reorder`/`fx_set_bypass`/`fx_set_param`/`fx_describe`), clips (MIDI clips carry a `notes` array: pitch, velocity, startBeat relative to the clip, lengthBeats; audio clips don't), live `meters` (peak/RMS) for master + each track — bus tracks meter here too, like any other track, `lastRecordingError` (null on success, else a string explaining the last `transport_record` take's failure), `undoLabel`/`redoLabel` (preview of what `edit_undo`/`edit_redo` would do, null if none), and optionally `midiInputs` (same shape as `midi_list_inputs`) and `midiEventCount` (monotonic counter of received MIDI events, pollable to detect live MIDI activity) |
| `generate_lyrics` | — (Anthropic/OpenAI) | Section-labeled lyrics from a theme (+ optional style/structure) |
| `generate_song_suno` | — (Suno) | Full song generation from a prompt (+ optional lyrics/instrumental) |
| `generate_image` | — (OpenAI) | Generate an image, saved as a PNG under `assets/generated/`, returns the file path |

Every tool returns its result as JSON text content; on failure it returns `isError: true` with a
human-readable message instead of throwing across the MCP boundary.

## Broadcast events

Besides request/response frames, the app also pushes unsolicited broadcast frames to every
connected control client, e.g.:

```json
{"event": "transport", "transport": {"playing": true, "positionBeats": 4, "loop": {"enabled": true, "startBeat": 0, "endBeat": 8}}}
```

These carry no `id` and are not replies to any tool call; `DawBridge` recognizes the `event` field
and silently ignores them (no pending request is resolved/rejected, nothing is logged).
